# Website

`src/Web/` is the community website. It is a Blazor Web App with interactive server rendering: pages are rendered on the server and kept alive over a SignalR connection, so it needs JavaScript. The pages and the theme live in `src/Ui/`, the same library the [launcher](launcher.md) uses; the website only adds the host, the language switch and the development switches.

## State

The screens follow the original website screen for screen (same theme, places, navigation and English texts; French uses the original French). With `SERVER_URL` set (the live site) the sign-in, the store, the profiles, the leaderboards, the wallet, the missions, the friends, the messages, the restore page and "Delete my data" are the community server's ([Sign-in](#sign-in), [Restore and your data](#restore-and-your-data)), and the news is the project's own; the other pages are hidden. Without it every page is the **mock**'s: the services in `src/Services/Mocks/` return fixed, fictional data and their actions do nothing real. The pictures are not in the repo: each one is a labelled box unless the operator supplies its file ([images.md](images.md)). See [launcher.md](launcher.md) for the service layer in `src/Services/Contracts/`.

Without `SERVER_URL` (development, the CI smoke test) every service is the mock. Its session starts signed in as a fictional hunter (`Hunter01`); sign out in the top bar to see the public site. Its sign-in is the email, then a six-digit code (there is no password), and it accepts any address with an `@` and any six digits. The live site has no email sign-in.

## Sign-in

Without `SERVER_URL` (development, the CI smoke test) everything above holds: the mock session and the email sign-in panel.

With `SERVER_URL` set (for example `http://server:8080`, the community server's address on the internal network) the website uses the server's Steam sign-in, which both serve on the same domain behind one reverse proxy. The server's `web_host` setting must be this website's domain, and the proxy sends the server's own paths (`/auth/*`, `/account/*`, `/hunters/*`, `/catalog/*`, `/photos/*`, `/stats/*`, the minigame boards) to the server ([deploy.md](deploy.md#the-community-server)); the website's server itself calls them over `SERVER_URL`.

- **Sign in**: "Already a hunter? Sign in" in the public bar (`src/Ui/Shell/PublicBar.razor`) is a plain link to `/auth/steam/login?next=<current path>`, a full page load. The server sends the player to Steam, asks for a handle the first time, sets the session cookie `hr_session` (HttpOnly, 30 days) and returns to `next`.
- **The sign-in's pages** (`src/Ui/Pages/SignIn/`, layout `SignInLayout`: the logo and one card, none of the shell's bars; `robots.txt` keeps `/signin/` out of search engines): the server does the sign-in and, at each step, redirects the browser to a page of the website: `/signin/handle` (the first sign-in picks a name; with an archive "I played before" restores the old profile), `/signin/confirm` (an app asks to be signed in, one "Yes, sign in": the launcher or the backup tool on this PC, which show no code, or the old launcher's start page, which shows one), `/signin/done` and `/signin/problem?reason=<key>` (expired, link, app, steam, banned, form, confirmed; any other key reads as expired). The pages are translated (`SignInPage.*` in the 19 `Strings*.resx`) and carry the operator's Discord invite (`LINK_DISCORD`) after a sign-in, nothing without one. A step page reads its state from the server with `ISignInService` (`GET /auth/pending` with the browser's `hr_login` cookie, which `App.razor` hands to the circuit like the session cookie, and `X-Requested-With`; the mock shows the steps for `?mock=signin:restore|confirm|app|none`) and draws a plain HTML form that the browser posts to the server itself (`/auth/handle`, `/auth/confirm`) with the token the state carries: the server keeps the logic, the cookies and the CSRF check, and the website changes no state. Without a sign-in in progress (or one of another step) a page says it ran out of time.
- **Who is signed in**: `ServerSessionService` (`src/Services/`) asks the server `GET /auth/me` with the browser's cookie; 200 gives the handle and the hunterscore (the status bar's paw), anything else (401, no answer within 5 s, an error) means signed out and never reaches the page. The paths and the JSON are in `src/Services/Contracts/ServerSessionApi.cs`. Nothing is cached: every read asks again. The answer also carries the wallet: `ServerWalletService` makes its own `GET /auth/me` for the balances (the status bar's em$ and gm$; 0 when the server does not answer), and the status bar shows no ammo or fuel days, which the server does not know.
- **Sign out**: the sign-out button opens `/logout`, which only shows a "Sign Out" button (opening the address signs nobody out); the click calls `POST /auth/signout` with the cookie and `X-Requested-With: XMLHttpRequest`, then shows the public site. The server deletes the session; if it cannot be reached the website is signed out for that tab only.
- **The cookie reaches the server** because the website forwards it: `src/Web/Components/App.razor` reads `hr_session` and the request's `Host` from the page request and passes them to `Routes` as parameters (the page's component marker is protected by data protection, so the browser cannot read it), where they fill a per-circuit holder. Blazor's `HttpContext` is not reliable once the circuit runs, so nothing reads it later. The server picks its site by `Host`, so the website sends the host the browser used.
- **The hunterscore** is the server's ([docs/server.md](server.md#the-hunterscore)) in three places: the status bar, the profile header of every player (`ServerProfileService` asks `GET /hunters/<handle>`: handle, hunterscore, rank, membership and avatar; a handle the server does not know, or a failed answer, is the "Page not found" page with HTTP 404) and the hunterscore board (`ServerLeaderboardsService`: `GET /hunters?page=<n>` for the rows, `GET /auth/me` for "Your rank"; a failed answer is an error with a **Try again** button, not an empty board). These two need the cookie ([Signed-in players only](#signed-in-players-only)); the website's server asks over `SERVER_URL`, the launcher through the proxy, which routes `/hunters/` to the server.
- **The statistics tab** of the profile page (`ServerProfileService.Tabs`, own and any other profile) is the lifetime statistics of the server ([docs/server.md](server.md#public-reads)): `TotalsAsync` asks `GET /hunters/<handle>/statistics` (with the cookie, as every `/hunters/` read: [Signed-in players only](#signed-in-players-only)) and shows the animals and the weapons, the distance and the hunt time; a failed answer is empty tables. A hunt played on the server is in it from its first events: the hunt in progress counts so far (at most one heartbeat behind), and when it closes its final statistics replace those. On the live site the tab has the lifetime, history and personal bests pills: there is no last hunt pill (the first row of the history is that hunt), and collectables stay empty. **The history** (`HistoryAsync`: `GET /hunters/<handle>/hunts?page=<n>`, 40 a page) lists the server hunts, then the saved ones; a start opens the hunt page (`ExpeditionAsync`: `GET /hunters/<handle>/hunts/<id>`) with the weapons, the animals, the distance, the time and the kills of that hunt, and a kill opens its score sheet (`/profile/<handle>/score/<id>`, `SheetAsync`: `GET /hunters/<handle>/score/<kill>`), all with the cookie. The reserve is the catalogue's name and the lodge the name of the start the hunt opened at, as the launch map names it (the hunt page shows both in its header). **A hunt in progress** (no end) says "In progress" in its header instead of the end time, shows the weapons, animals, collectables and kills its events have made so far, the time since it started, and a "-" for the distance (the game reports it only when the hunt ends); `HuntStats` reads the hunt again every 60 s (`Reload`, by its parent: the expedition tab, or the statistics tab's last hunt), about a heartbeat of the game, so the page follows the hunt without a reload and stops when the hunt has an end. The hunt page also lists what the hunt picked up and earned, each in a section of its own that is left out when empty (`HuntStats`, shared by the website and the launcher): the collectables (name, score, time), the achievements the hunt earned (title and description) and the shed antlers (species, single or double, score). A saved hunt shows the antlers and achievements its backup had, and no collectables (its backup holds per-type sums, not the pickups). A kill of a saved hunt has a link only when its backup zip held its score sheet page ([docs/restore.md](restore.md#pictures)): the sheet then shows the facts of the saved hunt and no worked rows (the game shows the saved page itself). A failed answer is an empty page or no page. **The personal bests** (`BestAsync`: `GET /hunters/<handle>/best?season=<n>`, with the cookie) list the best score of each species of the season (all time by default) with its weapon, time, score and range, as plain text (no link to a score sheet) and with the season list of the boards; a player with none, or a failed answer, sees the "no expeditions" text.
- **The ranks tab** (`ServerProfileService.Tabs`, own and any other profile) is the server's ([docs/server.md](server.md#public-reads)): `RanksAsync` asks `GET /hunters/<handle>/ranks` (with the cookie). The overview shows the hunterscore bar and the three category bars (animals, weapons, collectables) as the sum of the rows, each row counting to the cap (1000) at most, written with thousands separators ("1,010 / 4,000"); a category page lists its rows by name, each with its whole count as the number (thousands separated, past the cap too) and its count up to the cap as the fill of its bar (full at the cap). `MilestonesAsync` reads the same answer: a milestone row is one achievement definition of its kind (animals, weapons, exploration, daily missions) with its thresholds and the player's counter, the steps reached being the thresholds at most the counter. The live achievements tab has the overview and the animals, weapons, exploration and daily missions pages (a page is its milestones, each with the achievement's own picture, slot `ach-icon-<icon>`); there are no challenges (no server source). A failed answer is no bars and no rows.
- **The boards** of the live site are the server's six (`ServerLeaderboardsService.Kinds`): the species score and range boards, the hall of fame, the hunterscore, and Lane Bandit and Bust Through. They are for a signed-in player: signed out, the page shows the sign-in prompt (`SignInRequired`) and asks the server nothing, and the server answers 401 `signed_out` to every board call. A board shows its **Top 100** (the hunterscore and the minigames in pages of 30, a species in pages of 25; no page goes further and no board says how many players it has) and, under the pages, **Around your rank**: the player's own place and the 50 above and below it that are past the top (`around` of the board's reply, `Page.Around`; none in the top 50 or when not ranked; [docs/server.md](server.md#who-sees-whom)). The species boards and the hall of fame answer for a **season** ([docs/server.md](server.md#leaderboards-and-seasons)): `GET /leaderboards/seasons` lists them, and the page shows the current one (Season 2, the community server's) by default with a selector (All time = 0, Season 1 "before the community server", Season 2 "community server", later ones "Season N"); the season is the address's `?season=<n>`, none for the current one. The overview shows the top three of every ranked species (`GET /leaderboards/<score|range>?season=<n>`), a species the top 100 in pages of 25 with rank, hunter, score or distance, weapon and date of the kill (`GET /leaderboards/<score|range>/<species>?season=<n>&page=<n>`), and "Your rank" for a signed-in player (`.../<species>/me`, 404 when not ranked: nothing is shown). The hall of fame (`GET /leaderboards/halloffame?season=<n>`) lists the best score and range of each species of an ended season, the last ended one by default; all time and the current season have none. The overview and the hall of fame list the species A to Z by the name the page shows, in its language (the server sends them in species id order). While the server answers, the page shows a placeholder; "Nobody is ranked here yet" is only for a board the server answered as empty. When the server does not answer (an error, or no answer within 30 seconds: the boards have their own HTTP client, `server-boards`, longer than the 5 seconds of the others) the page shows "The leaderboard could not be loaded. Please try again." with a **Try again** button that reads it again; `ILeaderboardsService` throws `BoardUnavailableException` for that, the player's own place (`MyRankAsync`) is simply none. The hunterscore keeps its own rows; Lane Bandit and Bust Through (`GET /leaderboards/<lanebandit|bustthrough>?page=<n>`: the best scores, restored or played, [docs/server.md](server.md#the-hunterscore)) show no "Your rank" (their window shows the player's place) and no store link for the Lane Bandit item, whose id is the mock's, and all three ignore the season. The antler boards are not offered: their tabs are gone, and their addresses go to `/leaderboards/score`. The mock has the same pages with fictional rows (`MockLeaderboardsService`).
- **The live site** (`HostMode.Live`, true exactly when `SERVER_URL` is set): a signed-in player sees only their own data from the server, or nothing. These pages are not served (`LauncherGuard.MockOnly`: bank, the Steam callback, new message, invite friends, welcome, community league, and the competitions, whose only recorded ones ended weeks ago; the address goes back to the feed), and their links are gone: the menu's competitions item, the "Settings" heading opens "Restore your backup" (the menu's account item opens the settings page, which has the avatar only, [Avatars](#avatars)), a trophy's link to its competition (its name stays, as text), and in the status bar the message count (the messages and wallet links and the em$ and gm$ balances stay), and the "Send message" buttons of the friends lists. What the player owns is gone from the pages that stay: the bundle's "Own" and own-limit columns and its "you own the most" line, and "your rank" on every board but the hunterscore. The bank dialogs are hidden (the bank sells em$ for real money). **Messages** are the player's own and read only (`ServerMessagesService`, [docs/server.md](server.md#messages)): the messages page lists the server's notices and the conversations a backup restored, and opens a thread; there is no field to write one and no "only from friends" setting, and the website marks nothing read, so the status bar shows no count. **Friends** are the server's (`ServerFriendsService`, [docs/server.md](server.md#friends)): the status bar's friends button counts the requests and opens the list with the search (from 3 characters, up to 10 handles that contain the text, the exact handle first; past 30 searches in an hour the server refuses and the list says to try again in an hour, `Friends.SearchLimit`), the accept and decline buttons and the remove button, and the profile of another hunter has the friend request button, disabled and marked sent once asked (and gone for a friend). The server gives requests and the list by handle (`GET /account/friends`: friends, requests and the requests the player sent, with which friends are online; `GET /account/friends/search?text=<text>`; `POST /account/friends/add` asks, or accepts the other's request, `POST /account/friends/remove` declines, cancels or removes, form `handle`, with the player's cookie and `X-Requested-With`); it keeps no time for a request, so they are sorted by handle, not oldest first. A profile is a player of the server or "Page not found" (HTTP 404), never a hunter of the mock pages. Its header is the server's: handle, membership title, hunterscore, rank, avatar ([Avatars](#avatars)) and the header picture the player chose (the slot `profile-bg-<name>`, the restored profile's `background` without its extension; no picture without one, where the mock shows its `profile-banner` box); the avatar sits between the polaroid's two pictures (`polaroid-back`, `polaroid-front`), and a missing front picture is not drawn. A tab with no server source would be hidden on its own: `ServerProfileService.Tabs` lists the tabs the page shows (`Profile.Tabs`; null on the mock, which shows them all), and the ticket that gives a tab its source adds its key there. An address of a hidden tab opens the first shown one; with none the page is the header only. Today all eight tabs (ranks, skills, statistics, trophies, dogs, friends, achievements and gallery) have a source, so none is hidden for that; the friends tab shows only on the player's own profile, on the live site and the mock alike (a player sees only his own friends). The ranks and statistics tabs are described above; a row of the ranks tab shows its rank's own picture, the slot `rank-<id>` of the rank's game id. `GET /hunters/<handle>/skills` gives the species with spotting and tracking rings and the weapons by category with a shooting ring, each a level and the percent of its span; `GET /hunters/<handle>/trophies?page=<n>` gives 24 trophies a page (the competition trophies of the restored `Trophy/list`: the trophy's name, the day it was won, its competition's name and its cup picture, the slot `trophy-<image>` of the picture's file name; the hidden ones are left out, and the kills of the lodges and of the server's hunts are not listed), and a competition link is never shown; `GET /hunters/<handle>/dogs` gives every owned dog with its name, its level and the percent of the way to the next, its breed skills and its ribbons (the rest of the inventory is not shown); `GET /hunters/<handle>/friends?page=<n>` (the signed-in player's own handle only; 403 for any other) gives 20 friends a page by handle with their hunterscore, each with a remove button; `GET /hunters/<handle>/achievements` gives the overview of the achievements tab (the progress of each category, the number unlocked and the last ten by earn time, with the day; the category pages come from the ranks reply's milestones, and there is no challenges pill); `GET /hunters/<handle>/gallery?page=<n>` gives 24 photos a page, newest first, each a picture the game uploaded (the tab's tile shows the full picture scaled to fill the tile (`object-fit: cover`), as the share window and the lightbox do, so shots taken on the server and restored ones look alike; the animal and its score are those of the kill the photo shows, a photo of no kill has neither; the caption links the kill's score sheet when the server has it, `kill` of the row), and on the player's own tab each photo has a delete button (`POST /account/gallery/delete`) and the whole gallery downloads as a zip (`GET /account/gallery/zip`), both with the session cookie; a failed answer is an empty tab. Without `SERVER_URL` (development, the launcher) nothing is hidden. On a profile's skills tab the species' pictures are `statistics-<define>` (the dog species and species 56 are not listed, as in the original) and the weapons' pictures, here and in the statistics tab, are `store-item-<id>` ([images.md](images.md)). The profile reads of a signed-in player count in his read limit ([docs/server.md](server.md#read-limits)): past 120 a minute the server answers 429.
- **Galleries** ([docs/server.md](server.md#gallery)): only your own gallery can be downloaded and shared. On another player's profile the gallery tab has no download button and no Share button, and `/profile/<handle>/gallery/download` goes back to the gallery; its tiles and its lightbox load the display-size copy the server gives another player, never the original. The picture links of `GET /hunters/<handle>/gallery` are keyed for the signed-in player, so the launcher's pages, which send no cookie, load them too; they hold until the end of the next day. The Share window on your own pictures hands out the row's `share` link, the display-size copy, which a signed-in player can open and anyone else cannot (401).
- **The wallet** (`ServerWalletService`) is the player's own history from the server ([docs/server.md](server.md#wallet-history)): `/wallet` opens the em$ history, with an em$ and a gm$ tab and no bank tab (`/bank` stays hidden; `/wallet/bank` opens the em$ history); the header's balances are the account's (`GET /auth/me`) and its totals spent `GET /account/wallet/spent`; the rows are `GET /account/wallet/ems` and `/gms` (50 a page, "Show more" asks the next), newest first: the restored history, then the purchases and rewards made on the server. A bought item shows by name, with its count when more than one; a reward has none. Without an answer the page is empty, never the mock's rows.
- **The missions** (`ServerMissionsService`, owner only: signed out, the sign-in prompt is shown in their place) are the player's own from the server ([docs/server.md](server.md#missions)): `/missions` is the regular page, with the active and available lists, the packs with their progress and favourites, the filters and the three switches, from one `GET /account/missions`; its writes are `POST /account/missions/<call>` with the cookie, the game's own: activating one mission or all available ones (a mission whose dependency is open is refused, and the page says so as the game does), favouriting a pack and the switches (turning one automatic setting on turns the other off). A mission's reserve, species and weapon filters use the first name its filter lists name (none when the list is empty, and then no option). **The daily missions** (`/missions/daily`, the menu's missions item) are the same service's: one `GET /account/missions/daily` gives the seven days of the streak (difficulty and gm$ reward of each), today's mission with its objectives and the time left, and whether the streak is frozen. Only today's card (the server's streak day, which turns over at the UTC day's end) is a button and opens its mission; the other days are shown but disabled, and the server holds no other day's mission. The mission shows the species card of the original: the `mission-species-<species>-<m|f>` picture by the `species` and `gender` the server gives ([images.md](images.md)). The frozen streak's "Activate" button is `POST /account/missions/daily/activate`. The server has no item to resume a broken streak, so the page offers none and the call fails. A server that does not answer, or holds no missions, is an empty page, never the mock's.
- **Taxidermy** (`TaxidermyButton`, `TaxidermyModal`) is on the player's own hunt page, in the launcher and on the website (wherever a hunt's kills are listed: the statistics tab's last hunt and the expedition tab). `GET /hunters/<handle>/hunts/<id|latest>` gives a harvest of the signed-in player's own a `taxidermy` member (`end` is when the offer runs out, the harvest plus 72 hours or the later end the server gives a harvest from before the go-live, the prices in em$ and gm$, whether the species has a skull to mount, and what was bought: `done`); the server gives it to nobody else and not for a restored harvest. While `done` is empty and `end` is ahead, the row has a **Taxidermize** button with the hours left ("71 h left", minutes in the last hour); it opens a dialog in the in-game page's spirit: the animal and its score, a row per product (Taxidermy, and Mounted Skull where the species has one) with an em$ and a gm$ button showing the price, an error line and the note about the lodge. A click is `POST /account/harvests/<kill>/taxidermize` (`ServerProfileService.TaxidermizeAsync`, [docs/server.md](server.md)): 402 shows "Not enough em$" or "Not enough gm$", 409 "already", 410 "too late", anything else a plain failure, and the player may press the other button. A purchase shows the original's thanks ("Taxidermied animal sent to Trophy Manager."), a short line about the trophy lodge in the game (the site has no lodge editor page), closes by itself, and the row keeps a "Taxidermized" or "Skull mounted" badge. The button goes when `end` passes (the row checks once a minute) and is not offered again. The mock (own hunts 1 to 4 back: 71 h left with a skull, 2 h left without one, taxidermized, skull mounted; older hunts are too late; the mock wallet pays, so the default 1,000 gm$ is "Not enough gm$" and the 100 em$ pay) takes `?mock=taxidermy:late`, `taxidermy:already` and `taxidermy:fail` to make every purchase refused that way.
- **The store** (`ServerStoreService`, with `SERVER_URL`) is the community server's catalogue ([docs/server.md](server.md#the-store-catalogue)): the original's categories, items with their prices, the sales (the struck-through price) and the bundles, for signed-in players ([Signed-in players only](#signed-in-players-only)). The server's answer is asked with the player's cookie, kept for 5 minutes and shared by every signed-in visitor (`ServerCache`); without a cookie the store is empty and asks nothing; a server that does not answer, or holds no catalogue, is an empty store ("No items in this category"), never the mock's. For a signed-in player the store list and the item page show what they own, read from `GET /account/inventory` ([docs/server.md](server.md#accounts)) once when a store page opens and again after a purchase (a search does not ask again): "You own: N" for a counted item (units summed over the copies), "Owned" for one copy of an item that is not counted, "You own: N" for several copies, and for a license "Expires: <date>" on the list and "You have a valid license until: <date>" on the item page, or "You have an unlimited license" (a license that has ended shows nothing; while the server's `all_licenses` is on, every license of the catalogue shows it, [docs/server.md](server.md#licenses)), and an item with an unlimited license has no buy button (`StoreItem.LimitReached`); the buy dialog says the same as the card; nothing for an item they do not own (`OwnedLine`; item 0 like any other). **Buying** is the server's (`POST /account/buy` with the player's cookie, [docs/server.md](server.md#buying-from-the-website)): the buy buttons of the store list, the item and the bundle open the buy dialog, which offers an em$ button and a gm$ button with their prices (only the one an item has a price for; the gm$ price is the catalogue's, never discounted, [docs/server.md](server.md#buying-from-the-website)), and a player short of em$ or gm$ gets that button disabled (no bank to send them to) and a line says why ("Not enough em$: you have N, this costs M", the same for gm$). An item the store lists as not buyable keeps the disabled "not buyable" button. After a purchase the status bar shows the new balance when the buy dialog closes (it reads the balances whenever a dialog opens or closes, besides its 30 second refresh); the game gets the items with its next heartbeat or connect. The pictures: an item or bundle of the live site looks for `store-item-<id>` and `store-bundle-<id>`, never the mock's `item-<id>` and `bundle-<id>` ([docs/images.md](images.md)), so it is a labelled box until its picture is mapped.
- **Unlimited ammunition in the store**: while the server's `unlimited_ammo` is on, its catalogue marks every ammunition `unlimited` and not buyable ([docs/server.md](server.md#unlimited-ammunition)); the list and the item page show "Unlimited ammunition" (`Store.UnlimitedAmmo`, `OwnedLine`'s `Unlimited`) in place of what the player owns, and the button says "Not buyable".

## Restore and your data

With `SERVER_URL` set, two pages here are real: the restore page and the data page. They need the community server, and without it the restore page says it is not available here. The rest of the live site is the server's too ([the live site](#sign-in)), or hidden.

The restore page is three steps (a stepper on top; a player with a result, a waiting zip or a claim lands on step 3, everyone else on step 1; the page is `src/Ui/Pages/RestoreBackup.razor`): **1. What do you have?** "I have a backup zip" or "I have no backup" (the second only when the server keeps old public profiles, `GET /account/archive` says `enabled`, and the account has not claimed yet); **2.** the upload (three checks, "All the rules", the file picker, Upload with a progress bar of the bytes sent per part, `IRestoreService.UploadAsync`'s `IProgress<long>`) or the claim; **3. What happens next**: one card for the current state with a `Next:` line, the table "Your uploads" with every upload and claim decision (newest first: date, what, result, details; stacked rows on a narrow screen) and "Upload another backup" (only when `GET /account/restore` says `room`; otherwise the page says why).

**Claim.** Step 2 of "I have no backup" is the claim of an old profile. The player types their old hunter name and presses Find (5 searches a day). A found profile shows its hunterscore and what a claim restores: items, trophies, lodges, and whether skills, statistics and achievements are there. A checkbox "Use my old name" is on only when that name is free. The card warns that the claim replaces the items, skills, achievements, trophies and lodges on this server (hunts, kills and photos stay) and that only one profile can be claimed; pressing Claim is the confirmation (`confirm=overwrite`). The page then shows "restored", or "an operator will check this claim" for a big profile or one already claimed by someone else. Once the account has a claim, the box shows its state (waiting, restored, rejected) and no form.

- **`/restore`** (signed in; the settings menu has "Restore your backup"): choose the zip the backup tool made, "Upload". The page sends it with `ServerRestoreService` (`src/Services/`) to the server in parts (`POST /account/restore/start`, each part, then `/finish`: [docs/server.md](server.md#upload-a-backup-zip)) with the player's cookie, and shows a headline for the result (`Restore.Result.<status>`: kept for review, already restored, user id in use, not a usable backup, try again later, file too large) with the server's own plain words under it and the technical report under "Details". The rules shown on the page are the server's: every zip is kept for an operator to check by hand and is never restored automatically; a backup is restored once, and uploading replaces the profile on the server (the hunts played there stay), whether or not the account has played. The upload goes browser to the website's server over its SignalR connection (`InputFile`, at most 1 GiB, in small messages, so no request body of the website carries it), then to the community server in parts of at most 90 MiB, each streamed as it comes and never held whole, so neither hop passes a proxy's 100 MB request limit; the website's client for it has a 10 minute timeout per request where the sign-in's has 5 s. A failed upload is sent again from the start. Below, "Delete my data" (a tick box first) calls `POST /account/delete` and loads the public site.
  Step 3's card and table come from `GET /account/restore`: the zips kept for the operator (`Restore.Waiting`; one from another tool says so, by the `format`), the server's own English words as the reason when an approve was refused, and one row per decision: restored (`Restore.Done.restored`: the user id and the account's name now, then `Restore.Done.nameBackup` or `Restore.Done.nameKept`), rejected by the operator (`Restore.Done.rejected`, the operator's reason) or could not be read (`Restore.Done.refused`, the server's reason, for example that the zip holds a program or only pictures). The same news reaches the game as a message in the notice thread ([docs/server.md](server.md#upload-a-backup-zip)).
- **`/your-data`** (public; "Privacy Policy" in the footer): what the server stores (Steam id, handle, the game data, each uploaded zip, kept and after it is restored, hashed tokens and cookies), what accounts do not hold (e-mail, real name, address, phone), how to delete, and the privacy facts: who runs the service and the contact (the project's Discord server, the project's e-mail address), why the data is kept and the legal basis (the service the player asks for, the operator's legitimate interest in keeping it working and safe; nothing is sold or used for advertising), problem reports (the launcher's report after a failed game start, which can hold the game's last crash dump, the one file that is not cleaned, sent automatically only if the player chose so, kept 30 days, seen by the operators, announced in their private Discord channel, removed by "Delete my data"; the game's own crash reports, kept 30 days per account without install paths and device identifier), and how long (the account until "Delete my data"; server and proxy logs, which can hold IP addresses and handles, at most 30 days, see [deploy.md](deploy.md#logs)). The page does not list who else sees the data or the player's rights. The footer's "Privacy Policy" opens this page; there is no separate policy. The wording is the page's keys `Data.*` in `src/Ui/Strings*.resx`.
- **`/terms`** (public; "Terms of use" in the footer, `TermsOfUse.razor`): the short terms of the free, unofficial fan project: provided as is, the service and accounts can change or stop, rules of conduct, accounts that break them can be suspended, the game keeps its own license. The first sign-in page `/signin/handle` says that continuing accepts the Terms of use and links Your data, both in a new tab. The page `/eula` (on the live site acceptance is not asked, so it shows only with the mock `?mock=eula`; once to a signed-in account that has not accepted yet) asks for a tick on the Terms of use and one on "I have read Your data", with a link to each; keys `Terms.*` and `Eula.*`. There are no placeholder legal dialogs.

The texts are translated in every language file of `src/Ui`. The server's messages under a result are English.

## The game check

The launcher's install check ([launcher.md](launcher.md#the-install-check); `ILauncherBridge.CheckInstallAsync`, one `InstallCheck` per check) shows in the launcher only, on the dashboard and on every Hunt now page (single player and multiplayer on the launch map, Find a multiplayer game, tutorials): `GameCheck`, one line under the menu bar, run when the page opens and again after a fix. All is well: "Game check: OK" in green. Otherwise the line is the text of the first blocking result (red), else of the first warning (amber), with its fix button and a "See all" link. The fix buttons, by `InstallCheck.Fix`: `choose-folder` opens the "Game Folder" window, `open-steam` opens Steam, `verify-files` opens the game's page in Steam, `setup` opens the player kit's setup window (`KitSetupModal`), `close-game` has no button. The checks run again when the window a fix opened is closed (at once for Steam).

"See all" opens `GameCheckModal`: every check with its name, its level (OK, Warning, Blocks the start) and, for a problem, its text and fix button. The text is the check's `Text` key with its `Args` as the `{0}`, `{1}` values, in the order the launcher lists them; a text that has no check any more shows without values.

A refused start (`ModalService.StartFailed`, `StartFailedDialog`) says the same: the text of the error key, with the values and the fix button of the blocking check that holds that key (a `Check.*` or `Kit.*` key; the launcher refuses a start for the game and the running game with the older `Launch.NoGame` and `Launch.AlreadyRunning`, whose fixes are the Game Folder button and none). The server's join refusals (`Join.*`) are only a text. The website's mock (`MockLauncherBridge`) has switchable states, as the `?mock=` values `check:old`, `check:updating`, `check:newer`, `check:files`, `check:path`, `check:steam`, `check:setup`, `check:windows`, `check:disk`, `check:running`, `check:many`, `steam:none` (Steam is not installed) and `steam:wait` (a start waits 20 seconds for Steam); `folder:none` is the missing game. A start in a state with a block fails with the launcher's key for that block; opening Steam clears the state, as fixing it in Steam would.

## Starting without Steam

The launcher starts the game with Steam when it can and without it otherwise ([launcher.md](launcher.md#what-is-real-and-what-is-mock)). The UI shows two things of it, whichever of the four places started the game (the launch map, the multiplayer list and its join map, the tutorials, the sign-up's first tutorial): `SteamStart`, drawn by `ModalHost`.

- While a start waits for Steam to sign in (`ILauncherBridge.WaitingForSteam`, at most 20 seconds): a panel floating in the middle of the window, "Starting Steam…", with the button "Start without Steam" (`StartWithoutSteam()`), which ends the wait at once. There is no backdrop: the page behind stays visible and clickable, and a click elsewhere leaves the wait alone (the start is still running). When a dialog is open the panel is inside it (the join map starts the game while it is open, and an open dialog makes the page behind it inert), else on the page.
- After a start that went on without Steam (`LastStartMode` is `nosteam`, set once the game has really started): the same kind of panel with one plain line, "Started without Steam: Steam achievements are off for this session." (`Launch.NoSteamNote`). No dialog to answer: it goes at the next click anywhere (`shell.js` `onceClick`) or after 10 seconds, and comes back at the next start without Steam.
- The game check shows a Steam that is not signed in as a warning, `Check.Steam.Fallback` ("Steam is not signed in: the game will start without Steam."), with the Open Steam button; a Steam that is not installed has its own text, `Check.Steam.NotInstalled`, and no button.

Keys: `Launch.StartingSteam`, `Launch.StartWithoutSteam`, `Launch.NoSteamNote`, `Check.Steam.Fallback`, `Check.Steam.NotInstalled`. `SteamStart` follows `ILauncherBridge.StartStateChanged`, which the bridge may raise from any thread.

Deploy: the container image and the VPS setup are in [deploy.md](deploy.md).

`settings.json` in `src/Web/` is read for the game name and the external links (`game_name`, `game_full`, `link_*`); the keys are listed in [launcher.md](launcher.md#settingsjson). The `GAME_NAME` and `GAME_FULL` environment variables win over its two names; the live site gets them from the repository secrets of the same names at every deploy ([deploy.md](deploy.md#deploys)). Without the file and the variables the texts say "the game" and the links are left out. The real file is git-ignored.

`IMAGES_DIR` names the folder of the operator's pictures, one file per slot, served at `/images/` ([images.md](images.md)). Unset, every picture is its labelled box. Their list is at `/images.json`, for the launcher, and the slots that have none at `/images-missing.json`.

The pages use native dialogs, popovers and CSS anchor positioning (dropdowns, menus, modals): use a current Chrome or Edge (the launcher's WebView2 runtime is one). Other browsers are not tested.

The JavaScript modules of `src/Ui/wwwroot` (`shell.js`) are imported by their plain path, `./_content/Resurgence.Ui/shell.js`. On the website, `<ImportMap />` in `src/Web/Components/App.razor` maps that path to the fingerprinted file (`shell.<hash>.js`, served `immutable`), whose URL changes with every build, so a browser never runs a `shell.js` from an older deploy. The plain URL is not enough: the app sends it with `no-cache`, but Cloudflare's Browser Cache TTL raises that to 4 hours. The icon sprite (`icons.svg`) is fingerprinted the same way: `Icon` links it through `@Assets[...]` (`icons.<hash>.svg`). The CI docker smoke test checks that `/feed` names both fingerprinted files. The launcher needs no map: its BlazorWebView serves every file with `no-store`.

The paw favicon (`favicon.ico`, `favicon.svg`, which turns light in a dark theme, `favicon-32.png` and `apple-touch-icon.png`) lives in `src/Web/wwwroot/`, and `App.razor` links it through `@Assets[...]`, so its URLs are fingerprinted and served `immutable`, while the plain paths such as `/favicon.ico` answer too. The launcher's icon is made from `favicon.svg`; when the paw changes, regenerate it ([launcher.md](launcher.md#icon)).

## Search engines

Every page's `<head>` (`src/Web/Components/App.razor`) has a meta description (`App.Description`) and the link preview tags `og:type`, `og:title` (`Landing.Heading`), `og:description` and `og:image` (the paw's `apple-touch-icon.png`, as an absolute URL built from the request's scheme and host). They are in the page's language and say `{game_full}`, so the game's name comes from `GAME_FULL` or `settings.json` and the repository never holds it; without either they say "the game". The landing page (`/`, `src/Ui/Pages/Feed.razor`) has `Landing.Heading` as its `<title>` and in a visually hidden `<h1>`: the hero's logo is the visible title, and the public bar's logo links to `/`. Store item and bundle pages are titled with their name, a profile tab with the profile's title and the tab. The CI docker smoke test checks the `og:image` URL and the `<h1>`.

Every public page (`Seo.Indexed`, below) also has one URL per language (`src/Web/Components/SeoLinks.razor`, rendered by the router for a page it found, and `src/Web/Seo.cs`): `<link rel="canonical">` is the page in the language it shows, and `<link rel="alternate" hreflang>` names it in all 19 languages plus `x-default`. A page's URL is the scheme, host and path (no trailing slash) with only the queries that change what it shows: `page` (above 1) and `lang` (left out for English, which is the bare URL and `x-default`). Any other query (`?ref=`, `?next=`) is the same page, and `/feed` is `/`. Search engines crawl without a language, so the bare URL they fetch is English and they find the others through `hreflang`. A page for signed-in players, an unknown route, a page that turns out not to exist (`Nav.NotFound`) and `/not-found` have none of these links.

`/sitemap.xml` lists the public pages only (`Seo.Sitemap`: `/`, download, help, your data and terms), English URLs only: no profile, no store item, no board. Every response of any other path (`Seo.Indexed`, which also counts `/feed` and the help's tabs as public) carries `X-Robots-Tag: noindex`, set by the security headers middleware of `src/Web/Program.cs`, so a page for signed-in players, a sign-in step or a file is never indexed even when a crawler is signed in or finds a link. The operator submits the sitemap in the search engines' consoles: `robots.txt` has no `Sitemap:` line, because that line needs the absolute host and the file is static.

`src/Web/wwwroot/robots.txt` (served at `/robots.txt`) turns away two SEO backlink crawlers, `MJ12bot` and `serpstatbot`: they sent most of the website's requests and brought no visitors, and every page they fetch is rendered on the server. It also keeps the Blazor hub (`/_blazor/`) and the pages that give a crawler only an empty shell, a sign-in prompt or a redirect out of search engines: sign-in (`/auth/`, the server's Steam sign-in, and the website's `/signin/` pages), sign-up, payment, per-session and launcher-only pages, and the routes for signed-in players or that go to the feed on the live site (competitions, community league, restore). It is a request, not access control: the CDN's bot rules handle crawlers that ignore it, and `noindex` above keeps the rest out. The CI docker smoke test checks that it is served.

## Security headers

A middleware, the first one in `src/Web/Program.cs`, adds these headers to every response (pages, static files, the 404 page, the Blazor endpoints):

| Header | Value |
|---|---|
| `Strict-Transport-Security` | `max-age=31536000` (one year, this host only: no `includeSubDomains`, no `preload`) |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Content-Security-Policy` | `frame-ancestors 'none'` |

HSTS is sent over http too (`dotnet run`, the CI smoke test): browsers ignore it there. The CSP only forbids framing (clickjacking); a wider policy would have to allow the inline `<ImportMap />` script and the offerwall iframe (`src/Ui/Modals/OfferwallModal.razor`). Blazor's own `frame-ancestors 'self'` header is turned off (`ContentSecurityFrameAncestorsPolicy = null` in `Program.cs`) so this is the only CSP. Responses that issue an antiforgery token also get `X-Frame-Options: SAMEORIGIN` from the antiforgery; browsers ignore it because the CSP is there. The CI docker smoke test checks all four on `/feed` and on a 404.

## Two views of one app

The website is signed-in or public:

- **Signed out**: the public top bar (`Already a hunter? Sign in`) and the menu bar, the news with a play button, the store and its items, leaderboards, competitions (not on the live site), help, download, and hunter profiles and score sheets. Pages that need an account (missions, wallet, bank, messages, settings, invite, welcome, community league, restore) go back to the news.
- **Signed in**: the same menu as the launcher without the launcher-only items. The pages that only the launcher has (`/dashboard`, `/servers`, `/launch-map/...`, `/tutorials` and the sign-up screens) go back to the news. With `SERVER_URL` the pages of mock account data go back to the news too, see [the live site](#sign-in).
- **Multiplayer** (the games list at `/servers`, the dashboard's Quick Join, the host form at `/launch-map/2` and the join map) is the launcher's: a game is played from the player's PC, so the website does not show these pages (the row above) and has no browser version of them. They are `src/Ui` pages over `IServersService`; with `SERVER_URL` (or `server_url` in the launcher) `ServerServersService` reads `GET /catalog/games` and hosts or joins with `POST /auth/launch` (`mp=host`, `mp=join`; the games, the form and the refusals are in [launcher.md](launcher.md#multiplayer)). The dev state `servers:none` (no games) is the mock's.

Four plain pages are meant for the browser the old launcher opened: `/auto-login`, `/email/verify` (also `/email/confirm`, `/email/change`), `/thank-you` and `/logout`. They have no menu.

An unknown address answers with HTTP 404 and the "Page not found" page.

## Development switches

Only when the app runs in the Development environment (the default with `dotnet run`):

| Switch | Effect |
|---|---|
| `?mode=launcher` or `?mode=web` | renders the launcher view or the website view; remembered in a cookie. Screens built for the launcher can be looked at in a normal browser this way |
| `?mock=<state>` | puts a mock service in a state (cookie too); `?mock=none` clears it |
| `?lang=<code>` | picks the language: any of the 19 codes of `Languages.All` (`en`, `fr`, `de`, `pt-BR`, ...); this one works in every environment |
| `?alert=<text>` | opens the alert dialog with that text |
| `?modal=settings` or `?modal=initial` | opens the game settings dialog, or the first-start variant |

States: all those of [launcher.md](launcher.md#development-switches) (patch panel, account, store, wallet, bank, friends, messages, missions, profile, `session:out` for the public site, `session:signup`, `eula`, `start:hold`, `browser:hold`, `poll:fast` ...), plus these, which exist only on the website: `competitions:many` (45 entrants on a competition's leaderboard, three pages), `servers:none` (no games), `loadouts` (three saved loadouts), `tents` (two tents on the map) and `membership` (the signed-in hunter has a membership).

## Languages

The 19 languages and the resx files (`src/Ui/Strings.resx` and one `Strings.<code>.resx` each) are the launcher's: see [launcher.md](launcher.md#languages). The website picks the language from the browser's `Accept-Language` header, highest quality first, matching by `Languages.Match` (region ignored: `de-AT` is German, bare `pt` is Portuguese (Brazil), `no` and `nn` are Norwegian bokmål), else English. `?lang=<code>` overrides it and is remembered in a cookie.

A test in `tests/Resurgence.Tests` checks that all 18 non-English files have the same keys and the same `{0}` placeholders as the English one, and that no key holds its English text in all 18 (a key copied, not translated; names such as `App.Name` are listed in the test). Native speakers are welcome to check any of them.

## Tests

The website and the pages of `src/Ui` are tested in `tests/Resurgence.Tests/WebTests`, without a browser:

- Component tests (bUnit, `UiContext`): a page is rendered with the service mocks and asserted on its markup. Anything behind the mocks' delay is awaited with `WaitForAssertion`.
- Website tests (`WebAppTests`, `WebApplicationFactory`): the real `src/Web` app runs in memory in the Development environment, with no `SERVER_URL` unless a test sets it. They check the security headers, the page language, the cookie policy, `/images.json` and the services chosen by `SERVER_URL`. They read `src/Web/settings.json` when it exists.

Run one class with `dotnet test --project tests/Resurgence.Tests -c Release --filter-class Resurgence.Tests.WebTests.WebAppTests`.
