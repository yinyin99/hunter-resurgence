# Website

`src/Web/` is the community website. It is a Blazor Web App with interactive server rendering: pages are rendered on the server and kept alive over a SignalR connection, so it needs JavaScript. The pages and the theme live in `src/Ui/`, the same library the [launcher](launcher.md) uses; the website only adds the host, the language switch and the development switches.

## State

The screens follow the original website screen for screen (same theme, places, navigation and English texts; French uses the original French). With `SERVER_URL` set (the live site) the sign-in, the store, the profiles, the hunterscore and minigame boards, the wallet, the missions, the friends, the messages, the restore page and "Delete my data" are the community server's ([Sign-in](#sign-in), [Restore and your data](#restore-and-your-data)), and the news is the project's own; the other pages are hidden. Without it every page is the **mock**'s: the services in `src/Services/Mocks/` return fixed, fictional data and their actions do nothing real. The pictures are not in the repo: each one is a labelled box unless the operator supplies its file ([images.md](images.md)). See [launcher.md](launcher.md) for the service layer in `src/Services/Contracts/`.

Without `SERVER_URL` (development, the CI smoke test) every service is the mock. Its session starts signed in as a fictional hunter (`Hunter01`); sign out in the top bar to see the public site. Its sign-in is the email, then a six-digit code (there is no password), and it accepts any address with an `@` and any six digits. The live site has no email sign-in.

## Sign-in

Without `SERVER_URL` (development, the CI smoke test) everything above holds: the mock session and the email sign-in panel.

With `SERVER_URL` set (for example `http://server:8080`, the community server's address on the internal network) the website uses the server's Steam sign-in, which both serve on the same domain behind one reverse proxy. The server's `web_host` setting must be this website's domain, and the proxy sends the server's own paths (`/auth/*`, `/account/*`, `/hunters/*`, `/catalog/*`, `/photos/*`, the minigame boards) to the server ([deploy.md](deploy.md#the-community-server)); the website's server itself calls them over `SERVER_URL`.

- **Sign in**: "Already a hunter? Sign in" in the public bar (`src/Ui/Shell/PublicBar.razor`) is a plain link to `/auth/steam/login?next=<current path>`, a full page load. The server sends the player to Steam, asks for a handle the first time, sets the session cookie `hr_session` (HttpOnly, 30 days) and returns to `next`.
- **The sign-in's pages** (`src/Ui/Pages/SignIn/`, layout `SignInLayout`: the logo and one card, none of the shell's bars; `robots.txt` keeps `/signin/` out of search engines): the server does the sign-in and, at each step, redirects the browser to a page of the website: `/signin/handle` (the first sign-in picks a name; with an archive "I played before" restores the old profile), `/signin/confirm` (an app asks to be signed in, one "Yes, sign in": the launcher or the backup tool on this PC, which show no code, or the old launcher's start page, which shows one), `/signin/done` and `/signin/problem?reason=<key>` (expired, link, app, steam, banned, form, confirmed; any other key reads as expired). The pages are translated (`SignInPage.*` in the 19 `Strings*.resx`) and carry the operator's Discord invite (`LINK_DISCORD`) after a sign-in, nothing without one. A step page reads its state from the server with `ISignInService` (`GET /auth/pending` with the browser's `hr_login` cookie, which `App.razor` hands to the circuit like the session cookie, and `X-Requested-With`; the mock shows the steps for `?mock=signin:restore|confirm|app|none`) and draws a plain HTML form that the browser posts to the server itself (`/auth/handle`, `/auth/confirm`) with the token the state carries: the server keeps the logic, the cookies and the CSRF check, and the website changes no state. Without a sign-in in progress (or one of another step) a page says it ran out of time.
- **Who is signed in**: `ServerSessionService` (`src/Services/`) asks the server `GET /auth/me` with the browser's cookie; 200 gives the handle and the hunterscore (the status bar's paw), anything else (401, no answer within 5 s, an error) means signed out and never reaches the page. The paths and the JSON are in `src/Services/Contracts/ServerSessionApi.cs`. Nothing is cached: every read asks again. The answer also carries the wallet: `ServerWalletService` makes its own `GET /auth/me` for the balances (the status bar's em$ and gm$; 0 when the server does not answer), and the status bar shows no ammo or fuel days, which the server does not know.
- **Sign out**: the sign-out button opens `/logout`, which only shows a "Sign Out" button (opening the address signs nobody out); the click calls `POST /auth/signout` with the cookie and `X-Requested-With: XMLHttpRequest`, then shows the public site. The server deletes the session; if it cannot be reached the website is signed out for that tab only.
- **The cookie reaches the server** because the website forwards it: `src/Web/Components/App.razor` reads `hr_session` and the request's `Host` from the page request and passes them to `Routes` as parameters (the page's component marker is protected by data protection, so the browser cannot read it), where they fill a per-circuit holder. Blazor's `HttpContext` is not reliable once the circuit runs, so nothing reads it later. The server picks its site by `Host`, so the website sends the host the browser used.
- **The hunterscore** is the server's ([docs/server.md](server.md#the-hunterscore)) in three places: the status bar, the profile header of every player (`ServerProfileService` asks `GET /hunters/<handle>`: handle, hunterscore, rank, membership and avatar; a handle the server does not know, or a failed answer, is the "Page not found" page with HTTP 404) and the hunterscore board (`ServerLeaderboardsService`: `GET /hunters?page=<n>` for the rows, `GET /auth/me` for "Your rank"; a failed answer is an empty board). These two are public and need no cookie; the website's server asks over `SERVER_URL`, the launcher through the proxy, which routes `/hunters/` to the server.
- **The statistics tab** of the profile page (`ServerProfileService.Tabs`, own and any other profile) is the lifetime statistics of the server ([docs/server.md](server.md#public-reads)): `TotalsAsync` asks `GET /hunters/<handle>/statistics` (public, no cookie) and shows the animals and the weapons, the distance and the hunt time; a failed answer is empty tables. A hunt played on the server is in it once it closes. On the live site the tab has the lifetime, history and personal bests pills: there is no last hunt pill (the first row of the history is that hunt), and collectables stay empty. **The history** (`HistoryAsync`: `GET /hunters/<handle>/hunts?page=<n>`, 40 a page) lists the server hunts, then the saved ones; a start opens the hunt page (`ExpeditionAsync`: `GET /hunters/<handle>/hunts/<id>`) with the weapons, the animals, the distance, the time and the kills of that hunt, and a kill opens its score sheet (`/profile/<handle>/score/<id>`, `SheetAsync`: `GET /hunters/<handle>/score/<kill>`), all public and without a cookie. The reserve is the catalogue's name and the lodge the name of the start the hunt opened at, as the launch map names it (the hunt page shows both in its header). The hunt page also lists what the hunt picked up and earned, each in a section of its own that is left out when empty (`HuntStats`, shared by the website and the launcher): the collectables (name, score, time), the achievements the hunt earned (title and description) and the shed antlers (species, single or double, score). A saved hunt shows the antlers and achievements its backup had, and no collectables (its backup holds per-type sums, not the pickups). A kill of a saved hunt has a link only when its backup zip held its score sheet page ([docs/restore.md](restore.md#pictures)): the sheet then shows the facts of the saved hunt and no worked rows (the game shows the saved page itself). A failed answer is an empty page or no page. **The personal bests** (`BestAsync`: `GET /hunters/<handle>/best`, public, no cookie) list the all-time best score of each species with its weapon, time, score and range, as plain text (no link to a score sheet) and without the season list, since the server has no seasons ([#222](https://github.com/yinyin99/hunter-resurgence/issues/222)); a player with none, or a failed answer, sees the "no expeditions" text.
- **The ranks tab** (`ServerProfileService.Tabs`, own and any other profile) is the server's ([docs/server.md](server.md#public-reads)): `RanksAsync` asks `GET /hunters/<handle>/ranks` (public, no cookie). The overview shows the hunterscore bar and the three category bars (animals, weapons, collectables) as the sum of the rows, each row counting to the cap (1000) at most; a category page lists its rows by name, each with its count (up to the cap) as the number and the fill of its bar. `MilestonesAsync` reads the same answer: a milestone row is one achievement definition of its kind (animals, weapons, exploration, daily missions) with its thresholds and the player's counter, the steps reached being the thresholds at most the counter. The live achievements tab has the overview and the animals, weapons, exploration and daily missions pages (a page is its milestones, each with the achievement's own picture, slot `ach-icon-<icon>`); there are no challenges (no server source). A failed answer is no bars and no rows.
- **The boards** of the live site are the server's three (`ServerLeaderboardsService.Kinds`): the hunterscore, and Lane Bandit and Bust Through (`GET /leaderboards/<lanebandit|bustthrough>?page=<n>`: the best scores, restored or played, [docs/server.md](server.md#the-hunterscore); no "Your rank" and no store link for the Lane Bandit item, whose id is the mock's). The server has no seasons, so the species score and range boards (titled by season), the hall of fame and the antler boards are not offered: their tabs are gone, and their addresses go to `/leaderboards/hunterscore`.
- **The live site** (`HostMode.Live`, true exactly when `SERVER_URL` is set): a signed-in player sees only their own data from the server, or nothing. These pages are not served (`LauncherGuard.MockOnly`: bank, the Steam callback, new message, invite friends, welcome, community league, and the competitions, whose only recorded ones ended weeks ago; the address goes back to the feed), and their links are gone: the menu's "get em$" and competitions items, the "Settings" heading opens "Restore your backup" (the menu's account item opens the settings page, which has the avatar only, [Avatars](#avatars)), a trophy's link to its competition (its name stays, as text), and in the status bar the message count (the messages and wallet links and the em$ and gm$ balances stay), and the "Send message" buttons of the friends lists. What the player owns is gone from the pages that stay: the bundle's "Own" and own-limit columns and its "you own the most" line, and "your rank" on every board but the hunterscore. The bank dialogs are hidden (the bank sells em$ for real money), and so is the taxidermy button (its offer is a kill of the mock's). **Messages** are the player's own and read only (`ServerMessagesService`, [docs/server.md](server.md#messages)): the messages page lists the server's notices and the conversations a backup restored, and opens a thread; there is no field to write one and no "only from friends" setting, and the website marks nothing read, so the status bar shows no count. **Friends** are the server's (`ServerFriendsService`, [docs/server.md](server.md#friends)): the status bar's friends button counts the requests and opens the list with the search (from 3 characters, the handles that contain the text), the accept and decline buttons and the remove button, and the profile of another hunter has the friend request button, disabled and marked sent once asked (and gone for a friend). The server gives requests and the list by handle (`GET /account/friends`: friends, requests and the requests the player sent, with who is online; `GET /account/friends/search?text=<text>`; `POST /account/friends/add` asks, or accepts the other's request, `POST /account/friends/remove` declines, cancels or removes, form `handle`, with the player's cookie and `X-Requested-With`); it keeps no time for a request, so they are sorted by handle, not oldest first. A profile is a player of the server or "Page not found" (HTTP 404), never a hunter of the mock pages. Its header is the server's: handle, membership title, hunterscore, rank, avatar ([Avatars](#avatars)) and the header picture the player chose (the slot `profile-bg-<name>`, the restored profile's `background` without its extension; no picture without one, where the mock shows its `profile-banner` box); the avatar sits between the polaroid's two pictures (`polaroid-back`, `polaroid-front`), and a missing front picture is not drawn. A tab with no server source would be hidden on its own: `ServerProfileService.Tabs` lists the tabs the page shows (`Profile.Tabs`; null on the mock, which shows them all), and the ticket that gives a tab its source adds its key there. An address of a hidden tab opens the first shown one; with none the page is the header only. Today all eight tabs (ranks, skills, statistics, trophies, dogs, friends, achievements and gallery) have a source, so none is hidden (the ranks and statistics tabs are described above; a row of the ranks tab shows its rank's own picture, the slot `rank-<id>` of the rank's game id): `GET /hunters/<handle>/skills` gives the species with spotting and tracking rings and the weapons by category with a shooting ring, each a level and the percent of its span; `GET /hunters/<handle>/trophies?page=<n>` gives 24 trophies a page (the competition trophies of the restored `Trophy/list`: the trophy's name, the day it was won, its competition's name and its cup picture, the slot `trophy-<image>` of the picture's file name; the hidden ones are left out, and the kills of the lodges and of the server's hunts are not listed), and a competition link is never shown; `GET /hunters/<handle>/dogs` gives every owned dog with its name, its level and the percent of the way to the next, its breed skills and its ribbons (the rest of the inventory is not public); `GET /hunters/<handle>/friends?page=<n>` gives 20 friends a page by handle with their hunterscore, and on the player's own tab each has a remove button; `GET /hunters/<handle>/achievements` gives the overview of the achievements tab (the progress of each category, the number unlocked and the last ten by earn time, with the day; the category pages come from the ranks reply's milestones, and there is no challenges pill); `GET /hunters/<handle>/gallery?page=<n>` gives 24 photos a page, newest first, each a picture the game uploaded (its small picture is the tab's thumbnail, the share window and the lightbox use the full one; the animal and its score are those of the kill the photo shows, a photo of no kill has neither; the caption links the kill's score sheet when the server has it, `kill` of the row), and on the player's own tab each photo has a delete button (`POST /account/gallery/delete`) and the whole gallery downloads as a zip (`GET /account/gallery/zip`), both with the session cookie; a failed answer is an empty tab. Without `SERVER_URL` (development, the launcher) nothing is hidden. On a profile's skills tab the species' pictures are `statistics-<define>` (the dog species and species 56 are not listed, as in the original) and the weapons' pictures, here and in the statistics tab, are `store-item-<id>` ([images.md](images.md)).
- **The wallet** (`ServerWalletService`) is the player's own history from the server ([docs/server.md](server.md#wallet-history)): `/wallet` opens the em$ history, with an em$ and a gm$ tab and no bank tab (`/bank` stays hidden; `/wallet/bank` opens the em$ history); the header's balances are the account's (`GET /auth/me`) and its totals spent `GET /account/wallet/spent`; the rows are `GET /account/wallet/ems` and `/gms` (50 a page, "Show more" asks the next), newest first: the restored history, then the purchases and rewards made on the server. A bought item shows by name, with its count when more than one; a reward has none. Without an answer the page is empty, never the mock's rows.
- **The missions** (`ServerMissionsService`, owner only: signed out, the address goes back to the feed) are the player's own from the server ([docs/server.md](server.md#missions)): `/missions` is the regular page, with the active and available lists, the packs with their progress and favourites, the filters and the three switches, from one `GET /account/missions`; its writes are `POST /account/missions/<call>` with the cookie, the game's own: activating one mission or all available ones (a mission whose dependency is open is refused, and the page says so as the game does), favouriting a pack and the switches (turning one automatic setting on turns the other off). A mission's reserve, species and weapon filters use the first name its filter lists name (none when the list is empty, and then no option). **The daily missions** (`/missions/daily`, the menu's missions item) are the same service's: one `GET /account/missions/daily` gives the seven days of the streak (difficulty and gm$ reward of each), today's mission with its objectives and the time left, and whether the streak is frozen; the frozen streak's "Activate" button is `POST /account/missions/daily/activate`. The server has no item to resume a broken streak, so the page offers none and the call fails. A server that does not answer, or holds no missions, is an empty page, never the mock's.
- **The store** (`ServerStoreService`, with `SERVER_URL`) is the community server's catalogue ([docs/server.md](server.md#the-store-catalogue)): the original's categories, items with their prices, the sales (the struck-through price) and the bundles, for everyone, signed in or not. The server's answer is kept for 5 minutes and shared by every visitor (`ServerCache`); a server that does not answer, or holds no catalogue, is an empty store ("No items in this category"), never the mock's. For a signed-in player the store list and the item page show what they own, read from `GET /account/inventory` ([docs/server.md](server.md#accounts)) once when a store page opens and again after a purchase (a search does not ask again): "You own: N" for a counted item (units summed over the copies), "Owned" for one copy of an item that is not counted, "You own: N" for several copies, and for a license "Expires: <date>" on the list and "You have a valid license until: <date>" on the item page, or "You have an unlimited license" (a license that has ended shows nothing; while the server's `all_licenses` is on, every license of the catalogue shows it, [docs/server.md](server.md#licenses)), and an item with an unlimited license has no buy button (`StoreItem.LimitReached`); the buy dialog says the same as the card; nothing for an item they do not own or when signed out (`OwnedLine`; item 0 like any other). **Buying** is the server's (`POST /account/buy` with the player's cookie, [docs/server.md](server.md#buying-from-the-website)): the buy buttons of the store list, the item and the bundle open the buy dialog, which offers an em$ button and a gm$ button with their prices (only the one an item has a price for; the gm$ price is the catalogue's, never discounted, [docs/server.md](server.md#buying-from-the-website)), and a player short of em$ or gm$ gets that button disabled (no bank to send them to) and a line says why ("Not enough em$: you have N, this costs M", the same for gm$). An item the store lists as not buyable keeps the disabled "not buyable" button. After a purchase the status bar shows the new balance when the buy dialog closes (it reads the balances whenever a dialog opens or closes, besides its 30 second refresh); the game gets the items with its next heartbeat or connect. The pictures: an item or bundle of the live site looks for `store-item-<id>` and `store-bundle-<id>`, never the mock's `item-<id>` and `bundle-<id>` ([docs/images.md](images.md)), so it is a labelled box until its picture is mapped.
- **Unlimited ammunition in the store**: while the server's `unlimited_ammo` is on, its catalogue marks every ammunition `unlimited` and not buyable ([docs/server.md](server.md#unlimited-ammunition)); the list and the item page show "Unlimited ammunition" (`Store.UnlimitedAmmo`, `OwnedLine`'s `Unlimited`) in place of what the player owns, and the button says "Not buyable".
- **A store item's page** (`ItemDetail`, the launcher's too) shows under the name what the list lacks, read from `GET /catalog/item/<id>` when the page opens ([docs/server.md](server.md#an-items-page)), asked without the cookie and not kept: "Capacity cost" (the catalogue's weight divided by 1000, as the store shows it) and "Contains: 10 cartridges" for an item that has units; two columns under the description: on the left what fits the item under its category's title (a weapon: sights and ammunition; an ammunition: the weapons that fire it), one per row with its picture (the `item-<id>` or `store-item-<id>` slot at 260×70), name and variant; on the right, for a weapon or an ammunition, the "Permitted for" table: one row per species, named in the player's language (`Term.species.<id>`) and sorted by that name, and one column per ammunition, headed by its picture (46×34) with its name and variant under it, with a green tick or a grey cross by the server's own rule for judging a kill. A server that does not answer leaves the item with its name, price and description only. The page is in the player's language except the item names, which are the catalogue's: a fit list's title is the store's category text (`Store.Cat.<key>`, by the `key` the route gives, the title staying when no text exists) and a unit word has a text of its own (`Store.Unit.<word>`, `{0}` the count: cartridges, shotshells, arrows, units, uses, days, month, months; a word with no text stays as the catalogue gives it); `Store.Contains` is the label. The languages whose nouns change with the number (Czech, Finnish, Polish, Romanian, Russian, Slovenian) write `{0} ×` and the noun, which needs no ending.
- **Seasonal events** (`ServerSeasonalEventsService`, signed in): the settings menu's "Seasonal events" opens a dialog with the box "Play seasonal events", on by default; it reads and stores the player's setting on the server (`GET` and `POST /account/events` with the cookie, [docs/server.md](server.md#seasonal-events)), the same setting as the launcher's. Without `SERVER_URL` the box is a mock kept per browser circuit. On the dashboard the same `EventPanel` as the launcher's shows the running event's community and personal missions and store items, while an event runs for a player who plays events (`GET /account/events/panel`, [launcher.md](launcher.md#seasonal-events)). The website draws no event picture: the launch map's badges are the launcher's ([launcher.md](launcher.md#seasonal-events)).
- **Inventory** (`Inventory.razor`, `ServerInventoryService`): the page exists but is turned off (`LauncherGuard.Disabled`: its address goes back to the feed, the status bar has no link); the store shows what the player owns instead (the store entry above).
- **The news** on the feed (`/` and `/feed`) is the same on the live site, the mock website and the launcher (`NewsPosts`, `Feed.razor`): the project's own posts, shown whole in the original post format (title, date, text and a link), newest first, with no post page and no archive. They are the backup tool (`News.Backup.*`, the link `link_backup`) and the project in development (`News.Dev.*`, the link `link_source`, the repository, from the `LINK_SOURCE` variable the deploy sets; without a link the text shows as plain text). The carousel has one slide for each post, rotating every 18 seconds, with a picture each (two of the operator's competition pictures, `NewsPost.Picture`, [docs/images.md](images.md)), and links to the post on the same page (`#news-backup`, `#news-dev`). A new post is an entry in `NewsPosts`, its three resx keys (`News.<Id>.Title`, `.Text`, `.Lead`) in every translation, and a picture (an existing slot key, `NewsPost.Picture`). The Discord widget (signed in or not) is Discord's own iframe (`discord.com/widget`, dark theme) of the server behind the `link_discord` invite (`DiscordNewsService`): the invite gives the server's id, and the server's public `widget.json` says whether its owner turned the widget on (Server Settings ▸ Widget ▸ Enable Server Widget); both replies are kept for 5 minutes and shared by every visitor (`ServerCache`). Without the link, with the widget off or when Discord does not answer there is none; the launcher shows the same frame for its own `link_discord`, the mock website has none.
- **The Discord invitation** (`link_discord`, the `LINK_DISCORD` variable winning over it; without it neither of these shows). The feed has a "Join the Discord" button above Discord's frame (`DiscordWidget`; it shows also when the frame does not), a link to the invite in a new tab. The first time an account is in the shell after a sign-in (on the website and in the launcher, with a username and not on the agreements page), a dialog says the community meets on Discord, with "Join the Discord" and "Later" (`DiscordInviteModal`, `ModalService.OfferDiscordAsync`, from `ShellLayout`). Once per account, not per browser: the server remembers it (`POST /account/discord`, `ServerDiscordInviteService`; [docs/server.md](server.md#accounts)); accounts that exist before it are invited once too. It never opens over another dialog: the server is not asked then, so the invitation comes at the next page load; one that finds a dialog opened while the server answers is dropped, as the server has stored it already. Not on the agreements page, nor before the agreements are accepted. A server that does not answer shows nothing. Without `SERVER_URL` the mock asks once per browser circuit.
- **The restore offer** (`RestoreOfferModal`, `ModalService.OfferRestoreAsync`, from `ShellLayout`): right after the Discord invitation is closed (at once when there is none, with or without `link_discord`), a dialog asks "Do you have a backup of your profile?" and says a backup is the backup zip of the backup tool or a save made with another community tool; "Restore my profile" opens `/restore`, "Later" closes it. Once per account, like the invitation: the server remembers it (`POST /account/restore-offer`, `ServerRestoreOfferService`; [docs/server.md](server.md#accounts)) and never offers it to an account that has restored a backup zip or has an upload waiting; an archive claim does not stop it (the player may have more in a zip). Never over another dialog (the server is not asked then, so it comes at the next page load); not on the agreements page. Accounts that exist before it are offered it once. Without `SERVER_URL` the mock asks once per browser circuit.
- **Problem reports** (launcher only; what the zip holds and how it is built: [launcher.md](launcher.md#report-a-problem)). The windows keep their text short. The first time an account is in the launcher's shell, after the Discord invitation and the restore offer are closed, a dialog asks "Send problem reports?" while `ILauncherBridge.ReportConsent` is `unset` (`ReportConsentModal`, `ModalService.OfferReportConsentAsync`, from `ShellLayout`; never over another dialog; Escape does nothing; the keyboard focus starts on "Send automatically", so Enter accepts it): one line (if the game fails to start, the launcher can send its logs) and two buttons, no link. "Send automatically" stores `auto`, "Ask me each time" stores `ask`; "Send automatically" is the primary button, "Ask me each time" the grey one. The settings menu's "Report a problem" (launcher only) opens `ReportModal`: one line (it sends the game's logs to the community server, kept 30 days), the files and the ones left out behind a "Show files" toggle, and "Send" (primary, then the reference with "give it on Discord", or the text of the `ReportSent` error key), "Save" (to Downloads; a failed save says so) and "Close", with the box "Send automatically after a failed start" (`auto` or `ask`). The report is built with the trigger `manual`. After the game exits, the "Done hunting for now?" window (`GameStartedModal`) looks at `LastRun?.Trigger`: with `auto` it builds and sends a report by itself and shows "Problem report sent: <reference>" (or the error); otherwise it shows "Something went wrong? Report a problem", which replaces the window with `ReportModal` for that trigger. The window opens once per start, so there is at most one automatic send per start. The mock bridge implements all this with fakes and starts as `unset`; the website never asks.
- **Help** on the live site is its support tab (the site's own texts and the operator's links). The download button is `HunterResurgence-win-Setup.exe` of the latest release of `link_source` (the repository, from `LINK_SOURCE`) and the help box links its `docs/guide.md` and, when set, `link_discord`; without `link_source` there is no button and no guide line.
- **Not applying**: the e-mail, handle and agreements methods of the session do not apply (the agreements count as accepted). The live site's limits are listed in [deploy.md](deploy.md#known-limits).
- **Hunt now** (the menu's button and the news page's "Play for free" button, on the website; in the launcher the menu keeps its dashboard drop-down) is a link to `/download` with `data-launch="hunter-resurgence://open"`, the link the launcher's Setup registers ([launcher.md](launcher.md#files-on-the-pc)). `shell.js` (`watchLaunch`, started by `ShellLayout` outside the launcher) handles the click on Windows (the user agent has `Windows NT`): it opens the link in a hidden frame (Firefox shows an error page when a top-level address has no application) and the page stays where it is. A page can't ask whether the link is registered, so if the window neither lost focus nor was hidden within 2 s (the browser's "Open Hunter Resurgence?" prompt or the launcher's window takes it), the launcher is not installed and the page goes to `/download`; a player who leaves the prompt open longer is sent to `/download` behind it, and so is one who ticked "always open" when the launcher's window needs more than 2 s to appear. A click on another page in that time cancels the jump. Without JavaScript, on another system (a phone, a Mac, Linux) or with a modified click (new tab) the link is a plain `/download`. The download page says "Already installed? Start Hunter Resurgence from the Start menu" for the player the detection misses (`Download.Installed`).

## Restore and your data

With `SERVER_URL` set, two pages here are real: the restore page and the data page. They need the community server, and without it the restore page says it is not available here. The rest of the live site is the server's too ([the live site](#sign-in)), or hidden.

The restore page is three steps (a stepper on top; a player with a result, a waiting zip or a claim lands on step 3, everyone else on step 1; the page is `src/Ui/Pages/RestoreBackup.razor`): **1. What do you have?** "I have a backup zip" or "I have no backup" (the second only when the server keeps old public profiles, `GET /account/archive` says `enabled`, and the account has not claimed yet); **2.** the upload (three checks, "All the rules", the file picker, Upload with a progress bar of the bytes sent per part, `IRestoreService.UploadAsync`'s `IProgress<long>`) or the claim; **3. What happens next**: one card for the current state with a `Next:` line, the table "Your uploads" with every upload and claim decision (newest first: date, what, result, details; stacked rows on a narrow screen) and "Upload another backup" (only when `GET /account/restore` says `room`; otherwise the page says why).

**Claim.** Step 2 of "I have no backup" is the claim of an old profile. The player types their old hunter name and presses Find (5 searches a day). A found profile shows its hunterscore and what a claim restores: items, trophies, lodges, and whether skills, statistics and achievements are there. A checkbox "Use my old name" is on only when that name is free. The card warns that the claim replaces the items, skills, achievements, trophies and lodges on this server (hunts, kills and photos stay) and that only one profile can be claimed; pressing Claim is the confirmation (`confirm=overwrite`). The page then shows "restored", or "an operator will check this claim" for a big profile or one already claimed by someone else. Once the account has a claim, the box shows its state (waiting, restored, rejected) and no form.

- **`/restore`** (signed in; the settings menu has "Restore your backup"): choose the zip the backup tool made, "Upload". The page sends it with `ServerRestoreService` (`src/Services/`) to the server in parts (`POST /account/restore/start`, each part, then `/finish`: [docs/server.md](server.md#upload-a-backup-zip)) with the player's cookie, and shows a headline for the result (`Restore.Result.<status>`: kept for review, already restored, user id in use, not a usable backup, try again later, file too large) with the server's own plain words under it and the technical report under "Details". The rules shown on the page are the server's: every zip is kept for an operator to check by hand and is never restored automatically; a backup is restored once, and uploading replaces the profile on the server (the hunts played there stay), whether or not the account has played. The upload goes browser to the website's server over its SignalR connection (`InputFile`, at most 1 GiB, in small messages, so no request body of the website carries it), then to the community server in parts of at most 90 MiB, each streamed as it comes and never held whole, so neither hop passes a proxy's 100 MB request limit; the website's client for it has a 10 minute timeout per request where the sign-in's has 5 s. A failed upload is sent again from the start. Below, "Delete my data" (a tick box first) calls `POST /account/delete` and loads the public site.
  Step 3's card and table come from `GET /account/restore`: the zips kept for the operator (`Restore.Waiting`; one from another tool says so, by the `format`), the server's own English words as the reason when an approve was refused, and one row per decision: restored (`Restore.Done.restored`: the user id and the account's name now, then `Restore.Done.nameBackup` or `Restore.Done.nameKept`), rejected by the operator (`Restore.Done.rejected`, the operator's reason) or could not be read (`Restore.Done.refused`, the server's reason, for example that the zip holds a program or only pictures). The same news reaches the game as a message in the notice thread ([docs/server.md](server.md#upload-a-backup-zip)).
- **`/your-data`** (public; "Privacy Policy" in the footer): what the server stores (Steam id, handle, the game data, each uploaded zip, kept and after it is restored, hashed tokens and cookies), what accounts do not hold (e-mail, real name, address, phone), how to delete, and the privacy facts: who runs the service and the contact (the project's Discord server, the project's e-mail address), why the data is kept and the legal basis (the service the player asks for, the operator's legitimate interest in keeping it working and safe; nothing is sold or used for advertising), problem reports (the launcher's report after a failed game start, sent automatically only if the player chose so, kept 30 days, seen by the operators, announced in their private Discord channel, removed by "Delete my data"; the game's own crash reports, kept 30 days per account without install paths and device identifier), and how long (the account until "Delete my data"; server and proxy logs, which can hold IP addresses and handles, at most 30 days, see [deploy.md](deploy.md#logs)). The page does not list who else sees the data or the player's rights. The footer's "Privacy Policy" opens this page; there is no separate policy. The wording is the page's keys `Data.*` in `src/Ui/Strings*.resx`.
- **`/terms`** (public; "Terms of use" in the footer, `TermsOfUse.razor`): the short terms of the free, unofficial fan project: provided as is, the service and accounts can change or stop, rules of conduct, accounts that break them can be suspended, the game keeps its own license. The first sign-in page `/signin/handle` says that continuing accepts the Terms of use and links Your data, both in a new tab. The page `/eula` (on the live site acceptance is not asked, so it shows only with the mock `?mock=eula`; once to a signed-in account that has not accepted yet) asks for a tick on the Terms of use and one on "I have read Your data", with a link to each; keys `Terms.*` and `Eula.*`. There are no placeholder legal dialogs.

The texts are translated in every language file of `src/Ui`. The server's messages under a result are English.

## Avatars

With `SERVER_URL`, every player is drawn with their own avatar ([docs/server.md](server.md#avatars)): the status bar (the session's `avatar`, `GET /auth/me`; the bar takes it again whenever the shell gives it another session, so the launcher's bar, shown before the shell has read the session at a start, has it too), the profile header, the friends menu and the friends tab, the boards, the messages and the multiplayer lists. Each list reply carries the players' avatars (`avatar` in the rows of `GET /hunters`, `GET /leaderboards/<kind>`, `GET /hunters/<handle>/friends`, `GET /account/friends` and `/search`, `GET /account/messages`), so a page of players is one request. A page draws what `Avatars.Slot` makes of the server's address: the slot `avatar-<id>` for an avatar of the game's list ([images.md](images.md)), the link of the picture imported from a backup as an image (`AssetSlot` draws an `https://` name as it is), and `avatar-default` for no avatar. The mock pages keep the mock's `avatar-<NN>` slots.

The settings page (`/settings`, signed in) has the avatar as its one working item, the one account setting the community server has (`ServerAccountService`, on the live site: `GET /account/avatars` lists the game's avatars and, while the player has one, the imported picture; a choice is `POST /account/avatar`, and the status bar follows at once). Account email, Language & time zone, Purchase History, Multiplayer bans, Steam settings and Profile settings could be built later and show disabled (greyed, not links, `aria-disabled`, the title "Coming later" and the same text for a screen reader); Facebook settings is gone. The game shows the new avatar at its next start. The sign-up page's carousel is the same list (`ServerSignupService`). The launcher with a `server_url` uses the same services.

The Settings menu (`SettingsMenu`) offers only what works, and shows disabled what could be built later (Game Management: the lodges and bait sites the server keeps). On the website: Account settings (the avatar), Game Management (disabled), Restore your backup, Language and Seasonal events. The launcher adds Game settings, Use Steam's Play button, Screenshots, Logfiles, Report a problem, Game Folder (a window: see below), Clear launcher cache and Clear game cache (and the player kit's two items with an https `server_url`: [launcher.md](launcher.md)); none of them is on the website. A folder or cache entry the launcher refuses (the folder is missing, the game is running) says why in a dialog (`Settings.NoFolder`, `Settings.CacheGameRunning`, `Settings.CacheFailed`).

The "Game Folder" window (`GameFolderModal`, launcher only) shows the game install the launcher uses (`ILauncherBridge.GameInstall`) and how it was found: "Found in your Steam library" (`steam-library`), "From Steam's launch option" (`steam-option`) or "Chosen by you" (`manual`). ## Build and run

```
dotnet build hunter-resurgence.slnx -c Release
dotnet run --project src/Web
```

The development profile listens on `http://localhost:5080`.

Deploy: the container image and the VPS setup are in [deploy.md](deploy.md).

`settings.json` in `src/Web/` is read for the game name and the external links (`game_name`, `game_full`, `link_*`); the keys are listed in [launcher.md](launcher.md#settingsjson). The `GAME_NAME` and `GAME_FULL` environment variables win over its two names; the live site gets them from the repository secrets of the same names at every deploy ([deploy.md](deploy.md#deploys)). Without the file and the variables the texts say "the game" and the links are left out. The real file is git-ignored.

`IMAGES_DIR` names the folder of the operator's pictures, one file per slot, served at `/images/` ([images.md](images.md)). Unset, every picture is its labelled box. Their list is at `/images.json`, for the launcher, and the slots drawn without one at `/images-missing.json`.

The pages use native dialogs, popovers and CSS anchor positioning (dropdowns, menus, modals): use a current Chrome or Edge (the launcher's WebView2 runtime is one). Other browsers are not tested.

The JavaScript modules of `src/Ui/wwwroot` (`shell.js`) are imported by their plain path, `./_content/Resurgence.Ui/shell.js`. On the website, `<ImportMap />` in `src/Web/Components/App.razor` maps that path to the fingerprinted file (`shell.<hash>.js`, served `immutable`), whose URL changes with every build, so a browser never runs a `shell.js` from an older deploy. The plain URL is not enough: the app sends it with `no-cache`, but Cloudflare's Browser Cache TTL raises that to 4 hours. The icon sprite (`icons.svg`) is fingerprinted the same way: `Icon` links it through `@Assets[...]` (`icons.<hash>.svg`). The CI docker smoke test checks that `/feed` names both fingerprinted files. The launcher needs no map: its BlazorWebView serves every file with `no-store`.

The paw favicon (`favicon.ico`, `favicon.svg`, which turns light in a dark theme, `favicon-32.png` and `apple-touch-icon.png`) lives in `src/Web/wwwroot/`, and `App.razor` links it through `@Assets[...]`, so its URLs are fingerprinted and served `immutable`, while the plain paths such as `/favicon.ico` answer too. The launcher's icon is made from `favicon.svg`; when the paw changes, regenerate it ([launcher.md](launcher.md#icon)).

## Search engines

Every page's `<head>` (`src/Web/Components/App.razor`) has a meta description (`App.Description`) and the link preview tags `og:type`, `og:title` (`Landing.Heading`), `og:description` and `og:image` (the paw's `apple-touch-icon.png`, as an absolute URL built from the request's scheme and host). They are in the page's language and say `{game_full}`, so the game's name comes from `GAME_FULL` or `settings.json` and the repository never holds it; without either they say "the game". The landing page (`/`, `src/Ui/Pages/Feed.razor`) has `Landing.Heading` as its `<title>` and in a visually hidden `<h1>`: the hero's logo is the visible title, and the public bar's logo links to `/`. Store item and bundle pages are titled with their name, a profile tab with the profile's title and the tab. The CI docker smoke test checks the `og:image` URL and the `<h1>`.

Every page also has one URL per language (`src/Web/Components/SeoLinks.razor`, rendered by the router for a page it found, and `src/Web/Seo.cs`): `<link rel="canonical">` is the page in the language it shows, and `<link rel="alternate" hreflang>` names it in all 19 languages plus `x-default`. A page's URL is the scheme, host and path (no trailing slash) with only the queries that change what it shows: `page` (above 1) and `lang` (left out for English, which is the bare URL and `x-default`). Any other query (`?ref=`, `?next=`) is the same page, and `/feed` is `/`. Search engines crawl without a language, so the bare URL they fetch is English and they find the others through `hreflang`. An unknown route, a page that turns out not to exist (a profile's `Nav.NotFound`) and `/not-found` have none of these links.

`/sitemap.xml` lists the open pages (`/`, store, bundles, the three leaderboards of the live site, download, help, your data), every store category (but `all`, which is `/store`), item and bundle, and the profile of every hunter on the hunterscore board, English URLs only. It is built at each request from the store and the board the website shows (the server's on the live site, asked with the website's host like a page). The operator submits it in the search engines' consoles: `robots.txt` has no `Sitemap:` line, because that line needs the absolute host and the file is static.

`src/Web/wwwroot/robots.txt` (served at `/robots.txt`) turns away two SEO backlink crawlers, `MJ12bot` and `serpstatbot`: they sent most of the website's requests and brought no visitors, and every page they fetch is rendered on the server. It also keeps the Blazor hub (`/_blazor/`) and the pages that give a crawler only an empty shell or a redirect out of search engines: sign-in (`/auth/`, the server's Steam sign-in, and the website's `/signin/` pages), sign-up, payment, per-session and launcher-only pages, and the routes that go to the feed for a signed-out visitor or on the live site (competitions, community league, restore). The news, profiles, leaderboards, store, help and download stay open. It is a request, not access control: the CDN's bot rules handle crawlers that ignore it. The CI docker smoke test checks that it is served.

## Security headers

A middleware, the first one in `src/Web/Program.cs`, adds these headers to every response (pages, static files, the 404 page, the Blazor endpoints):

| Header | Value |
|---|---|
| `Strict-Transport-Security` | `max-age=31536000` (one year, this host only: no `includeSubDomains`, no `preload`) |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Content-Security-Policy` | `frame-ancestors 'none'` |

HSTS is sent over http too (`dotnet run`, the CI smoke test): browsers ignore it there. The CSP only forbids framing (clickjacking); a wider policy would have to allow the inline `<ImportMap />` script and the offerwall iframe (`src/Ui/Modals/OfferwallModal.razor`). Blazor's own `frame-ancestors 'self'` header is turned off (`ContentSecurityFrameAncestorsPolicy = null` in `Program.cs`) so this is the only CSP. Responses that issue an antiforgery token also get `X-Frame-Options: SAMEORIGIN` from the antiforgery; browsers ignore it because the CSP is there. The CI docker smoke test checks all four on `/feed` and on a 404.

## Development switches

Only when the app runs in the Development environment (the default with `dotnet run`):

| Switch | Effect |
|---|---|
| `?mode=launcher` or `?mode=web` | renders the launcher view or the website view; remembered in a cookie. Screens built for the launcher can be looked at in a normal browser this way |
| `?mock=<state>` | puts a mock service in a state (cookie too); `?mock=none` clears it |
| `?lang=<code>` | picks the language: any of the 19 codes of `Languages.All` (`en`, `fr`, `de`, `pt-BR`, ...); this one works in every environment |
| `?alert=<text>` | opens the alert dialog with that text |
| `?modal=settings` or `?modal=initial` | opens the game settings dialog, or the first-start variant |

States: all those of [launcher.md](launcher.md#development-switches) (patch panel, account, store, wallet, bank, friends, messages, missions, profile, `session:out` for the public site, `session:signup`, `eula`, `start:hold`, `browser:hold`, `poll:fast` ...), plus these, which exist only on the website: `competitions:many` (45 entrants on a competition's leaderboard, three pages), `servers:none` (no games), `loadouts` (three saved loadouts), `tents` (two tents on the map) and `membership` (the signed-in hunter has a membership).

## Languages

The 19 languages and the resx files (`src/Ui/Strings.resx` and one `Strings.<code>.resx` each) are the launcher's: see [launcher.md](launcher.md#languages). The website picks the language from the browser's `Accept-Language` header, highest quality first, matching by `Languages.Match` (region ignored: `de-AT` is German, bare `pt` is Portuguese (Brazil), `no` and `nn` are Norwegian bokmål), else English. `?lang=<code>` overrides it and is remembered in a cookie.

A test in `tests/Resurgence.Tests` checks that all 18 non-English files have the same keys and the same `{0}` placeholders as the English one, and that no key holds its English text in all 18 (a key copied, not translated; names such as `App.Name` are listed in the test). Native speakers are welcome to check any of them.

## Tests

The website and the pages of `src/Ui` are tested in `tests/Resurgence.Tests/WebTests`, without a browser:

- Component tests (bUnit, `UiContext`): a page is rendered with the service mocks and asserted on its markup. Anything behind the mocks' delay is awaited with `WaitForAssertion`.
- Website tests (`WebAppTests`, `WebApplicationFactory`): the real `src/Web` app runs in memory in the Development environment, with no `SERVER_URL` unless a test sets it. They check the security headers, the page language, the cookie policy, `/images.json` and the services chosen by `SERVER_URL`. They read `src/Web/settings.json` when it exists.

Run one class with `dotnet test --project tests/Resurgence.Tests -c Release --filter-class Resurgence.Tests.WebTests.WebAppTests`.
