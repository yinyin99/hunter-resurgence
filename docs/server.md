# Server

`server/Server` is the game server: the local server a player runs on their own PC, and the code of the community server. Tests: `server/Server.Tests`. One SQLite database per server ([ADR 0001](adr/0001-sqlite-for-profiles.md)).

At this stage it answers the hunt itself (connect, heartbeat, kills, harvest, score, purchases, expeditions, multiplayer sessions, chat notices, photo upload) from a player state, and answers everything else from what the operator supplies: the game's install archives, recorded replies and a mirror folder. It needs no recordings to start: the player state is built from the operator's own install and the facts file ([Starting data](#starting-data)). The current game build (one web host, signed tokens) is described in [The current build](#the-current-build).

## Run it

```
dotnet run --project server/Server -c Release -- [--settings <file>] serve | admin ... | import backup|pictures ... | review ... | claim ... | coverage | backup <folder> [keep]
```

`serve` is the default. The settings file is `--settings <file>`, else the environment variable `SERVER_SETTINGS`, else `settings.json` in the current folder. It is never committed (`.gitignore`); start from `server/Server/settings.example.json`. Relative paths are relative to the settings file.

`serve` needs no change to the PC: it does not read or require the Windows hosts file. How the client is pointed at the server is not part of the server.

`admin rescore [--account <id or handle>] [--kill <id>] [--apply]` (below), `admin item <item_id> [count]`, `admin em|gm <amount>` and `admin spawn <reserve> <animal> <males> [females] [x z radius]` change the player in `data_dir` from the command line (add `--account <user id or handle>` to `admin item|em|gm` for another account, e.g. `docker compose exec server dotnet server.dll admin item <item_id> <count> --account <handle>`; the admin API's account routes take the same as the `account` query parameter; without it the local account); `admin missions-rollback [--apply] [--account <user id or handle>]` reopens mission objectives the earlier rules finished without their conditions ([Missions](#missions)); `coverage` replays every request of the recordings through the server and lists what it cannot answer, naming hosts by their settings key and masking ids and tokens in paths, then reports how many mission objectives the server understands ([Missions](#missions)). `coverage --no-recordings` replays them against the server as it starts without recordings and without the mirror (player state from the install and the facts file, on a temporary database): what it lists as unanswered still needs a recording.

A reserve takes at most 20 new animal kinds from `admin spawn`; further entries of that reserve are not applied.

`backup <folder> [keep]` copies every `*.db` of `data_dir` to `<folder>/<name>-<yyyymmdd>.db` with SQLite's `VACUUM INTO` (consistent while the server runs) and keeps the newest `keep` (default 7) copies of each; the community server's daily backup is this command ([deploy.md](deploy.md#backups)).

## How a request is answered

1. A request for `telemetry_host` or `crash_host` gets 204. With player state, the crash host's fatal and error reports are kept per account ([Crash reports](#crash-reports)) and everything else it sends is dropped; the telemetry host's requests (and the crash host's, without player state) are kept in `telemetry.jsonl`.
2. The player state answers what it owns: `heartbeat`, `heartbeatScenario`, `disconnect`, `connect`, the photo upload and photo files on the game host; `Inventory/move_multiple2`, `Inventory/buy`, `Launch/start`, `Launch/start_mp`, `Launch/join`, `Network/list` ([Multiplayer](#multiplayer)), `session/start_tutorial`, `User/jwt`, `Oauth/token`, `Chat/conversations`, `Chat/conversation`, `Skill/list`, `Statistics/total`, `Achievement/stats` (the last three for a restored account's own user id, see [Import a backup zip](#import-a-backup-zip); on a community server `Achievement/stats` for any account's user id, see [Public reads](#public-reads); `Statistics/total` for any account's user id, see [Public reads](#public-reads)), the lists that wrap a base reply (`Splash/list_active`, `Public_user/expedition`, `Expedition/list`, `Me/poll`, `Me/me`: the recorded reply on a local server, the empty shape on a community server; `Public_user/expedition` and `Expedition/list` for any account's user id, see [Public reads](#public-reads)) and, on a community server, `Inventory/list`, `Inventory/dict`, `Trophy/list`, `Gallery/list`, `Gallery/delete` ([Gallery](#gallery)), `Wallet/transactions`, `Wallet/silver_transactions` and `Wallet/spent` ([Wallet history](#wallet-history)), `Mission/missions` and the page's mission writes ([Missions](#missions)) and the friends calls ([Friends](#friends)) on the API host; the harvest pages, the trophies, the lodges and the edits of lodges and trophies on the API v2 host ([Lodges](#lodges-and-trophy-visibility)); the sign-in and start page on the website and signup hosts, and the old launcher's own calls on the game host ([Sign-in and tokens](#sign-in-and-tokens)); the kill details page on the website host. `Inventory/buy` accepts amounts of 1 to 1000; any other amount gets `success: false` and costs nothing.
3. Everything else, in this order: an archive file in the URL's own folder, the recorded reply (a JSONP callback is swapped; on a community server only for a global endpoint, [below](#recordings-on-a-community-server)), the mirror, an archive file found by its name, an empty 200 for a request that was only recorded as unchanged, else a miss: `null` under `/v1/`, `{"err": 0}` on the game host, 404 on the API v2 host. Every miss carries `Cache-Control: no-store`, so the client's disk cache never keeps one and a later fix reaches players without a cache clear. A miss is written to the miss log, keys only.

The state answer wins; a handler that has nothing to say returns control to step 3. On a local server a reply is never made up where a recorded one exists.

## Recordings on a community server

A recording holds one player's replies, so with `offline_mode` false step 3 replays a recorded reply only for a **global** endpoint, one that is the same for everyone. Every other request on the API, API v2, game and website hosts is **per player**: the state answers it from the database, or it gets the empty reply of its shape, and a path the table does not list gets the miss reply (default deny). The table is `ReplayScope.Rules`; a test checks that no per-player rule ever returns recorded bytes. The asset hosts (static, map, photo, avatar, news, signup) and the mirror are not affected. With `offline_mode` true nothing changes: the recordings are the operator's own.

## The current build

The current client build sends all its traffic to `game_web_host`, with lower-case paths and JSON bodies. `NewBuild.Rewrite` (before routing) turns a request for that host into the one the handlers know, so every handler, recording and rule below is the old one:

| Request on `game_web_host` | Becomes |
|---|---|

**The lodge editor's addresses.** The editor builds its server addresses from the domain the game hands it (`api.`, `apiv2.` and `static.` names the player's PC does not send to this server), so its requests never arrived. Whatever answers `/dist/main.js`, the server replaces the three address builders with this host's own origin (`/v1` for the two API ones, the origin for the pictures), an exact text replacement on the served bytes (each text must be found exactly once, else the script is served unchanged and one warning is logged). The script and its frame page are served with `Cache-Control: no-cache`, and the page asks for the script as `main.js?t=urls2`. The page's reads of the lodge lists carry no token while the routes need the player's, so the frame page wraps `fetch` before the script runs, adding the game's own token to each request to this origin that has none. The editor asks for its pictures under `/static/img/`, which the game answers from its own archives alone (a request for a picture they lack never reaches this server), so the same replacement turns the script's lodge and item picture addresses into `/content/` ones (the gun racks' icons, which the script takes from a fixed host, too; its other `/static/img/` addresses stay): `/content/lodge/<animals, skulls, weapons, slots, styles, layouts or lodges>/<name>` is read from the archive (a file of that exact path), else from the static host's folder of the mirror, else, for a layout only (its name is in no other folder), from the archive's one file of that name.

**The lodge editor's game functions.** The editor calls the game's own functions (`window.hunter`: the language, the player's and the lodge's ids, `isStaff`, the inventory, label texts) as if each answered at once, but in the current build each answers with a promise, so the editor failed on its first label and stayed empty. The frame page (`/static/app/<version>/webgui/index.html`, whatever answers it) therefore no longer names the script in its own tag. When the language call answers with a promise, the page first waits for the answers the editor reads at once (`getServer`, `getActiveLodgeId`, `getHostPlayerGuid`, `getLocalPlayerGuid`, `isStaff`, `isSinglePlayer`, `getInventory`, `getLocale`) and for the locale script of that language (`/static/app/<version>/locale/<language>.js`, found from the page's own address), replaces `window.hunter` by an object that returns those answers, reads the label texts from the locale script (the key itself when it is not there, as the game does) and passes every other call on to the game, returning its promise (`editLodge`, `loadLodge`, `resumeGame` and the token calls, which the editor wraps in a promise itself); only then (or after 8 seconds, whatever has not answered by then) does it add the script, as `/dist/main.js?t=urls2`; a call that fails is not kept and is passed on like the others. The replacement is a proxy of the game's object, so every member stays reachable. The game's page asks the frame to go to the editor's route (`setURL`) as soon as the frame has loaded, which can be before the script is added, so the frame page defines `setURL` at once as a stand-in that keeps the route; when the script has loaded, its own `setURL` is called with it. The editor's own style zooms its container to 0.9 (`zoom`), which in this build puts each tooltip (a fixed element placed from the icon's position) on top of its own icon, so the tooltip closes at once; the frame page therefore adds a style that sets that zoom back to 1 on the three containers that have it (the editor's and the two menus'), under the names they have in the mirror's script and in the install's. The style also gives the page the dark background the other in-game pages have instead of plain black (`#050505` under a dark gradient, on the body; min-height 100% on the html and body). The editor's page layout draws its own full-window container in plain black on top of the body, so the style also clears that container's background (under its two names, like the zoom), and the body's shows around the panel. When the language call answers at once, the script is added as before. The token the page adds to the requests that carry none is asked for at each request, since it is a promise too; a failing token call only leaves the request as it was. The inventory is read once, when the page loads. Not on the game's object, and not made up here: `getSelectedPlatformId`, `getMountedTrophiesDelta`, `getUnmountedTrophiesDelta`, `getWeaponPlatformTypeID`, `selectTrophyMount` and `selectWeaponMount` (the trophy and weapon menus' own routes, not the editor) and `getLoggedInUserID` and `confirmBuy` (only when the page sits in the website).

**The in-game pages fit the window.** Two pages of the in-game browser were fixed boxes: the missions page (940 px wide, its list 800 px high with its own scrollbar, and an empty rest of the window under it) and the lodge editor (a panel 762 px wide, 962 px for one layout, whose map overflowed the panel's right edge, and a frame as high as the whole body, so its lower end was cut off under the tab bar). Both now follow the window, with no fixed size in the added styles. Whatever answers `/client` (when its `<head>` is found exactly once, else it is served as it is and one warning is logged), the server adds a style to the head: for the lodge editor's and the missions pages (the body's id the page sets, with a selector as specific as the page's own, so no other page is touched) the body is a column of the tab bar and `#main`, which takes the height that is left; on the missions page the box takes the window's width up to 75rem and all that height, and its list scrolls inside the box, so nothing is left empty under it. The filters' labels, half the width of their row in the page's own style, would have the Search field beside its label in the wider box, so each is shown above its control (the checkbox's stays as it is). The page is served with `Cache-Control: no-cache`. The editor's frame page (above) adds to its style: the layout's container keeps a margin of 2% of the window's smaller side; the panel takes the window's width up to 80rem and at most its height (a very small window scrolls it); the editor's container takes the height of its content; the left column floats and the right one takes the width that is left; the list's and the style picture's heights follow the window (`--l` and `--h`, set by the script below); the style picture is no larger than its column. The map is a picture with the slots placed on it in pixels, so it cannot be resized by a style alone: a second script in the frame page sets `zoom` on the map's container (the picture's parent) so it fits the width of the right column and the height that is left under it (no more than 1.6 times and no less than 0.3), at load, on resize, whenever the editor draws something and whenever the panel or the column changes size. The tooltips and the drag picture, which are `position: fixed` inside that container, get the inverse zoom, so they stay where the icon's measured position puts them. The selectors are the names of both scripts the server may send (the mirror's and the install's), as for the zoom above. The picture shown under the mouse while a trophy or weapon is dragged (a `position: fixed` element) is placed by the script at the mouse's position divided by 0.9, the zoom of the editor's own style that the frame page cancels; left as it is, it showed 11% further right and down than the mouse (the drop was not affected: it reads the mouse and the targets' rectangles). Whatever answers `/dist/main.js`, the server drops that division from the four places that have it (`offset.x / 0.9` and `offset.y / 0.9`), so the picture is at the mouse. A script without those texts is served as it is. The panel is shared by the other in-game pages (lodge selection, trophy and weapon menus, bait sites), whose own boxes keep their sizes, so the window-sized panel rules apply only to a panel with the class `fit`, which the second script sets on the panel that holds the editor's container; the other pages are unchanged.

**The in-game page's round timer.** The inventory page's Teams tab expects the round timer as a number, but the game answers a record `{time, running}`; for the host the page then recursed until it failed and the tab never opened. Whatever answers `/static/app/<version>/client.js` (recording, archive or mirror), the server replaces the page's two reads of the timer with one that takes a plain number or the record's `time`. The change is an exact text replacement on the served bytes (a page copy is never kept in the repository); if either expected text is not found exactly once that rewrite is skipped and one warning is logged. The script is served with `Cache-Control: no-cache`, and the page `/client` asks for it as `client.js?t=timer3` (the `?t=` token of the page's script tag is replaced), so a copy the game cached earlier is not used. Nothing of the page is rewritten for ammunition: its copying of a lodge stack is the one [Unlimited ammunition](#unlimited-ammunition) answers.

**Recordings of the current build** are found too: `NewBuild.Alias` adds, for every recorded request to `game_web_host` that the rewrite would move, the key of the moved request (the original stays).

**The old build** is no longer served by the server's own start page and connect reply: the launch URL, `config.domains`, `network` and the photo links are the current build's. Its other handlers keep their paths.

**Tokens.** The launch URL is `<scheme>://<game_web_host>/<session>/lang/en_US/access_token/<JWT>/refresh_token/<JWT>`. Both JWTs are HS256-signed with a key the server makes in a file beside the database (`state.db.jwtkey`) and carry `sub`, `user_id` (the account), `iss`, `scp`, `typ` (`access`/`refresh`), `iat`, `exp`, `jti`. Each is also stored in `tokens` like every other token, so a ban or a delete ends it, and every endpoint that takes a token takes them. The client does not check the signature; the server does when a refresh token comes back. An expired token is never sent: the game crashes on one.

**Sign-in on two hosts.** On our website (`web_host`) it is as above. In the launcher (`game_web_host`, through the player's forwarder) the page asks `POST /auth/link` for a code; the reply's `url` points the player's own browser to `https://<web_host>/auth/steam/login?link=<code>`, because only our domain has a certificate the browser trusts. The browser signs in and confirms there, and the launcher, polling `GET /auth/link/<code>` on the game host, receives the session cookie for that host (the launcher app and the backup tool do not use this: they sign in by [the loopback sign-in](#the-loopback-sign-in)). A poll that is still pending is not logged to the console (about one a second); the poll that completes and any error are.

**Settings the current build needs**: `web_host`, `game_web_host` and `crash_host`. The player's kit redirects `game_web_host` and `crash_host` only; `web_host` is ours and is never redirected.

## Starting data

`serve` builds the player state from three sources and needs none of the recordings. For each input the first source that has it wins (a recording never loses to the install, and the install never loses to the facts file), except where noted:

| Input | 1. Recording | 2. Install (`install_dir`) | 3. Facts file |
|---|---|---|---|
| Connect reply (the game data, and the local account's start) | the newest recorded `connect` | `game/json_connect_results.json`, with the sample account replaced (below) | - |
| Application catalogue (`species`, `items`, `reserves`, `locations`) | the recorded `Application/application` | `species.json` and `item.json` of the archives | reserves, lodge positions and the enum tables (`types`, `groups`, `categories`, `client_types`) |
| `populations` and `species_ammo` of a reserve | the newest connect after a `Launch/start` of that reserve | - | `reserves[].populations` and `species`; the ammo of a species is its entry of the connect's `ethical`, also over a recorded connect (a recorded one may hold a seasonal event's ammo); a werewolf's and a wendigo's entry is the facts file's `species_rules` when the connect lists none |
| Kill page labels and texture names | the recorded locale and web scripts | - | `labels`, `textures` |
| Item definitions of update 10 | the recorded connect's | `game/json_inventory.json`, then the catalogue above, then the install's item definitions | - |
| Discounts, the player's skill list | recorded only (without them: no discounts, fresh skills) | - | - |
| The avatar list (`Avatar/getAvatars`) | recorded only: a restore picks the profile's avatar from it ([docs/restore.md](restore.md#storing-the-model)); without it every restored account has the default avatar, unreported, and the website offers no avatar to choose ([Avatars](#avatars)) | - | `store_avatars`: the avatars the store sells, added after the recorded ones |
| Animal ids, score families | - | - | `animals`, `families` (always) |

With recordings that cover every input, the replies are the ones the recordings gave, except that the connect reply has `ingame_event` null unless a seasonal event runs for the player ([Seasonal events](#seasonal-events)), and `species_ammo` from the `ethical` list (the event's ammo on the event's reserves). Every connect reply also sets each `boost` entry's `own` per account: true when the account owns the entry's item (in any slot, placed or stacked) or the item has a `hunterscoreGiveLevel` and the account's hunterscore is at least that level (a purchase or a reached level unlocks it at the next connect), else false. Without a recorded connect, `connect` is the install's sample made neutral: the account, `account_info`, `network`, `user_stats` and `boost` of the sample's test player are replaced (handle `hunter`, user id 1, no e-mail, Steam id, address or counters; `config.domains` names the settings' hosts), `spawn` and `competitions` are empty and everything that is game data (species, items text, locations, store, ethical ammo, achievements, ...) stays. `serve` says `player state: off` only when there is neither a recorded connect nor a connect sample in the install.

**The welcome message.** Every `connect` queues one `update 3` toast for the first heartbeat (`State.TOAST_TEXT`, shown once however many times the game connects): "Hunter Resurgence community server" and "Progress is saved on the community server", two short lines that fit the in-game toast.

**The starting profile of a new account** is neutral and the same for everyone, recordings or not: the items of `start.items` of the facts file, one each in the first free slot of its type above the backpack and the pockets, or in the backpack when those are taken (a full stack for items with a stack size), the items of `start.stored` in the inventory (slot 0, never equipped), the wallet of `start.wallet` (1,000 em$ and 15,000 gm$) and every skill at level 1 (no weapon skill rows until a first hit), and an `account` object made from the install's sample (no avatar, name or other field of the operator's recorded account). Today that is the free start of the original game: a 12 GA single-shot shotgun and a .243 bolt-action rifle, a box each of .243 and of 12 GA birdshot, buckshot and slug shells, binoculars, the blue basic Arctic set (jacket, pants, boots, hat, gloves, scarf), a T-shirt, basic pants and basic boots, and a second T-shirt in the backpack (the inventory page fills an empty body, legs or feet slot with the slot's default clothing, looked up among the account's own items, and fails without it); and, stored since kit version 2, a 4x32mm rifle scope, a deer bleat call, a roe deer caller, a compact digital camera and a water bottle, and the items of the original's free Steam extra equipment: scent eliminator, camping supplies, first aid kit, wind indicator, face paint, moose scent, hog scent spray and whitetail deer urine spray; and, stored since kit version 3 for the Halloween event's creatures, the Maisto 12 GA sawed-off shotgun "Wolfsbane" and a box of Silver 12 GA slug shells (the ammunition `species_rules` allows for the werewolf and the wendigo). Change the facts file to change it; a restored backup keeps what it brings and gets each start item it lacks, the way the next paragraph describes. Only the local account of a local server starts from a recorded connect. A community server (`offline_mode` false) with a recorded connect and no connect sample in the install does not start.

**The start kit of an older account.** `start.version` of the facts file (1 when absent) is the kit's version, and `accounts.start_kit` the version an account has (0: it existed before schema 22). At each server start, every account with a lower version gets each start item it does not own, once and with no action from the player, and then has the current version: in the item's slot unless that is taken, else in the backpack, the way a restore adds the start items its zip lacks (`PlayerRows.AddMissingStart` is the one function of both). An item the account owns, in any slot, is never added again. A banned account is skipped until the first start after the ban is lifted. A new account has the current version from the start: it is seeded with the kit. Raise the version when items are added to the kit.

**The free ammunition.** `start.free_ammo` of the facts file lists the ammunition every player gets for free (`items`: the .243 ammunition and the three 12 GA shells) and `boxes`, how many full boxes (3). Every launch tops each of them up in the launch's transaction, before the connect, to that many full boxes (`Launch/start`, `Launch/start_mp`, `Launch/join`, `session/start_single_player`, and `POST /auth/launch` when it opens a hunt), a box being the item's stack size in the catalogue (so 30 .243 rounds, 90 birdshot, 30 buckshot, 30 slugs): the stacks the player has used are filled first, then new full stacks are added. A larger stock, bought in the store, is never lowered. The refilled stacks are in the connect that follows, like any change of the inventory.

**Unlimited ammunition.** With `unlimited_ammo` on (the default) the same launches also show the game only the oldest of the lodge's stacks of one ammunition (the others are kept, hidden), fill every other ammunition the player owns to a full box, and top the free ammunition up to one box instead of `boxes` (the lodge keeps one stack of each, which the page copies, and it copies a stack only when it is the only one in the lodge), [Unlimited ammunition](#unlimited-ammunition).

**The `infos` of the connect reply** are the definitions of the account's own items, one per distinct `item_id`, in order of first appearance, as the game's server sends them. A list longer than `items` stops the game right after `connect`, so the recorded connect's `infos` are only a source of definitions, never sent whole.

A definition not in the samples is built from the catalogue; an ammo's is completed with the `extra.ammo` ballistics of the install's item definitions, which the game needs to get past `connect` for an account that owns such an ammo. An item the catalogue does not list (a restored inventory may keep one the store no longer sells) has its definition built from the install's item definitions the same way; the store still shows only the catalogue's items. An owned item without any definition is left out of `infos`, and the game closes after `connect`.

**The `items_locale` of the connect reply** lists the name of every item. The game looks an item's name up there when it creates one that stands in the world (a placed tent), and it closes on an item the list lacks, as soon as a reserve with such an item placed loads. The sample's list stops at the last item before the events, so the server adds, with the catalogue's `define`, `name` and `variationname` (as `variationName`), every item of the catalogue and of the install's definitions that the list does not have (the event tents among them); the entries the list has stay as they are.

Still answered only from recordings (without them: a miss, `null` under `/v1/`): the launcher and website pages and their assets, the sign-up host, the avatar and photo hosts, news, `Launch/start` (its tokens), `User/jwt`, the lists that wrap a recorded base reply (`Me/poll`, `Expedition/list`, `Public_user/expedition`, `Splash/list_active`) and the profile, statistics, mission, challenge, leaderboard and friend pages. `coverage --no-recordings` prints the exact list.

## Accounts

Every player is in `state.db`. `accounts` holds the game's user id, the Steam id (optional, unique), the handle (unique, case does not matter), the creation time, the time of the one-shot claim, a banned flag, whether the player plays seasonal events, whether the Discord invite was shown to the player, whether the restore offer was, whether the account has its start kit and the connect reply's `account` object; `tokens` maps a token to an account and keeps only its SHA-256 hash. No e-mail, real name or address is stored. `seasons` (schema 29) holds the leaderboard seasons, shared by all players ([Leaderboards and seasons](#leaderboards-and-seasons)). Every per-player table has an `account_id`. The ids a restored backup brings (item guids, kill ids) are unique per account, so two accounts can both own item 100 or kill 1; the ids the server hands out (expeditions, photos) are unique in the whole database and always looked up together with the account. A new account starts with the connect template's inventory, wallet and skills (`State.CreateAccount`; [Starting data](#starting-data)). A database from before accounts is refused: delete it.

A request's account comes from its token. The tokens it carries are tried in this order, the first that resolves wins: the `X-Hun-Session` header (game host), `Authorization: Bearer` (API v2 host), `oauth_access_token` in the form or the query (API host). A token that is unknown, expired or of a banned account does not resolve. When none does, the request is the local account's if `offline_mode` is true, else it is refused: `{"errorCode": 5, "message": "token expired"}` with status 200 on the API host, status 401 on the game host (`{"err": 1}`) and on the API v2 host. A CORS preflight carries no token and is answered by the replay. Photo links name the account (`/photos/<account id>/<file>`) and need no token; the kill details page finds the account by the handle in its URL (on a local server any handle is the local account). The `admin` commands and the admin API act on the local account.

The database is in WAL mode with `synchronous=NORMAL` and a 5 s busy timeout, connections are pooled, every transaction starts with `BEGIN IMMEDIATE`, and the schema and its migrations run once at startup under `PRAGMA user_version`. A database call is scoped to one account: the SQL names it as `$a`, and a statement that touches a per-player table without it throws, so a forgotten filter fails in the tests and never reads another player's rows.

## Scoring and paying a harvest

A harvest (heartbeat event 3) is scored from the kill's spawn (event 7), its trophy measurement (event 22: the latest one after that spawn, since individual ids are reused across hunts and a female deer sends none, so a doe never takes the measurements of an earlier buck) and its hits (event 1). The next heartbeat carries update 6 with the score (`score_text` "Score: <score>", or "No score"), the kill's `css` and its kill id, and the kill's gm$ comes with update 15 (`CSS Reward`): `round(css)`, paid when it is above 0.

- **Disqualified** (`score_text` "Disqualified ", `score` -1, `trophy_shot` 0, no gm$, the usual notice) only when a hit used an ammunition that is not in the species' permitted list (the connect's `ethical`, by species id; the non-typical deer use their species' list) and not one of the ammunitions `species_rules` lists (the event's three silver ones), which every species permits. A species with an empty list, the dogs, has no rule.
- **The score** is one formula per family of the facts file's `families`, from the measurements below. The pheasant, the ducks, the geese and the ptarmigans get score type "A" when the last hit's animal state was flying and "G" otherwise; a tusked kill gets "T" when the tusks outweigh the weight and "W" otherwise.
- **The css** is `round(css_multiplier x 100 x (score - min_score) / (max_score - min_score), 1)` with the species' row of the facts file's `variants` (the operator's `variants_file` rows win); there is no clamp. A species with no family has no score, and one with no row has a score and no gm$ (none today): the dogs 22, 32 and 48, the sasquatch 31 and the t-rex 56.

| Family | Species | Score from | A female |
|---|---|---|---|
| `weight_lb` | coyote 4, red fox 14, arctic fox 23, werewolf 50, wendigo 58 | the weight in pounds | scores |
| `weight_mg` | the rabbits and hares 17, 20, 25, the ducks, geese and ptarmigans 15, 16, 27, 28, 29, 33, 34, 35, 47, 51 | the weight in grams (event 7 `feature`, in milligrams) | scores |
| `weight_kg`, `weight_g` | red kangaroo 21; roebit 53 and wood grouse 57 | the weight in kilograms; the weight in grams | scores |
| `skull` | bears 9, 13, 30, 37, wolf 36, bobcat 43, lynx 49, puma 52 | skull width plus length in inches (event 7 `feature`) | scores |
| `tusks` | feral hog 5, wild boar 10 | the weight in pounds, plus the tusk circumferences, plus 50 times the tusk lengths | a sow has no tusks: her weight |
| `turkey` | turkey 2 | the weight in pounds, plus 10 times the spurs, plus 2 times the beard (inches) | the weight (event 22 is all zeros) |
| `pheasant` | pheasant 7 | the tail plus the spurs in inches (event 22 `tail`, `left_spur`, `right_spur`) | the tail |
| `bc_deer` | whitetail 0, mule deer 1, blacktail 6, sitka 26, and the non-typical 100, 101, 106 | B&C typical or non-typical total | no antlers: no score |
| `elk` | Roosevelt 3, Rocky Mountain 38 | the typical total plus the crown points of both antlers (event 22 `crown_points` lengths) | no score |
| `moose`, `cic_roe`, `cic_red`, `cic_fallow`, `tines` | moose 8; roe 11, red 12, fallow 55; rusa 44, sambar 45, axis 54 | the family's total from the antlers | no antlers: no score |
| `caribou`, `bovid`, `sheep`, `cic_horn` | reindeer 18; bison 24, water buffalo 42, banteng 46; bighorn 39, Dall 41; alpine ibex 19, feral goat 40 | the family's total from the horns | scores when the animal carries horns (event 22 has a main-beam point) |

A kill whose family needs a measurement the heartbeat lacks (a skull with no `feature`, a deer without its event 22 or without a main-beam point) has no score.

## Seasonal events

The game build learns of an event from the connect reply's `ingame_event`: `{name, define, reserves}`, or `null` for none. It reads it once per start of the game, so an event never changes a hunt that is running. `reserves` are the game's own reserve numbers (the lodge id / 100, the launch map's reserve id minus 1); an empty list is every reserve.

**The operator's switch** is the `event` of settings.json: `{"name": "halloween_2026", "define": "HALLOWEEN_2026", "reserves": [0, 1, 2, 8, 9], "start": "2026-10-22T00:00:00Z", "end": "2026-11-10T18:00:00Z"}`. `name` (lower case letters, digits and `_`) and `define` (upper case) are the build's own names of the event, `start` and `end` a date and time with an offset (`Z` is UTC), `end` after `start`. The server checks it when it starts and refuses a wrong one. From `start` to `end` (exclusive) the connect reply carries the object; outside it, or with no `event`, `ingame_event` is `null` as it always was. A new or changed `event` needs a restart; the window opens and closes by itself.

**What the event adds** to a player's connect reply, on the reserves of `reserves` for which the facts file has an entry (`events.<name>.reserves.<game reserve number>`), while it runs:

- its `populations`: the event creatures, each on a density map the game ships, with `active_start` and `active_end` the event's window;
- its `ammo` as the `species_ammo` of every species of the reserve (the game uses that list only for a hint; the permitted ammo, `ethical`, is not touched).

A reserve of the event without an entry gets only `ingame_event`, and so does every reserve outside the event's `reserves`. The shipped `halloween_2026` has an entry for each of its five reserves. What the game does by itself when it reads the event is the same on all five, and the server sends nothing for it: the clock is frozen at night (1.25 h; 4.7 h on reserve 8), the weather is harsher (a default severity of 1.25, and Whiterime Ridge has its own, stronger weather block), the lodges are decorated, the ambient sounds change, and the event's own animal files give the species of the reserve their event coats and behaviour. The creatures are the server's:

| Game reserve (launch map) | Event creatures the server adds | Why this reserve |
|---|---|---|
| 0 (1, Whitehart Island) | a werewolf (index 50) and a feral hog (51) | the game ships a werewolf and a feral hog density map for it |
| 1 (2, Logger's Point) | a werewolf (150) | the game ships a werewolf density map for it; its feral hog is the normal one |
| 2 (3, Settler Creeks) | a werewolf (250) | the same |
| 8 (9, Bushrangers Run) | a werewolf (850) | the same |
| 9 (10, Whiterime Ridge) | a werewolf (908) and a wendigo (909), both on the snowshoe hare's map, and a feral hog (914) | the game ships no werewolf map for it, so both monsters use the snowshoe hare's, as the event's own rows do; the sizes are the event's |

A creature is only ever put on a density map the game ships for that reserve (a missing map fails the hunt): the werewolf's maps are the game's reserves 0, 1, 2, 8 and 10, the feral hog's 0, 1, 2, 6, 8, 9 and 11. Reserve 9's rows are the event's own; the other rows are sized like them. All five entries carry the three silver ammunitions, the ones reserve 9 carries, as the `species_ammo` of every species the reserve lists. The event has nothing else for any of them: no seasonal collectable has a `count_per_area` above 0 in its connect replies, and `ingame_store` is the same. A connect recorded during an event may carry its creatures; the server removes the rows the facts file lists for any event before it adds the running one's, so a player who does not play events never gets them.

**Scoring and paying an event creature** is the same as for any species ([Scoring and paying a harvest](#scoring-and-paying-a-harvest)). A werewolf or a wendigo scores by its weight in pounds (the family `weight_lb`, like the coyote) with `min_score` 190, `max_score` 390 and `css_multiplier` 1 (the facts file's `variants`), and a kill with a hit of any ammunition outside the species' permitted ammunition is disqualified. The permitted ammunition of both is the three silver ones (the connect's `ethical`, which is also what the game is sent). The facts file's `species_rules` give that list when the recorded connect lists no ammunition for them; what the recording itself holds wins. The silver ammunition is permitted on every species, not only on these two.

**The player's setting**, "Play seasonal events", is the account's `seasonal_events` column (schema 17), on by default. Off, that player's connect has `ingame_event: null` and none of the content above, and so has a tutorial's. `GET /account/events` and `POST /account/events` (the account routes below) read and set it; the launcher's Settings menu, launch map and tutorials page call them ([launcher.md](launcher.md#seasonal-events)). The same `GET` tells the launcher which event runs, so it can show the event's picture of a reserve ([images.md](images.md)).

**The event's missions** are in the facts file, `events.<name>`: `title` (the panel's heading), `missions` (the catalogue's ids of the event's personal missions), `items` (the event's store item ids) and `community` (`[{id, title, target, gm, em}]`). A personal mission is an ordinary mission: the player activates it and the mission engine ([Missions](#missions)) counts it. The shipped `halloween_2026` lists the mission 1201 ("Progressive Pursuits", 30 objectives on the event's creatures) and as store items the three Wolfsbane weapons (960, 967, 1143) and the three silver ammunitions (962, 963, 1142). A personal mission or store item the server's catalogue lacks is left out of the panel. Its `community` is empty: the numbers of its community missions are not known, so it has none until the file lists them.

**Community missions** are shared objectives of the event. `title` is read like a mission objective's (`Harvest ...`, `Spot ...`, `Locate ... tracks`, `Arrive ...`: [Missions](#missions)), `target` is how many the original asked of all its players, and the server asks `ceil(target / event_community_divisor)` (default 20, [settings.json](#run-it)), because the community is far smaller. While the event runs, each hunt event of a player who plays events that meets a mission counts 1 for that player in the table `community_progress` (schema 19: event, mission id, account, count, paid), until the sum over all players reaches the divided target; after that nothing counts. A player who opted out counts nothing and sees no panel. When the sum is reached, every player with a count is paid the mission's `gm` and `em` once through `AddCurrency` ("gm$ community reward", wallet history), at their own next heartbeat (the reply's update 15 carries the new balance, a notice follows): one heartbeat changes only its own player's wallet, and `paid` makes it once. A contributor who does not send a heartbeat before the operator switches the event off is not paid.

**The event panel** is `GET /account/events/panel` (the account routes below): for a player who plays seasonal events while an event runs, `{name, title, start, end, community, contributors, missions, items}`, otherwise `{"event": null}` (401 when signed out). `start` and `end` are unix seconds; `community` is `[{id, title, progress, target, gm, em}]` with the divided `target` and `progress` at most that; `contributors` the 10 players (not banned) with the most counts, `[{handle, count}]`; `missions` the player's personal missions, `[{id, title, state, objectives: [{title, done}], reward}]` with `state` `active`, `available`, `completed` or `locked`; `items` `[{id, name}]`. The launcher and the website show it on the dashboard ([launcher.md](launcher.md#seasonal-events)). The game's own screens show no panel: the game asks nothing of an event beyond the connect reply's `ingame_event`, and `Me/poll` and `Application/application` keep `campaign_stylesheet`, `community_campaign_stylesheet` and `active_campaign` false.

## Dog level rewards

A dog's level rewards are paid from its heartbeat event 23 for an owned dog item, which comes every 60 s and carries the dog's cumulative `experience`. Each connect `dog_skills` row whose `xp` the stored experience (missing: 0) is below and the event's is at or above adds the `SILVER` amounts of its `rewards` unlocks to the `gm` wallet, and the heartbeat reply carries one update 15 with the new balance. The stored experience only grows (an event whose `experience` is not a number leaves it as it is) (`max` of both), so a repeated or lower value pays nothing, and a dog restored or bought with a high experience pays only for levels crossed afterwards. The ribbon trophy and the skills are not paid: the game and the website show them from the experience.

## Missions

On a community server `Mission/missions` and the calls the missions page sends answer from the catalogue's `missions[]` and `mission_groups[]` (the recorded application reply: without a recording there are no missions, and every call keeps the empty reply of [the table above](#recordings-on-a-community-server)) and from the account's rows (schema 13): `missions` has a row for every active (state 2) or completed (3) mission with the ids of its finished objectives in the order they were finished, `mission_prefs` has the account's three switches and favourite groups. A row also remembers (schema 30) `since`, the last event before the mission was activated here (null for a row of an earlier schema), `seen`, the events after which its harvests are checked, `earlier`, the objectives finished before `seen`, and `kept`, the objectives a restore brought (`*` for a mission completed before the restore). A local server replays its recordings and tracks nothing. Every call needs the player's own token.

| Call (form `oauth_access_token` and) | Answer |
|---|---|
| `POST /v1/Mission/missions` | `{active, completed, available, states, auto_mission_activate, activate_only_favourite, hide_completed_favourite, favourites}`. `available` is derived: every dependency completed, not active, not completed. `states` has an entry for every id listed and for no other: `{state: 1}`, `{state: 2, objectives: [finished ids]}`, `{state: 3}` |
| `POST /v1/Mission/activate`, `mission_id` | `true` once the mission is active; `false` for a mission that is not available (unknown, a dependency open, already started) |
| `POST /v1/Mission/activate_all_available` | `true`: every available mission becomes active |
| `POST /v1/Mission/update_automatic_activation` (`auto_mission_activate`), `update_activate_only_favourite` (`activate_only_favourite`), `update_hide_completed_favourite` (`hide_completed_favourite`), `true` or `false` | `true`; the switch is stored |
| `POST /v1/Mission/update_favourite`, `group_id`, `is_favourite` | `true`; the group is added to or removed from the favourites. `false` for a group id that is no number |

**The website.** The missions page reads the same rows through `GET /account/missions` and writes through `POST /account/missions/<call>`, the six calls above ([Upload a backup zip](#upload-a-backup-zip)): the session cookie names the account, and a write is the very handler of the game's call, so the two surfaces always show one state. The page's titles, texts, rewards and filters come from the definitions, so it needs the same recording.

**Progress.** The game keeps no mission state and a definition has no condition field: the English title of an objective is turned into a rule when the server starts (`State.LoadMissions`). A leading `Then`, `Finally`, `First` or `After` makes the objective ordered (it counts only when every objective before it is finished). The first word gives the kind: `Harvest` (heartbeat event 3), `Spot` (event 11), `Locate`, `ID`, `Identify` or `Find` with a clue word (`tracks`, `droppings`, `call`, `blood`, ... event 12), `Arrive`, `Visit` or `Walk` (event 101 with `direction` `enter`) and `Start` (a hunt starts at the lodge, `Launch/start`). The species named in the title (the catalogue's longest species name found in it; a variant counts as its species) and the gender (`male`, `buck`, `bull`, `stag`, `rooster`, `tom`, `ram`; `female`, `doe`, `cow`, `hen`, `ewe`) must match the animal's event 7 (event 3's `extended_species` for a harvest). `N tracks` needs N events 12 of one animal in the hunt. A place matches when its words (the event's `location_name` or the lodge's name or define, without its leading reserve words and trailing number, down to two words) are in the title. Each event finishes the first unfinished objective it meets of every active mission that was activated before the event. A mission with `singleExpedition` forgets its finished objectives when a hunt starts. A clue, an arrival and a start are read by these words only (the kind of clue, `singleplayer`, time limits and a count other than clues of one animal are not checked); an objective whose first word is none of the above never finishes. A harvest and a spot are read further, as the next paragraphs say.

**Announcements and pay.** A finished objective that is not the last queues `update 3` `Mission "<mission title>", objective "<objective title>" completed.` for the next heartbeat. The last one completes the mission: its `N gm$` and `N em$` rewards are paid through `State.AddCurrency` (so each has a wallet row, `gm$ reward` or `em$ reward`), `update 15` with the new balance goes into the reply of the heartbeat that carried the event, and `update 3` `Mission <title> completed.` into the next one (after the harvest's trophy score). Item and trophy rewards (only the event mission lists any) are not delivered. The missions it unlocks become active when `auto_mission_activate` is set, or, with `activate_only_favourite`, when they are in a favourite group.

**Restored states.** The saved `Mission_missions.json` (`extras`) is copied into the rows at restore and, for an account restored before, on its first mission call: `completed`, `active` with the finished objective ids of `states`, the three switches and `favourites`; `available` is not stored. Ids without a definition and favourite groups that no longer exist are kept as they are (they unlock nothing and cannot complete). A restore replaces the rows with the zip's, or with none.

**Conditions of a harvest.** The rest of the title is read for what it asks of the kill, from the events of the animal since its spawn (event 7): its hits (events 1, the last one is the killing hit) and its harvest (event 3). Every condition the title names must hold.

| Words of the title | Checked against |
|---|---|
| a weapon's name (`using the .22 Air Rifle`), a class (`any shotgun`, `any bow or crossbow`; a bare `bow` is no crossbow) with the name words before it (`any 12 GA Shotgun`, `a Compound Bow`) | the last hit's `weapon_id` |
| an ammunition's name (`using .17 HMR HV ammunition`, `Slug Shells`, `a .243 ammunition`) | the last hit's `ammunition_id` |
| `permitted` or `ethical` ammunition | no hit of the kill was not permitted (the kill is not disqualified) |
| `with one shot`, `single shot` | the animal has exactly one hit |
| `double lung shot`, `lung`, `heart`, `heart or lungs`, `brain` | the bits of the last hit's `organ2` (heart 1, right lung 2, left lung 4, brain 16; double lung needs both) |
| `at 100% Harvest Value` | event 3's `harvest_value` is 100000 |
| `over`, `under`, `at least`, `at most`, `a maximum of`, `N or more`, `between A and B` metres | the last hit's `distance_cms`; the feet and pounds in brackets are not read |
| `a score of N or higher`, `scoring more than N`, `N point score` | the harvest's score (the one its update 6 shows); a kill with no score meets none |
| a weight in `kg` or `lbs` with `at least`, `more than`, `or lower` ... | event 7's `weight_grams` |
| `airborne`, `standing`, `walking`, `running`, `moving`, `charging`, `fleeing` | the last hit's `animal_state` (flying 6 and 11, standing 3, walking 4, running 5, charging 9) |
| `unspooked`, `spooked` | the animal's first hit's `animal_state` (calm: 1 to 4, 6, 7, 8, 12; fleeing: 5, 10, 11, 15, 16). An approximation: the data has no threat state, only the animal's state at its first hit |
| `from a Tree Stand`, `Hunting Tower`, `Ground Blind`, `Waterfowl Blind`, `Tripod`, `Shooting Tripod Rest` (also a list of them); `without a tower, blind, ...` | the last hit's `location` (tower 1, tree stand 2, ground blind 3, tripod 4, waterfowl blind 5, rifle rest 6; 0 for none). A spot reads its own `location`, which is assumed to carry the stance like a hit's does (not confirmed: without it such a spot is never met) |
| `without a scope`, `iron sights`; `scoped` | the last hit's `scope_id` is -1; is not |
| `in <reserve>` | the reserve of the hunt the harvest happened in |
| a quoted name (`"Patient Zero"`) | with the title's coordinates: an animal of the species (the title's, else the mission's own list) and gender within 1000 m of them (the last hit's `x` and `z`, else the spawn's, read as metres in the reserve's map frame: the unit is an assumption, and a wrong one means the objective is never met), together with the title's other conditions; event 7's `special` is not required until its meaning is known (an ordinary animal sends 0), so any such animal there counts. Without coordinates: an animal whose `special` is not 0. The words that name the place before the coordinates are not read |

**What is not understood.** What is left of a title after the conditions above, the species, the gender, articles, `any`, `permitted` and `in the same hunt` are taken out makes it not understood: typical points, colours and variants, places (`north of ...`), counts and time spans (`two within 5 minutes`), a sight, a stance such as `prone`, a weapon spelled another way, a second species. A spot is read for its stand, its reserve and a name only: any other condition makes it not understood. Such an objective, and one of a kind the server does not read, is never met: a harvest of its species no longer completes it. The harvest stays among the stored events, and [it is confirmed later](#missions) when a version reads the title. `coverage` ends with the missions' report: the objectives of the catalogue and how many are understood by kind, the conditions read, how many are not, and each objective that is not, with its mission id and title.

**Confirmed later.** At its start the server checks every account's active missions again (`State.ConfirmMissions`): the open harvest objectives against the harvests stored since the mission was activated (`seen`; for a single-hunt mission those of the latest hunt), in order, as the heartbeat would have. An objective that a harvest meets under the rules of this version is finished now, with the toast and the rewards of that finish (gm$ and em$, and the missions it unlocks, activated as at that harvest); the server prints how many it finished. A player loses nothing by waiting for a version that reads their title. A mission of an earlier schema (`since` null) counts the harvests from the first start of schema 30, and the objectives it had finished then are `earlier`: no later harvest is given to them again. Only harvest objectives are checked again.

**Rollback.** The earlier rules finished objectives whose titles had conditions the server did not read. `admin missions-rollback [--apply] [--account <id or handle>]` checks each finished harvest objective of every mission against the harvests since it was activated (since the account's first event when the activation is not known; the best single hunt for a single-hunt mission) under the rules above; one that no harvest meets is reopened. A completed mission that loses an objective is active again, and the missions it had made available are activated, so nobody is locked out. The gm$, em$ and items already paid are not taken back, and a mission or objective a restore brought (`kept`) is never touched: no event of it exists. A mission that was reopened and is finished again pays its rewards again. Without `--apply` it prints one line per account with a change and the total, and writes nothing (a dry run); `--apply` changes the rows and writes a record per account in `mission_rollbacks` (schema 30: the time, and JSON with the missions and objectives reopened and the missions activated). Run it once, after `backup`, with the server stopped; a second run finds nothing more.

## Daily missions

On a community server `Daily_Mission/*` answer from the facts file's `daily_missions` table and the account's row of `daily_missions` (schema 15: one JSON row with `frozen`, `day`, `date`, `done`, the finished `objectives`, the broken streak (`has_broken`, `larger`) and `days`, the days completed here by difficulty id). Without templates in the facts file, and on a local server, the calls keep the empty replies of [the table above](#recordings-on-a-community-server). Every call needs the player's own token.

| Call (form `oauth_access_token` only) | Answer |
|---|---|
| `POST /v1/Daily_Mission/get_daily_missions_calendar` | `{is_frozen, mission_end, broken_streak_info: {has_broken_streak, streak_larger}, calendar}`. `is_frozen` is 1 until the player activates a streak, `mission_end` the unix second the UTC day ends at. `calendar` has 7 entries, `day_number` 1 to 7: the block of 7 streak days that holds today (days 1 to 7, then 8 to 14 shown again as 1 to 7, and so on), each with `difficulty` (`{id, title, alias, mission_cooldown, color}`), `rewards` (the `SILVER` row: its `amount` is the day's gm$) and `protected` false. The entry of today has `today` true and the mission: `date`, `species` (the define of the first objective's species), `character` (the giver, its name made from the alias), `rewards_translations`, `mission` (`id`, `title`, `description`, `gender` 0, `species`, `reserves`, `objectives`) and `objectives`, the JSON string `[{objective_data: {id, title, update_message, conditions, completed?}, event_type}]` (`completed` once the objective is finished; `event_type` `CLUE`, `SPOT` or `KILL`). The other entries have `date`, `species`, `character`, `mission` and `objectives` null and `rewards_translations` `[]` |
| `POST /v1/Daily_Mission/activate_user_progress` | `{"success": true}`. A frozen account becomes active at day 1 with today's date, keeping the mission it showed, and the broken streak is let go; an account that is not frozen is left as it is |

**The day's mission.** The templates of the day's difficulty, in the file's order, are taken in turn by the date (`templates[date.DayNumber % count]`), so every player on the same day and difficulty has the same mission. The difficulty is the cycle's entry for the streak's day (0 first): `E E E M E E E M E E E M E E E H` in the file. The reward is the difficulty's `reward` gm$, 10 % more for each completed cycle of 16 days, up to 10 cycles (110, 550, 1100 in the second cycle). Objectives are read like a catalogue mission's ([Progress](#missions): a title gives the kind, species, gender, clue count and order; the condition text the page shows is made from the rule), with two differences: a harvest is the player's own, and a clue counts whatever its type (the condition names footsteps for the page). The templates are the facts file's: the known EASY ones, and made-up MEDIUM and HARD ones. A template with an objective that is no harvest, spot or clue, or that names no species of the catalogue, is left out (logged at the start): it would never complete, or accept any animal.

**The streak.** A new account, and a restored one that was frozen, is frozen: the calendar keeps the date it was made on (the restored one's date) and the mission picked for it, so the mission stays the same however many days pass, and its events count for nothing until `activate_user_progress`, which moves the date to today and keeps that mission for the first day. An active account's day is its date: a completed day is followed by the next one on the next date; a date that passes with the mission not completed, or a date skipped, freezes the account and breaks the streak, which starts again at day 1 on the next activation. A streak of at least one day that breaks is kept as `broken_streak_info` (`has_broken_streak` true, `streak_larger` the days it had) until the next activation; resuming it with the service item is not part of the server.

**Completing a day.** The last objective of today's mission pays the reward through `State.AddCurrency` (wallet row `Reward for Daily Mission`, `update 15` with the new gm balance in the heartbeat reply that carried the event), sends `update 17` `{mission_id, difficulty_id}` (no toast), marks the day done and adds a day to `daily_missions.<difficulty id>.days` of the account's [statistics](#the-statistics), so the achievements of `daily_missions.EASY.days`, `MEDIUM` and `HARD` follow at the next recompute ([Achievements](#achievements)). The entry stays as it is, with its objectives `completed`, until the day ends.

**The website.** The daily missions page reads the same state through `GET /account/missions/daily` and starts a frozen streak through `POST /account/missions/daily/activate` ([Upload a backup zip](#upload-a-backup-zip)), owner only. The server has no item to resume a broken streak, so the page offers none.

**Restored calendars.** The saved `Daily_Mission_get_daily_missions_calendar.json` (`extras`) is read the first time the account's daily missions are used: `is_frozen`, `broken_streak_info` and, for a frozen account, the date of today's entry; an account that was not frozen starts its streak at day 1 on that first day. A backup holds no streak length, so a restored streak always starts again; the restored `daily_missions.<id>.days` counters are the base the days counted here add to. A restore makes the calendar and streak again (from the zip's calendar, or as for a new account) and keeps the days counted here, like the hunts.

## Challenges

On a community server `Challenge/get_user_challenges` answers from the account's rows, and the hunt's events complete the challenges of the recorded `Challenge/get_challenges` list (the reply of the recorded player's list; without that recording there are no challenges and the empty reply stands). A challenge is a permanent, one-time goal with a badge and no pay: completing one writes a row and queues a notice, and changes no wallet and no statistics. The call is public ([ADR 0005](adr/0005-public-and-owner-only-profile-areas.md): the website shows the badges of any profile) and takes no token, as the game's own handler does: any account's rows are read with the `user_id`, in the form of a `POST` or in the query of a `GET` (the current build's pages use the second). An unknown, banned or recorded user id gets `{}`; a local server tracks nothing and leaves the call to its recordings.

The rows are the `challenges` table (schema 14): one per completed challenge (`challenge_id`, the definition's `objectives` text with `"completed": true` added to the objective, the definition's `objectives_hash`, `challenge_date` the UTC day), unique for an account and a challenge. The reply is an object keyed by the challenge id as text: `{id, user_id, challenge_id, objectives, objectives_hash, completed: 1, challenge_date}`; a challenge that is not completed has no entry (the page reads a missing id as not completed), and a completed one is not reset by the hunt (a restore replaces the rows). The heartbeat's events also carry the receive time now: `events.ts`, set at schema 14 (older events have none and are outside every time window).

**Rules.** An objective's `conditions` is a Python expression over the animal `a` of the event, the events `e` of the hunt and the constants `c`; the server reads the subset below when it starts (`State.LoadChallenges`) and an objective it cannot read (an unknown event type, call or constant) is left out: it never completes. A challenge completes with its first met objective (every definition has one). The objective's `event_type` says which heartbeat event tries it: `KILL` event 2, `CONFIRMKILL` event 3, `SHOT_HIT` event 1, `CLUE` event 12, `COLLECTABLE` event 24, after the event is stored. Distances are millimetres (event 1 `distance_cms` x 10). The animal is the event's `individual`: its latest spawn (event 7) gives the species, `texture`, and the hits (event 1) since it are its wounds.

| Expression | Value |
|---|---|
| `or`, `and`, `not`, `==`, `!=`, `>=`, `<=`, `>`, `<`, `True`, `False`, numbers, text, `{...}` and `[...]` lists, `set([...])`, `name=value` arguments | as in Python |
| `c.species.<DEFINE>`, `c.variant.<DEFINE>` | the catalogue `species[]` entry with that `define` (a variant is the id of its own entry) |
| `c.item.<DEFINE>` | the catalogue `items[]` entry with that `define` |
| `c.collectableCategory.<CAT>` | the catalogue `collectables[]` ids whose `cat` is `<CAT>` |
| `c.state.FLYING`, `c.state.FLYING_NOT_SPOOKED`, `c.organ.HEART`, `c.texture.ALBINO`, `c.clue.BLOODTRAIL` | 6, 11, 1 (the bit of event 1 `organ2`), 2, 0 |
| `a.species()`, `a.variant()`, `a.texture()` | the spawn's species number (variant 100 and up count for their species; a harvest's `extended_species` for `a.variant()`), the same, its `texture` |
| `a.ethical()` | no hit has an ammunition the species does not permit |
| `a.range('minimum')`, `a.range('maximum')` | the shortest and the longest hit in mm, 0 without a hit |
| `a.wounds.count()` | the hits so far, the current one included |
| `a.wounds.ammo(set)`, `.weapon(set)` | there is a hit, and every hit's `ammunition_id` or `weapon_id` is in the set |
| `a.wounds.scope(False)`, `.scope(True)` | there is a hit, and every hit has no scope (`scope_id` -1) or has one |
| `a.wounds.organ(list)` | a hit has one of the organ bits set in `organ2` |
| `a.wounds.state(set)` | the event's own `animal_state` (event 2), else the last hit's, is in the set |
| `e.animalCountWithFilters(<species>, seconds=N, same_shot=True)` | the deaths (event 2) of that species (any without it) in the last N seconds by receive time, else in this hunt (since the hunt's `first_event`), and with `same_shot` only those of the shot (`shot_id` of the death, else of its last hit) that killed the animal of the event |
| `e.animalCount(N)` | the harvests (event 3) of the animal's own species in the last N seconds |
| `e.collectableCountWithFilters(collectable_category=<ids>)` | the pickups (event 24, one for each `collectable_id`) of this hunt whose `type` is in the ids |
| `e.trackType()`, `e.individualCount()` | the clue's `track_type`; the clues (event 12) of that type for that animal in this hunt |

Where the definitions do not say, a hit-wide condition holds for every hit except the organ (any hit), and a count of harvests counts the animal's own species.

**Announcement.** `update 3` (`type` 100, `timer` -1, the missions' colour and icon) with the definition's challenge-level `update_message` goes into the next heartbeat's reply, like a mission's notice.

**Restored rows.** The saved `Challenge_get_user_challenges...json` (`extras`) is copied into the rows at the restore, and at the schema 14 migration for the accounts restored before: each entry with `completed` 1 or `true` keeps its `objectives`, `objectives_hash` and `challenge_date` as saved (what is no text is kept as none); entries with `completed` 0 or `false`, keys that are no number and values that are no object are skipped, and a restore replaces the rows with the zip's, or with none.

## The hunterscore

On a community server the server computes every account's hunterscore and stores it in the account's `account` object (and in a restored account's Me/me profile); the recorded player's account keeps its recorded value, and a local server computes nothing. The value is the sum over the rows of `ranks` in the facts file of min(`cap`, the row's count):

- **animal**: the ethical kills of harvested animals of that species (variants, ids 100 and up, count for their species);
- **weapon**: the ethical kills made with any of the row's items, all ammo summed;
- **collectable**: the pickups of the row's types.

The counts are the account's statistics ([The statistics](#the-statistics): `animal.<species>.ethical_kills`, `weapon.<item>.<ammo>.ethical_kills`, `collectables.<type>.collected`; a key or counter that is not a number counts 0, a counter counts at most a billion, and a row adds at most `cap`), so a server kill counts once, through its hunt: once harvested (event 3) and ethical (no hit with an ammo not permitted on its species), for its species and for the weapon of its last hit. A pickup counts once, through its hunt, for its type: a heartbeat's event 24 (`collectable_id`, `type`) or event 36 (a shed antler, type 2000 + its `species_id`, a variant counting for its species); one `collectable_id` counts once per hunt, however often the game repeats it, and an event whose type or species is no 64-bit whole number counts 0. Nothing else counts: no missions, competitions, challenges, achievements or trophy scores. An id that is no whole number counts 0 (a kill without a species counts for no species, a weapon that is no id counts for the species only); a kill, a hunt or restored statistics the server cannot read back (a number that is not finite) count 0 and are logged (`statistics of account <id>: …`, `statistics: …`, `hunterscore of account <id>: …`). The stored value is always the computed one, never a backup's own.

A hunt's kills are credited when it closes: the client's disconnect, the next `Launch/start` after a quit, or a close after `HEARTBEAT_TIMEOUT` without a heartbeat. A timer in the server (every 30 s, every account, no game call needed) makes that last close, so a player who quit through the game's menu is credited within about `HEARTBEAT_TIMEOUT` + 30 s; a connect or expedition read closes it too. A heartbeat that comes after such a close reopens the hunt (it is open again with its kills so far), and its later kills are credited when it closes again. The game shows the new value at its next connect. A restore and every server start recompute it too, so the stored values follow the facts file of the running server.

**The board** is every account not banned, the recorded player's left out, highest first; equal hunterscores take consecutive places in account id order (a missing hunterscore is 0). `Me/me`'s `rank` and `/auth/me`'s `rank` are the account's place on it. The website's server and the launcher read it on `web_host`, public and without a cookie: `GET /hunters?page=<n>` gives `{page, pages, total, rows: [{rank, handle, hunterscore, avatar}]}`, 30 rows a page (a page past the end is the last); `GET /hunters/<handle>` (case does not matter) gives `{handle, hunterscore, rank, membership, avatar, background}` (the membership's title, `""` without one, the URL of the avatar picture, [Avatars](#avatars), and the header picture the player chose, null without one), or 404 for a handle that is not an account of a player here ([Public reads](#public-reads)). The website's server asks over `SERVER_URL`; on the public domain the reverse proxy routes `/hunters` and `/hunters/*` to the server ([docs/deploy.md](deploy.md#the-community-server)).

**The minigames' boards**: `GET /leaderboards/<lanebandit|bustthrough>?page=<n>` on `web_host`, the same way, gives `{page, pages, total, rows: [{rank, handle, value, avatar}]}`, 30 rows a page: the best scores, highest first (a best is the higher of the restored statistics' `lane_bandit_score` / `bust_through_score` from a backup and the best heartbeat event 17 `{game_id, score}` of the account's hunts, game 0 Bust Through, 1 Lane Bandit; a score that is not a whole number is ignored; the connect reply's `user_stats` carries the same two bests wherever the server builds it from its own rows), equal scores in account id order; an account without one, or with 0, is not on it, nor is a banned one or the recorded player's. A player who never restored a backup is on them once a hunt reported a score. Another kind answers 404. Each account is read on its own (two queries per account and page view).

## Leaderboards and seasons

The species boards rank every hunter's best harvests, per species, by **score** and by **range** (the longest last hit, in metres). A board is of one **season**: 0 is all time (every harvest below; never stored), the others are the `seasons` table (schema 29: `no`, `start`, `end` in Unix seconds UTC, both inclusive, `end` null for the current season).

| Season | Holds |
|---|---|
| 0 | all time: every harvest of seasons 1 and later |
| 1 | up to 2026-11-11 23:59:59 UTC: the harvests of the restored accounts that a restore brought, with their original time. These are the saved all-time bests of each species (the best score and the best range, `Leaderboard/personal` of season 0 as the backup saved it); the saved replies of the original's own seasons are not read. An account with no saved bests (a claimed archive account has none) brings its restored trophy list and the animals mounted in its restored lodges instead (a trophy in both counts once, a hidden one not at all): the best score of each species counts, with the trophy's own time. These rows have no shot distance, so they rank on the score boards and the Hall of Fame's score only, never on a range board, and their weapon is unknown |
| 2 | from 2026-11-12 00:00:00 UTC, the first day of the community server: this server's harvests (`harvests`). The current season until the operator starts the next |
| 3 and later | this server's harvests made from the day the operator started it |

A harvest belongs to the season its kill time falls in: a restored harvest of 2025, or one at 23:59:59 on 2026-11-11, is in season 1 and in season 0; one at 00:00:00 on 2026-11-12, or today's, is in season 2 and in season 0. A harvest of this server made before 2026-11-12 (a test hunt) is in season 2, since season 1 is the restored harvests only. A hunter has one row per species on each board: the best of its harvests of the season (a tie goes to the earlier kill, then to the lower account id). Left out everywhere: hidden harvests (the lodge editor's visibility), harvests the server refused (score 0), banned accounts and the recorded player's. The page of a kill sheet (`kill`) exists for this server's kills only; a restored row has `kill` 0.

**Starting a season**: `POST /admin/season/start` (the [Admin API](#admin-api)) ends the current season one second before now and starts the next number now; harvests made from then on rank in it and the ended season gets a Hall of Fame. The original started a season on the first day of March, June, September and December since 2023; that is the proposed rhythm here, started by hand on those days.

**The Hall of Fame** of an ended season is, per species, the best score and the best range of it. Season 0 and the current season have none.

**Web calls** (`web_host`, public JSON, no cookie except `/me`; `season` is a number, 0 for all time, the current season when left out, 404 for one that does not exist):

| Call | Gives |
|---|---|
| `GET /leaderboards/seasons` | `{current, seasons: [{no, start, end}]}`, oldest first; 0 is not listed |
| `GET /leaderboards/<score\|range>?season=` | `{boards: [{species, name, top: [Row]}]}`: a block per species with a ranked hunter, in species id order, the best 3 |
| `GET /leaderboards/<score\|range>/<species>?season=&page=` | `{page, pages, total, rows: [Row]}`: the best 100 of the species (its id), 25 a page |
| `GET /leaderboards/<score\|range>/<species>/me?season=` | The `Row` of the hunter of the `hr_session` cookie, with its place on the whole board; 404 when it is not ranked, 401 when signed out |
| `GET /leaderboards/halloffame?season=` | `{rows: [{id, species, score: Row, range: Row}]}`, species id order; empty for season 0 and the current season |

`Row` is `{rank, handle, value, weaponName, ts, kill, avatar}`: `value` the score, or the range in metres; `weaponName` the weapon's name ("" where unknown); `ts` the kill's Unix seconds; `kill` its id for `/hunters/<handle>/score/<kill>` (0 for a restored one); `avatar` as on the hunterscore board. The hunterscore board and the minigames' boards above are unchanged.

**The original's calls** are answered from the same boards on a community server, for the pages that ask them: `Page_content/leaderboards_all` (`type` 1 score, 2 range: a block per species of the current season with its best 5), `Page_content/leaderboard_details` (`type`, `species`: the best 100), `Page_content/leaderboards_hall_of_fame` (`season_no`, default the season before the current one; a score is a text, a range a number; `[]` for the current season), `Leaderboard/current_personal` (`user_id`: the account's places, `[{species_id, score: {total, rank, animal_id, score}, distance_min: {...}}]`), `Leaderboard/personal` ([Public reads](#public-reads)), and `season` in the reply of `Application/application` and `Application/client_application`, which is the current season. They need no token (but `Leaderboard/personal`).

**The boards are kept.** A board is computed from the restored bests and the hit events of the harvests, one connection per account (1 to 2 seconds with the accounts of a live server), so the server keeps each computed board in memory: per kind (score, range) and season for 15 minutes (the current season and all time), for an ended season (its end is past) for 24 hours. The overview, a species' page, `/me`, the Hall of Fame and the original's board calls all read these kept boards; callers that arrive while one is computed wait for that one computation. A new harvest therefore shows within 15 minutes (an ended season's within 24 hours; a browser that keeps the reply may be up to a minute further behind), a restore or a ban the same way; `POST /admin/season/start`, deleting an account and hiding a harvest drop all kept boards at once. The anonymous board replies of `web_host` (the overview, a species' page and the Hall of Fame) carry `Cache-Control: public, max-age=60` and `Vary: Accept`; `/me` and the other replies stay `no-store`.

## The statistics

`Statistics/total` and the connect reply's `user_stats` are the account's restored statistics, a base that play never changes (empty for an account that restored nothing), plus the sum of its closed server hunts. When a hunt closes (the ways in [The hunterscore](#the-hunterscore)), its statistics, the `stats` that `Public_user/expedition` shows for it, are stored with it: its events up to the next hunt's start, its harvests and pickups; a server start first stores those of any closed hunt that has none, and a harvest or pickup that lands in a hunt after its close (a heartbeat between a disconnect and the next connect) has that hunt counted again at once. The sum adds per species `spots`, `tracks`, `kills` and `ethical_kills`, per weapon and ammo `hits`, `misses`, `kills` and `ethical_kills`, per collectable type `collected` and `sum` (and the larger `max`, [Pickups](#the-statistics)), and the hunts' `distance` and `duration`; a weapon and ammo's `distance` (its longest hit) is the longest of the base's and the hunts'. A restored counter that is no number is replaced by the hunts' sum. A later restore replaces only the base: the server hunts stay and still add on top. On a community server every account has them; on a local server a restored account does (any other account replays its recording). The days of the account's completed [daily missions](#daily-missions) add to `daily_missions.<difficulty id>.days` the same way.

`Expedition/list` pages the account's server hunts, newest first, by `offset` and `limit`; each shows its `collectables` (its pickups and shed antlers), and `Public_user/expedition` lists its shed antlers as `antler_collectables` `{id, species, score, type, ts}` (`type` `single` or `double`, as the original servers sent them; the in-game page reads `type`). The recorded ones, if any, follow them, and a page past the server hunts is the recorded page. `total` is the server hunts plus the recording's `total`, and `has_more` is true while a later page has entries. `Public_user/expedition` answers the hunt named by `expedition_id`, else the latest; an unknown id gets the reply an account without a server hunt gets (the recorded one, `null` on a community server).

**Pickups.** A pickup (heartbeat event 24) or shed antler (event 36) is answered with update 7 `{collectable_id, score, update: 7}` in the same heartbeat; the game asks every second until it comes. `score` is a text the HunterMate shows as is, and the game closes on a number. The score is `min + (max - min) * f` of the type's `score` range in the install's collectable definitions (`collectable.json` in the archives), or, for a type it gives none, in the facts file's `collectables`; a type with neither scores 0, `f` the share the game drew for the pickup: `scale` / 100, or the antler's `antlers_score_percentage`. The game draws `scale` as a half-normal value, and the original servers' scores of restored hunts spread over each range the same way. The text follows the site's own formats: `29g / 1.03oz` for a mushroom, `450mm / 17.72in` for a feather, `915y` for an artifact or recent fossil, `12m.y` for an old fossil, the score for an antler, `5 points` for event items, the rounded score otherwise. The score is kept with the event, and a hunt's statistics hold per type `collected`, `max` and `sum` (a text, three decimals, as the original servers); the profile totals add the counts and the sums and keep the larger `max`.

A restored account ([Import a backup zip](#import-a-backup-zip)) whose backup zip saved hunts also lists them: `Expedition/list` is the server hunts, then the saved hunts in the order the backup zip saved them, one paged list whose `total` is both counts and whose `has_more` is true while a later entry exists (the recorded reply is not used; a zip that saved no hunt keeps the recorded answers). `Public_user/expedition` with a saved hunt's id answers its saved reply, and without `expedition_id` answers the newest saved hunt (the highest id) while the account has no server hunt. A saved hunt is shown only: it is not added to the statistics or the hunterscore again, the restored statistics already hold it.

## Achievements

On a community server the server awards the achievements an account's [statistics](#the-statistics) reach; the game works out an unlock itself and never tells the server. Whenever the hunterscore is recomputed (a hunt's close, a restore, a server start; the recorded player's account is left out, as there), every definition of the connect reply's `achievements` is checked: its `value` path names a counter of the statistics, and each of its `triggers` thresholds at most that counter which has no earn time yet gets an earn time: the close time (Unix seconds) of the hunt that has just closed (the latest one when several closed together, as a server start or a timer can close more than one), else the current time. A hunt's page lists the thresholds whose earn time is its close ([Public reads](#public-reads)). The account's row keeps the counter, in whole numbers, as its `value` (a larger stored one, a backup's, stays); a row is made once the counter is above 0. Earn times already stored, a restored backup's too, are never changed, so the game does not announce an achievement again. A restore replaces the rows with the backup's, and the check right after it awards again what the server hunts reach. `Achievement/stats` (any account's user id) and the connect reply's `user_stats.achievement_stats` carry the rows, and the profile page header (`earned_achievements`) counts the thresholds with an earn time (the achievements tab's `unlocked` counts those of the connect reply's definitions).

A path's segments are split on `.`. The first is the root: `animal`, `weapon`, `collectable` and `daily_missions` are those objects of the statistics (`collectable` is `collectables`), `distance` is the metres / 1000 (km) and `duration` the seconds / 3600 (hours). The segment after an object root names its entry: a species define of the application catalogue, an item define of the install's item definitions, a daily mission kind (`EASY`, `MEDIUM`, `HARD` are 1, 2, 3), or the id itself; the entry is that exact id (a species variant, id 100 and up, is its own entry, unlike in the hunterscore), and later segments are keys as they are. `*` sums every child, `[a,b]` the children listed, and the last segment is the counter (`ethical_kills`, ...). So `animal.*.ethical_kills` is every ethical kill, `weapon.<ITEM>.*.ethical_kills` those of one item with any ammo. A name that is unknown, an entry that is missing or a counter that is no number counts 0.

## Friends

On a community server two players are friends when both have an account here and either one's restored friend list (`User/friendslist` and `Me/friends` of the backup, kept in `extras`) holds the other, or when one accepted the other's request here. The `friends` table keeps one edge per pair and direction: `request` (the account asked the other) or `friend`. A restore adds the edges of its lists (`friends`, incoming `requests`, outgoing `pending`): a `friend` edge replaces a request, any other edge the pair has already stays, so the order of two players' restores does not matter and a friendship removed here comes back with the next restore of a list that holds it; an edge to a player without an account here counts once that account exists, and never for a banned account or the recorded player's. Deleting an account drops its edges both ways. A local server replays its recordings.

| Call | Answer |
|---|---|
| `POST /v1/Friend/add`, form `oauth_access_token`, `friend_user_id` | Accepts the other player's open request (they are friends, the request is gone), else asks them; nothing more when they are friends or asked already. `true`; `{"errorCode": 400}` for the player's own id or one with no account here |
| `POST /v1/Friend/remove`, same form | Drops every edge of the pair: declines or cancels a request, or ends a friendship on both sides. `true`; `{"errorCode": 400}` as above |
| `POST /v1/Me/friends`, `oauth_access_token` (form, or a JSON body) | `{friends, friendCount, requests, requestCount, pending}`: `friends` and `requests` (the players who asked) are entries `{id, handle, avatar, fullbody_avatar, hostname, hunterscore, online}` (`fullbody_avatar` 0 without one, `online` as `Public_user/getByHostname` has it), sorted by `handle` in upper case, ordinal; `pending` the user ids the player asked |
| `POST /v1/User/friendslist`, form `user_id`, `offset`, `limit`, no token | `{total, friends}`: every friend of the account in `total`, one page of the same entries in `friends`. `limit` 1 to 50 (above 50: 50; missing, empty or below 1: every friend); `offset` missing, empty or negative is 0, past the end an empty page. No `user_id`: `{"errorCode": 400}`; an empty, non-positive or unknown one: `null`; a non-numeric `user_id`, `offset` or `limit`: `{"error": 1, "code": "handlerError"}` |

`Me/poll` and `Me/me` carry `friend_requests`, the number of `requests`. The current build's `/v1/friend/add?locale=<locale>`, `/v1/friend/remove`, `/v1/me/friends` and `/v1/me/poll` with a JSON body are the same calls ([The current build](#the-current-build)).

## Messages

The player's own inbox, on a community server. `Chat/conversations` lists the server's notice conversation (sender `Server`, user id 1024, the notices of [Upload a backup zip](#upload-a-backup-zip)) first, then the conversations a backup held (`Chat_conversations.json` in `extras`) exactly as saved, owner-only (the token's account). `Chat/conversation` with `user_id` answers the notice thread (and marks it read), or else the saved `Chat_conversation__user_id=<id>.json` of that partner as it is, or an empty thread; reading a restored thread marks nothing, so a restored conversation keeps the `read` it was saved with. Sending messages between players is not part of the server.

The website reads the same through `GET /account/messages` and `GET /account/messages/thread` ([Upload a backup zip](#upload-a-backup-zip)), read only. A message is the player's own (`mine`) when its `user_id` is not the partner's.

## Gallery

A photo the game asks for (heartbeat event 4) gets a row in `photos` and an upload link; the file it sends is stored as `photos/<account id>/<id>-<photo_type>-<token>.jpg`, the thumbnail as `<id>-<photo_type>-<token>-thumb.jpg` (none for the automatic shot screenshot, `photo_type` 14). `<token>` is the first 32 lower-case hex digits of an HMAC-SHA256 of `photo:<account id>:<id>`, keyed with the secret the server keeps beside its database (`state.db.jwtkey`): the picture and its thumbnail, uploaded in either order, share it, and a link cannot be guessed from the sequential photo ids and the public account ids. The row's `file` holds the name and every link is built from it. A requested photo that was never sent is no photo. The gallery of an account is its uploaded camera photos (`photo_type` 1) and trophy shots (`photo_type` 2) and the pictures a restore unpacked (below), newest first; every other type of an uploaded photo (the automatic screenshots the game takes by itself, the avatar picture) is stored but never listed, zipped or linked. A photo shows the kill of the animal it was asked for while (the same `individual` and the same latest event 7 as the kill's hits; `photos.spawn` holds that event, as the schema of version 8 added): `animal` is that kill's species name and `label` its score (both `""` without a kill), `thumbnail` the link of the small picture (the picture's own link when the game sent none), `url` the full picture. `Gallery/list` links the game's host; the website's `GET /hunters/<handle>/gallery` links `https://<web_host>/photos/<account id>/<file>`, which the server serves on `web_host` too (the reverse proxy routes `/photos/*`, [Behind a reverse proxy](#behind-a-reverse-proxy)). **At start**, every server renames the photos still stored under the earlier names `<id>-<photo_type>.jpg` (and their `-thumb` files) to their token names and updates their rows, whatever the type; a file that is gone only updates the row, and a second start changes nothing. The earlier links stop working.

| Call | Answer |
|---|---|
| `POST /v1/Gallery/list`, form `oauth_access_token` (any player's token), `user_id` (the player's own without it), `offset`, `limit` (missing or below 1: all) | `{total, photos: [{id, type, url, thumbnail, label, animal}]}`: any account of this server is listed (not a banned one, nor the recorded player's); an unknown id is `{"total": 0, "photos": []}` |
| `POST /v1/Gallery/delete`, form `oauth_access_token`, `photo_id` | `true` after deleting the player's own photo (its row and files), `false` for anything else, another player's photo included |

A kill's `photo` in `Public_user/expedition` and the kill details page is the link of the newest trophy shot (`photo_type` 2) of its animal, `null` without one: a camera photo or an automatic screenshot is never a kill's picture. A restore unpacks the pictures of its zip into the same folder ([Pictures](restore.md#pictures)): its gallery pictures are rows with `photos.saved` set (schema 10: the saved `label` (the entry's, else its kill's score), `animal` (the species) and `kill_id`, listed where no kill is found here; a real `Gallery/list` entry's `animal` is an object `{scoreType, species_id, score, id, species}`, null for a camera photo, and the details are read from it) and get the links above; a saved kill's `photo` is the link of its stored picture, else of the newest restored trophy shot (type 2) whose saved `kill_id` is the kill's id (set when a saved hunt is answered, in the game reply and the website's hunt page, never written to the saved reply); the game's kill details page (`/user/<handle>/score/?id=<kill>`) of a saved kill is its saved page, sent with `Content-Security-Policy: sandbox` so that no script of a zip runs on this host. A restore again replaces them all; the photos taken here stay. A restore that makes the account adopt the backup's user id (`review approve`) moves `photos/<old id>/` into `photos/<new id>/` with its rows: the folders are merged, and on a name clash the account's own photo is kept; the photo links follow, as they are built from the account id. The website's gallery tab and its delete and download are in [Public reads](#public-reads) and [Upload a backup zip](#upload-a-backup-zip).

## Avatars

Every account shows one picture: an avatar of the game's list, or the one imported from its backup. The list is the recorded `Avatar/getAvatars` ([Starting data](#starting-data)): its ids (`1000000` and on). Their pictures are this server's own, `<game host>/media/avatar/256/<id>.png` (`<game host>` is `https://<game_web_host>`; the website and the launcher get the website's copy, below): the server never hands out the list's own address, which names the original's avatar host. The account holds its choice in its connect `account` object: `avatar_url` (the picture's address), `face` (the avatar's id) and, where the object has them, `avatar` and `avatar_id` (the same id); a restored profile's `Me/me` has the address as its `avatar`, and `Public_user/getByHostname`, `Me/poll` and the friend entries read it from there. The game reads these values in its connect reply, so a changed choice shows in the game at its next start.

**A reply for the website or the launcher** (the boards, a profile, the friends, the messages, `GET /account/avatars`, `Me`) gives an avatar of the list as the website's own copy, `<site>/images/avatars/256/<id>.png` (`<site>` is `https://<web_host>`, the stock copies of [images](images.md)); the imported picture is `<site>/photos/<account id>/avatar.jpg`. A reply for the game, the in-game board pages included (`leaderboards_all`, `leaderboard_details`, the Hall of Fame), keeps the game host.

An address is an avatar of the list when its path ends with the path of that avatar's picture in the list, whatever its host: an account's `…/media/avatar/256/<id>.png` on the web host is the list's `…/256/<id>.png`.

- **A new account** has the default avatar, `1000000`, and the `gender` of its list entry (`m` is 1, `f` is 0; the male default gives a male body). The game draws the character from `gender` and `face` of the connect `account`, so a choice shows at the player's next game start.
- **Choosing a listed avatar** (`POST /account/avatar`, which the website, the launcher and the sign-up carousel use) sets `gender` from its list entry together with `face`; choosing the imported picture leaves `gender` as it is.
- **Store avatars.** The store sells avatars (catalogue category Services, sub-category Avatars) that the recorded list does not hold. The facts file's `store_avatars` names each one's picture id, and the server adds it to the list after the recorded avatars (only when the catalogue has its `item`), with `unlock_item_id` the item and `unlocked` false. An account can choose it once it owns the item (an inventory row, however it got it); until then it is shown locked and refused. The picture is served like every other avatar's (the operator's `avatar-<id>.png`, else the stock copy `avatars/256/<id>.png`). A restored profile that names one keeps it.
- **At start**, a community server gives an account whose `avatar_url` is an avatar of the list under another address (a row from before: the original's avatar host, which the game no longer reaches) this server's address, in its `avatar_url` and its restored profile's `avatar`; its other values stay. A second start changes nothing.
- **At start**, a community server also gives an account that never restored anything (no restored id, restore audit or claim) the `gender` of its listed avatar when they disagree. A restored account keeps its own until the player picks a listed avatar. A second start changes nothing.
- **A restore** ([Pictures](restore.md#pictures)) sets them from the zip's profile: the picture's address is an avatar of the list: `avatar_url` is this server's address of that avatar (`<game host>/media/avatar/256/<id>.png`) and `face` the avatar's id; else, when the zip holds the picture, it is the account's *imported avatar*: stored as `photos/<account id>/avatar.jpg` (besides its `images_` copy), `avatar_url` is its link on the game host (`/photos/<account id>/avatar.jpg`) and `face` the default avatar; else (no picture in the zip, or no address) the default avatar. A restore again replaces the imported avatar; the account's choice of a game avatar is replaced like the rest of the profile.
- **At start**, a community server gives an account whose `avatar_url` is the address of a picture the player uploaded on the official site, and whose restored copy (`photos/<account id>/images_…`) is in its photo folder, that picture as its imported avatar (a copy at `avatar.jpg`, `avatar_url` and the restored profile's `avatar` the link above; its `face` stays). A picture with no copy stays as it is and shows the default avatar.
- **The picture** of the imported avatar is the photo link `/photos/<account id>/avatar.jpg`, on the game host and on `web_host` ([Gallery](#gallery)), served as `image/jpeg` whatever the bytes are.
- **The game's avatar pictures** `<game host>/media/avatar/256/<id>.png` are the operator's `avatar-<id>.png` in `images_dir`, else the stock copy `avatars/256/<id>.png` there, served as `image/png`: `GET /media/avatar/256/<id>.png` on `game_web_host` (where an account's `avatar_url` points) and `GET /256/<id>.png` on `avatar_host`. Only an `<id>` of the list is answered (written as a number, no leading zero), so the path never leaves the folder: any other id or path, and any other host, is a miss. The notice sender's picture (`256/10000000.png`, the avatar of a notice in the inbox) is answered the same way (`avatar-10000000.png`, else its stock copy, else the default avatar's picture). An id with no file of either kind is served the default avatar's picture; without that file too it is a miss. The folder is read at each request, so a new file shows at once. A local server and a community server answer the same.
- **An uploaded avatar the zip does not hold**, only its link: fetched from `<avatar_uploads>/uploads/thumb/242x242/<uid>.jpg` (without `avatar_uploads`: the base of the recorded avatar list's address) under the rules of `picture_link_hosts` and stored as the imported avatar, as above ([Uploaded avatars](restore.md#pictures)); `admin avatars [--account <id or handle>] [--dry-run]` does it for the accounts already restored: every account (or one) whose avatar is the default or a dead upload link gets the uploaded avatar its restored data names (the `avatar` of its profile, saved Me/me or Public_user/getByHostname reply, the first upload link wins; with none of them, the archived uid of its claim). The default avatar `1000000` is never the player's choice, even where the restore wrote it into the profile: it is ignored, so a save whose profile says the default but whose saved Me/me names an upload, or whose claim has no avatar in its data, is fetched. It prints one line per account, `<id> <handle> <result>` (`set`, `no uploaded avatar`, `fetch failed`; `--dry-run` fetches nothing and prints `would fetch the avatar of user <uid>`). An account whose avatar is already a stored picture, or a stock avatar other than the default, is not touched. The avatar host must be in `picture_link_hosts`, except for a uid with a saved copy (`avatar_uploads_dir`, [Run it](#run-it)).

What the website is told (`avatar` in `GET /hunters/<handle>`, the board rows, the friends and conversations of `/account/` and the friends tab of a profile; also `GET /auth/me`) is one URL: the imported avatar's link on `web_host`, this server's address (`<game host>/media/avatar/256/<id>.png`) for an avatar of the list, whatever address the account stored (a row from before names the original's avatar host), and `null` for anything else (an address that is none of the list, an imported picture that is gone), where the page shows its default avatar. A list reply carries each player's, so a page of players takes one request. The notice icon of the heartbeat (`destination`) and the notice sender's avatar are on `<game host>/media/avatar/` too.

**The stock copies** are kept so the avatars outlive the original's avatar host: `<images_dir>/avatars/256/<id>.png` for every id of the list (256 pixels square, the only size the game and the website ask for), and `10000000.png` (the notice sender), also served by the website at `/images/avatars/256/<id>.png` (a subfolder is not a slot: it is not in `/images.json` or the missing list). To refresh them after the list changes, copy the new ids' pictures from a saved copy of the avatar host into that folder (or add `avatar-<id>.png`, which wins over the stock copy and is the website's slot picture); the folder is read at each request, so nothing restarts. Uploaded avatars (`/uploads/thumb/242x242/<uid>.jpg`) are not stock copies: a restore reads the saved copy `<avatar_uploads_dir>/242/<uid>.jpg` (`avatar-uploads/` next to `settings.json`, in the folder the server already mounts), else fetches it from `avatar_uploads`, and keeps it as the account's imported avatar; the sweep `admin avatars` does the same.

## Wallet history

`Wallet/transactions` (em$), `Wallet/silver_transactions` (gm$) and `Wallet/spent` answer the account's own history on a community server; another player's `user_id` gets the empty reply, and a local server replays its recordings. A page is 50 rows from the form's `offset`, newest first by `created`: the rows of the restored backup zip's pages (`Wallet_transactions`, `Wallet_silver_transactions` in `extras`, as saved) and this server's own rows. A row is `{id, created, type: {id: C|D, name}, amount, preBalance, postBalance, summary, mission, items, qty}`: `amount` is never negative (`type` gives the direction), `items` are the catalogue's definitions of what was bought (one entry for each kind, `qty` the copies of each). `Wallet/spent` is `{spent, silver_spent}`: the restored totals (`Wallet_spent`) plus the payments made here. `Wallet/bank_transactions` is still the empty reply: the server has no bank.

This server's rows are the `wallet_log` table (schema 11): `State.AddCurrency` writes one row for every change of a balance, in its transaction: a purchase (summary `In-game payment.`, with the item ids; the game's `Inventory/buy` and the website's [buy](#buying-from-the-website)), a kill's gm$ reward (`CSS Reward (Animal Id: <kill id>)`; the operator's `/admin/rescore` pays a missed one the same way), a dog's level reward (`Dog level reward.`, [Dog level rewards](#dog-level-rewards)), a mission's reward (`em$ reward` or `gm$ reward`, [Missions](#missions)), a daily mission's (`Reward for Daily Mission`), an event's community mission's (`em$ community reward` or `gm$ community reward`) and an operator's adjustment ([Admin API](#admin-api); `Adjustment by the operator.`). A change that is refused (a balance too low) writes none. A taxidermy or a skull mount is a purchase of the store item 744 or 1111 (`Taxidermy (immediate)` in the catalogue; [Taxidermy](#taxidermy)), so it counts in `Wallet/spent`; one the operator undoes is given back with `Taxidermy undone by the operator.`; a price of 0 writes no row.

The website reads the same rows with the session cookie: `GET /account/wallet/ems` and `/account/wallet/gms` (query `offset`) answer the array above, `GET /account/wallet/spent` the totals; 401 `signed_out` without a session.

## Placed items and stacks

A heartbeat changes an item's place and units, one account's rows only:

- **Placing**: event 25 `{item, position_x/y/z, direction_x/y/z}` (millimetres and x 1000, numbers within ±2,000,000,000, the restore's limit of 2,000,000 metres, rounded to whole numbers: the units of a restore, [restore.md](restore.md#field-rules)) stores `__position`, `__direction` and `__reserve` in the item's metadata; the reserve is the one of the account's newest hunt (the web's number, from 1; none without a hunt). A position that is not three numbers is ignored. Event 8 `{item, slot: 23}` then puts the item in slot 23.
- **Picking up**: event 8 `{item, slot}` with any other slot sets the slot and removes the three keys, so a restored placed item stays picked up at the next connect.
- **Moving units**: event 33 `{item_from, quantity, item_to?}` takes `quantity` units from a stack and adds them to `item_to`, a stack of the same item; with no `item_to` nothing moves (the client's way of splitting a stack is not known). A stack that reaches 0 units moves to slot 0, as for event 6. Nothing moves when a stack is unknown, has no units, holds fewer than `quantity`, is of another item, or `item_to` is `item_from`.

The connect reply gives a placed item its `position` and `direction` (the restored rows' shape, without the reserve). `Inventory/list` and `Inventory/dict` (`{<item id>: [{id, slot, units, metadata, location}]}`; own user id only, another gets `{}`) give an item in slot 23 with a position `location: {reserve, pos: {x, y, z}, dir: {x, y, z}}`, `pos` in metres and `dir` the direction divided by 1000 (left out when the item has no direction); every other item has `location: null`.

## Lodges and trophy visibility

A lodge is the rows it has (`lodges`, one row of `/game/user/lodges` and one of `/game/user/lodge` per lodge id, as read): the ones a restore stored for the account, and one for each unit of a lodge item the account buys in the store (a catalogue item of the facts file's `trophy_lodge.lodges`, bought in the launcher, on the website or in the game, or added with `admin item`). A new lodge is named for its layout (`Rustic Lodge`), unlocked, style 0, empty, with `lodge_engine_id`, `lodge_type_define` and `lodge_type_id` (the item id) of its layout and the account's next lodge id (a whole number above every lodge id of the account). **A new account starts with no lodge**: the start kit ([Starting data](#starting-data)) holds none, and the original's free start did not either; the selection page then says the player owns none. On a community server the player edits them, with a Bearer token, on API v2 and at the same path under `/v1` on the game's web host (the game sends the JSON body as `text/plain`; the body is read whatever its content type, and the web host's JSON-to-form rewrite ([The current build](#the-current-build)) leaves a PUT alone):

## Taxidermy

A harvest made here can be taxidermized, or its skull mounted, once, in the game and from the player's own hunt page. The harvest then is a trophy: it is in `/game/user/trophies` (the lodge editor's list; a skull mount with `is_skull` true, for the editor's skull slots) and its harvest page has `taxidermized` true. A harvest that is not taxidermized is not in that list, except in the grace window below. The trophies a restore brought are not harvests made here: they are all listed, as always.

**The grace window.** Harvests made before the taxidermy went live were all in the lodge editor. Their window ends 72 hours after the deploy, not after the harvest: `taxidermy_grace` (schema 28, one row `start`, `grace_end`) is written once, at the first start with this code (`start` now, `grace_end` now + 72 hours; a database made new has `start` 0, so it has no such harvest). A harvest whose `timestamp` is before `start` has `end` = `grace_end` (the offer's `taxidermy.end` and the check of the game's path alike), same price and rules; until `grace_end` it is also listed in the editor, after it only if it was taxidermized. No date is in the code.

A harvest that is already mounted in a lodge slot is not taken out of its lodge by any of this: the slot's `trophy_details` ([Lodges](#lodges-and-trophy-visibility)) are read from every harvest of the account, taxidermized or not, so the lodge keeps showing the animal after the window ended or an operator's undo. Only the editor's list of what can be mounted is narrowed.

**The rules** (`State.Taxidermize`, one transaction): only the account's own harvest made on this server (a harvest a restore brought is never offered: 404, like an unknown kill or another player's); once, either product (409 `already`); within 72 hours of the harvest (`timestamp` of its page; the grace end for an older one; 410 `too_late`); a skull mount only for a species of the lodge catalogue's `skull` page (400 `no_skull`); the price in the currency the player picks (402 `not_enough` when the balance is lower; nothing changes). The price is the facts file's `taxidermy` (10 em$ or 2,000 gm$, the same for both products; 0 is free). It is paid with `State.AddCurrency`: a wallet row `In-game payment.` for the store item 744 (taxidermy, `Taxidermy (immediate)`) or 1111 (skull mount), and the new balance reaches the game with its next heartbeat (update 15). The harvest page keeps what was paid (`taxidermy: {currency, price, ts}`) for the operator's undo.

**In the game** the harvest window sends `POST /v1/harvest/<kill id>/taxidermize` on the web host of the current build (JWT as `Authorization: Bearer`; API v2's `POST /game/user/harvest/<kill id>/taxidermize` for the old build). The body is `{"currency": "gold"|"silver"}` (gold is em$, silver gm$), with `"is_skull": true` for the skull mount; the handler also reads the form the current build's JSON becomes on its way here. The answer is 200 with no body (the game logs only a status outside 200 to 399), else the status above with `{"error": ...}`.

**On the player's own page.** `POST /account/harvests/<kill>/taxidermize` on `web_host` (the `hr_session` cookie and the header `X-Requested-With`, like the other account writes), body `{"product": "taxidermy"|"skull", "currency": "ems"|"gms"}`: 200 `{done, ems, gms}` with the balances after; 402 `{error: not_enough, currency}`; 409 `{error: already}`; 410 `{error: too_late}`; 404 for an unknown, restored or another player's kill; 400 for anything else, a skull for a species without one included. `GET /hunters/<handle>/hunts/<id>` shows the offer: when the `hr_session` cookie it carries is the handle's own, each kill made here has `taxidermy: {end, ems, gms, skull, done}` (`end` ISO UTC: the harvest plus 72 hours, kept after it passed so the page can hide the button; `skull` whether the species has a skull to mount; `done` `taxidermy`, `skull` or null). A restored kill, and the page of anyone else, has no `taxidermy`.

**The operator** lists the taxidermized harvests and undoes one ([Admin API](#admin-api)). An undo makes the harvest a plain one again (it leaves the editor's list, and can be bought again within its 72 hours) and gives the price back unless asked not to; a lodge slot that held it is not changed.

## Loadouts

An account's loadouts are its rows of `loadouts` (schema 12): `id` (unique across the accounts: it is the key of the save), `name`, `color` and `entries`, the list of items. Nothing deletes one. A restore reads the saved reply of `/game/user/loadout` (the extras file `game_user_loadout.json`) into rows, in order, under new ids (the saved ids are the game's own; an entry that is not an object is left out; a name that is no text, a color that is no whole number or items that are no list are read as `""`, 0 and `[]`); the migration to schema 12 did the same for the accounts restored before it. A purchase adds one default loadout (`<handle>'s Loadout #<n>`, `n` counting the account's loadouts, `color` 0, no items) for each unit of item 811, the loadout slot the store sells, that is delivered: bought alone or in one of its bundles, by `Inventory/buy` or the website's store, or granted by the admin.

On a community server, with the player's Bearer token, on API v2 and at the same path under `/v1` on the game's web host:

| Call | Answer |
|---|---|
| `GET /game/user/loadout` | `[{name, color, items: [{slot_id, item_id, item_guid}], id}]`, ascending by `id`, `[]` for none: `application/vnd.game_data.user.loadout+json; type=collection` (`application/json` under `/v1`). `item_guid` is the dog's (slot 29) and null for every other item |
| `PUT /game/user/loadout/<id>`, `{name, color, items: [{slot_id, item_id, item_guid}]}` | Replaces all three of the account's loadout and answers 200 with it in the `GET` shape; the inventory is not touched. The body is read as JSON whatever its content type (the page sends `json`). `name` is 2 to 50 characters, `color` 0 to 11, `items` at most 200 entries, each with a whole `slot_id` of at least 1 but not 23 (the placed items' slot), a whole `item_id` of at least 1 and an `item_guid` that is absent, null or a whole number; any other body is 400 and changes nothing. A loadout the account has not (another player's, an unknown id) is 404, a request without a valid token the expired-token reply ([Accounts](#accounts)); on `/v1` a 404 is `{"errorCode": 404}` with status 200 |

The page's CORS preflight for either call is the replay's, with the headers it asks for allowed.

A non-zero `loadout_id` of `Launch/start` or `POST /v1/session/start_single_player` that is one of the account's loadouts is put on in the launch's transaction, before the connect, as the in-game page does when a loadout is clicked: every owned item goes to slot 0 except a placed one (slot 23, which no loadout lists); then each entry in order takes the owned row of its `item_guid` (a dog), else the first row of its `item_id` still in slot 0, and gives it the entry's `slot_id`. An entry with no such row, or with a slot below 1 or 23 (a restored loadout may have one), is skipped and the others still apply. While the connect template has `inventory.active_services.UNLIMITED_AMMO` set, an ammunition entry (catalogue category 3) with no free row clones a row the account owns of that item (a full stack), so one ammunition fills several slots. The slots stay after the hunt: they are the equipment last saved. A `loadout_id` of 0, of another account's loadout or of none changes nothing. A tutorial (`start_tutorial`) puts none on.

## The store catalogue

`GET /catalog/store` on `web_host`, community server only (a local server answers the miss reply), public and without a cookie: the website's server calls it over `SERVER_URL` ([docs/website.md](website.md#sign-in)) and the launcher on the public domain, where the reverse proxy routes `/catalog/` here ([docs/deploy.md](deploy.md#the-community-server)). It is the same for everyone. The answer is `{categories: [{key, name, children: [{key, name}]}], items: [{id, name, variant, description, category, ems, was, gms, buyable, unlimited}], bundles: [{id, name, description, price, buyable, items: [{id, name}]}]}`, made from the application catalogue the server loaded ([Starting data](#starting-data)):

- **Items**: those that are not hidden. `category` is the key of the item's sub-category. `ems` is today's em$ price: the item's first row in the recorded `Application/discounts` takes its percentage off while it is active, the rule `Inventory/buy` charges by; `was` is the em$ price before it (null without a discount, and always null when no discounts are recorded). `gms` is the catalogue's gm$ price rounded to a whole number, **never discounted** (a discount is a percentage of the em$ price only, and the original's store showed and charged the gm$ price as the catalogue has it); it is 0 for an item with no gm$ price. `buyable` is false for an item that is `notbuyable`, is a service (`Inventory/buy` does not sell services either), or has neither an em$ nor a gm$ price of at least 1 (the starter items cost 0); an item sold for one currency only has 0 as the other price. The catalogue's inventory weight is not in this list; the item's page has it as `capacity` (below).
- **Categories**: a category's key is a sub-category's, and a top-level one is keyed by its default (first) sub-category, the way the store links to it, so its page lists only that sub-category's items; `all` is the first. One with no item left (the store's own link to its bundles) is left out. An item whose sub-category no category lists is only in "all".
- **Bundles**: the price rounded to a whole number, the items named from the catalogue, a hidden item too (an unknown id keeps an empty name). `buyable` is false for a bundle whose price is below 1 or that lists an item the catalogue does not have, or a license while `all_licenses` is on ([Licenses](#licenses)): [buying](#buying-from-the-website) refuses it.
- **Unlimited ammunition**: while `unlimited_ammo` is on, an ammunition item (category 3) has `unlimited` true and `buyable` false, and a bundle that lists one is not buyable ([Unlimited ammunition](#unlimited-ammunition)); `unlimited` is false for every other item, and always when the setting is off.

Only a recorded `Application/application` has categories and bundles: a catalogue built from the install alone has the items and empty lists for the others, and one with no item answers 404 `{"error": "no catalogue"}`. A recording is found by the host names of the settings (`api_host` and the others): with names that differ from the recording's, the server does not see it and falls back to the install. The reply is some 0.7 MB for a catalogue of about a thousand items, so the website keeps it for 5 minutes. It is built from the catalogue and the discounts, not replayed: a recorded discount that is still active (a free week, for example) shows as the item's price until it ends.

### An item's page

`GET /catalog/item/<id>` on `web_host`, community server only, public and without a cookie, for an item the store lists (a hidden or unknown one answers 404 `{"error": "no item"}`). It holds what the item's page shows beyond the list, which would make the list ten times larger if it held it for every item; the website's server and the launcher ask for it when a page opens. The answer is `{capacity, contents, fits, ethical}`:

- `capacity` is the catalogue's inventory weight divided by 1000, the number the store shows as the capacity cost (it has no unit); 0 for an item without one. `contents` is `{count, name}` for an item the catalogue gives units (a pack of cartridges, a refill of uses), else null.
- `fits` is `[{title, key, items: [{id, name, variant}]}]`: the items of the catalogue's `fit` lists, one entry per group, under the title of the category of that number and its `key` (the store's key of that category, as `GET /catalog/store` names it; the clients translate the title by it) (a weapon lists its sights and its ammunition, an ammunition and a sight the weapons). A hidden item, which has no page, is left out; a catalogue built from the install alone has no `fit` lists.
- `ethical` is `{ammo: [{id, name, variant}], species: [{id, name, permitted: [bool]}]}` (`id` is the species' id, for the client to name it in the player's language) for a weapon (over the ammunition that fits it) and for an ammunition (over itself), else null: one row per species of the catalogue that has permitted ammunition (the dogs have none, so no row) and one flag per ammunition. The flag is the rule [kills are judged by](#scoring-and-paying-a-harvest): the ammunition is in the species' `ethical` list (a non-typical variant uses its species' list), or is one of the event's silver ammunitions, which every species permits. The page and a hit's verdict read the same code, so they cannot differ.

## The launch map

`GET /catalog/reserves` on `web_host`, community server only (a local server answers the miss reply), public and without a cookie, from the application catalogue the server loaded ([Starting data](#starting-data)): the reserves and start places of the facts file, and the catalogue's tutorials. The launcher's map reads it. The answer is `{reserves: [{id, name, starts: [{id, kind, name, x, y}]}], tutorials: [{id, name, reserve}]}`; one with no reserve answers 404 `{"error": "no reserves"}`.

- **Reserves** are the catalogue's, in its order (the 12 of the facts file). A reserve with no start has an empty `starts`.
- **Starts** are the catalogue's `locations` of the types `LODGE`, `CAMPSITE`, `HUNTING_TOWER` and `INTEREST`, by id; `kind` is `lodge`, `campsite`, `tower` or `interest`. `id` is the location id, the number `POST /auth/launch` takes as `lodge`. A start's name is the location's `name`, else its `name` in the connect's `locations_descr` (the texts the game shows by location id), else the kind and its number in the reserve (`Lodge 1`, `Tower 3`). The hunt history uses the same names: the website's rows and hunt page show the name of the start the hunt opened at, and the game's `Expedition/list` carries its `location_id`, which the game resolves through the same `locations_descr`.
- **Position**: `x` and `y` are percent of the reserve's map picture (`map-<NN>`, [images.md](images.md)), 0 to 100 from the left and from the top, with two decimals. The picture covers the box of the facts file's `reserves[].map` (world `x` and `z` of its left, top, right and bottom edges), world `x` runs to the right and world `z` down, so a start at world (`x`, `z`) is at `(x - left) / (right - left)` and `(z - top) / (bottom - top)`, times 100. A start outside the box gets a value below 0 or above 100 (the map does not show it). A reserve with no usable `map` (missing, not four numbers, or an empty box) has the square around its starts instead: its side is the larger spread of their world `x` and `z`, plus a quarter of that for a tenth of margin on each side, centred on the middle of the starts, and a reserve whose starts all stand in one place has them at 50, 50; the picture is not cut to that square, so the starts are right relative to each other only.
- **Tutorials**: the catalogue's `id`, `name` and the `reserve` the tutorial runs in.
- **Placed items**: `GET /account/placed` on `web_host`, community server only, with the session cookie, lists the signed-in player's own placed items the map shows (401 when signed out; another player's are never listed): `{items: [{id, reserve, kind, name, x, y}]}`, one for each item in slot 23 ([Placed items and stacks](#placed-items-and-stacks)) that has a position and a reserve and whose catalogue `define` is a tent (`TENT`, `TENT02` ...), an electronic caller, a ground or waterfowl blind, a tree stand, a tripod stand, a deployable hunting tower or climbing gear (`CLIMBING_GEAR`, the ropes of the cliffs). `id` is the item's guid, `reserve` the web's reserve number, `kind` `tent`, `caller`, `groundblind`, `treestand`, `tripod`, `deployabletower` or `climbing` (from the define, never from the name), `name` the catalogue's name (else `Tent`, `Caller`, `Blind`, `Stand`, `Tripod`, `Tower` or `Rope`), `x` and `y` percent of the reserve's map picture as for a start, from the item's position. Other placed items (feeders, decoys, targets) are not listed. The launcher draws each kind with its own picture ([images.md](images.md)).

`GET /account/loadouts` (below) lists the player's saved loadouts for the picker.

### A hunt at a tent

A placed tent is a permanent start of its player, a place to begin a hunt next to the lodges. The original's launch map listed the player's tents with the lodges, and picking one sent `Launch/start` `{start, loctype, reserve, time, loadout_id}` as for a lodge, with `start` the tent's item id (its guid), `loctype` the item's own `define` (`TENT`, `TENT06` ... where a lodge sends `LODGE`) and `reserve` the reserve it stands in. The game needs no other field to begin there: the connect reply's `expedition` holds the spawn pose, `x`, `y`, `z` in metres (the game uses it when `x` and `z` are both not 0) and `dir_x`, `dir_y`, `dir_z` in per mille, and the game reads its reserve from `lodge` as `lodge / 100`. Before schema 21 this server handled no start but a lodge's location number.

- **Launch**: `POST /auth/launch` takes `tent` (a guid of [`GET /account/placed`](#the-launch-map)) in place of `lodge`, and `Launch/start` takes a tent's define as `loctype` with the guid as `start`. The server checks the item, not the digits of the `loctype`: it must be the account's own, a tent (its `define` is `TENT`, then digits, as in `TENT06`; the heated tents are `TENT` and a number too), in slot 23 and placed in `reserve`. `POST /auth/launch` answers 400 and opens nothing for any other item, a tent of another reserve, a tent that is not placed, and for both a `lodge` and a `tent`; `Launch/start` opens the hunt with no start, as it does for any start that is nothing.
- **Record**: the hunt keeps the tent's guid (`expeditions.tent`, schema 21) and its location is the reserve's first location number, `(reserve - 1) * 100`, because the game reads its reserve from it; the hunt history names that first start of the reserve. No `Start at` objective of a lodge is met at a tent.
- **Connect**: the reply's `expedition` has `x`, `y`, `z` the tent's position (metres, the row's millimetres divided by 1000), `dir_x`, `dir_y`, `dir_z` its direction (the row's, already per mille) and `lodge` that location number. A tent picked up after the launch is no start any more: the connect then answers the location's pose, as for a hunt from the catalogue's start.

## Multiplayer

The game plays multiplayer peer to peer: the joiners connect straight to the host's PC over UDP, and animals, shots, chat and kicks run between the games. The server never relays any of it. It creates the session, says in each player's connect reply who the host is and where it is, learns the host's port and network id from the heartbeat, and lists the open sessions. Each player keeps their own heartbeat, so kills, scores and missions stay per player. A session lives in memory (`Games` in `Multiplayer.cs`) and ends with its host; there is no table and no schema change. Community server only: a local server has none.

| Call | Host | Answer |
|---|---|---|
| `POST /v1/Launch/start_mp` | API | The caller hosts a session and a hunt opens as at `Launch/start`: `start` and `loctype` (a lodge, or a tent's define with its guid as `start`), `reserve`, `time`, `loadout_id`, and the session's `name` (up to 25 characters; default `<handle>'s game`), `description` (255), `public_game` (0: friends only, otherwise anyone), `free_players`, `hs_min`, `hs_max` (a hunterscore range, at most 99999), `password` (20; none is open), `max_players` (2 to 8; default 8). The reply is `Launch/start`'s: `{access_token, refresh_token, session, status: "ok"}`. |
| `POST /v1/Launch/join` | API | The caller joins the session `network_id` of the list: `start`, `loctype`, `loadout_id`, `password`, and `time` (default: the host's). The hunt opens in the session's reserve. The reply is `Launch/start`'s, or with HTTP 200 `{"errorCode": 23, "message": "USER_CANT_JOIN"}` for a wrong password, a full session (the host counts), a friends-only session of a player who is not the host's friend, a hunterscore outside the range, the host's own session (`own_game` at `/auth/launch`), an unknown or ended `network_id`, and a session whose host has not reported its port yet. |
| `GET` or `POST /v1/Network/list` | API | No token (the original refuses one); the same list is `GET /catalog/games` on `web_host`, the one the reverse proxy reaches. The open sessions, oldest first, as the original lists them: `[{id, name, handle, host, description, password: bool, public, singleplayer: false, freeplayers, hs_min, hs_max, max_players, start_ts, clients_len, clients: [{user_id, handle, guid, color, avatar, x, y, z, hunterscore}], reserve: {id, define, name, species, border}}]`. `id` is the `network_id` of `Launch/join`. `guid` is the member's network id as decimal text and `color` its `rrggbb`, both empty until its heartbeat event 29; `x`, `y`, `z` are the host's `player_positions`, 0 until the first. There are no `country_code` and `continent_code`, `species` and `border` are empty, and `description` is null when empty. |
| `GET /stats/game` | web | Public like `/stats/online`. `{"build": n}`, the `game_build` setting (`null` when unset), sent with `Cache-Control: public, max-age=300`. The launcher compares it with the installed game's build id. |
| `GET /stats/online` | web | No token, no cookie; the reverse proxy reaches it ([deploy.md](deploy.md#the-community-server)). `{"players": n, "games": m}`, counts only, never a handle: `players` the accounts with a hunt open and a heartbeat in the last `HEARTBEAT_TIMEOUT` (120 s; a banned account and the recorded player's are not counted, as for the `online` of [Public reads](#public-reads)), `games` the open sessions of `Network/list`. The server counts at most once in 30 s and sends `Cache-Control: public, max-age=30`. It reads each account's hunts on its own connection (`State.OnlineCounts`), so a count costs one query per account. |
| `POST /v1/Map/locations` | API | `[{id, define, name, description, reserve, type, pos, metadata}]`: the catalogue's locations of the reserve of the session `network_id` (else of `reserve`; `[]` for neither). The world items placed in the session are not listed. |
| `POST /auth/launch` with `mp` | web | The same two calls for the launcher and the website's start page, see [Sign-in and tokens](#sign-in-and-tokens). |

**The connect reply.** The `session` of `start_mp` or `join` is the token the game connects with (`X-Hun-Session`), and its `network` says what the player is. Any other connect, a single-player hunt among them, keeps `"singleplayer": true` and sends no `ip`.

- **Host:** `{"singleplayer": false, "host": H, "user_id": H, "handle", "ip", "max_players": N, "clients": null}`. `ip` is the address the connect came from.
- **Joiner:** the same with `user_id` the joiner's and `"clients": [{"user_id": H, "handle", "ip", "port", "guid"}]`, the host as the one client: its `ip` is the address of the host's connect, `port` and `guid` (a string) its heartbeat event 29's. A joiner's game connects to that address directly, or through the punch-through server first.
- **Address:** the peer's, or from a `trusted_proxies` peer the last address of `X-Forwarded-For` ([Behind a reverse proxy](#behind-a-reverse-proxy)). A host and a joiner on one LAN must reach the server by its LAN address (the launcher's `server_url`), so that the host's connect is seen from its LAN address and not from loopback. The address is sent as the server saw it: for a host whose connect reached the server over IPv6 that is an IPv6 address, which a joiner's game may not be able to use.
- **Punch-through:** `config.nat.pt_server` of the connect template is `nat_host` (else `web_host`) on UDP 10000 (`Install.Connect`), where the `natpt` container runs ([server/natpt](../server/natpt/), [deploy.md](deploy.md#punch-through-server)): a RakNet punch-through server, so a joiner behind a home router reaches a host without a forwarded port. It is never the game host's name, which the player kit maps to loopback. The name must resolve, because one that does not hangs the game's start; with nothing answering, the game waits about 30 s, then joins directly (UPnP or a forwarded port). The game has no relay: strict NATs may still fail. A recorded connect reply of a community server gets the same address.

**The heartbeat.** Event 29 `{port, guid, color}` stores the player's port (1 to 65535), network id (an unsigned 64-bit number) and colour (6 hex digits). A port or network id that is not valid ignores the event; a colour that is not valid is stored as empty. A host's session can be joined once its event 29 came (the game sends it with its first heartbeat, after the connect). Event 30 `{guid}` (a joiner could not connect to the host) removes the sender from the session when `guid` is the host's. The host's `player_positions` set the members' `x`, `y`, `z`. Every heartbeat keeps its sender in the session.

**The end.** A player's own `disconnect`, a `Launch/start`, `start_single_player` or a tutorial of the same account, a `Launch/start_mp`, a `Launch/join` that is accepted, and 120 s (`HEARTBEAT_TIMEOUT`) of silence after the first heartbeat remove it; a game that sends none is removed after 10 minutes (`Games.Grace`). When the host goes, the session ends and a joiner's next connect is a single-player one.

## Licenses

The original sold a license to hunt a species (1, 7 or 28 days) and licenses of the reserves; the catalogue's item type of them is `LICENSE` (the facts file's `types`, number 13; their slot is the lodge's, 0). With `all_licenses` on (the default) every player has all of them, without end, until the operator sets it to `false`:

- **Connect:** every entry of `spawn_licenses` other than 2 becomes 1 (licensed), so the game shows no "need license" notice and refuses no kill; an entry of 2 (the species is not available) stays 2. The admin spawner still sets its own species to 1.
- **Inventory:** the connect reply's `inventory.items` lists one lodge-slot row (no units) of every license item the catalogue or the install's definitions have, with its definition in `infos`, in place of the account's own license rows; `GET /account/inventory` lists the same rows with `expires` 0, which the store shows as "You have an unlimited license" with no buy button.
- **Buying:** `Inventory/buy` and `POST /account/buy` refuse a license as already owned (`{"success": false}`, 409 `refused`), nothing is charged. A bundle that lists one is not for sale: `buyable` is false in `GET /catalog/store` (the website shows its buy button disabled) and `POST /account/buy` refuses it.

With it off, a license is an item like any other: sold, owned by the rows the account has, its `spawn_licenses` as the connect carries it.

## Unlimited ammunition

The original's unlimited-ammo service gave a player every ammunition without limit. With `unlimited_ammo` on (the default) every player has it, until the operator sets it to `false`:

- **Connect:** every connect reply (single player, multiplayer and tutorial) has `inventory.active_services.UNLIMITED_AMMO` set to the integer 1, which switches the game's mode on: the lodge and tent inventory show every ammunition with an infinity badge. The other services (`UNLIMITED_FUEL`, `STREAK_PROTECTION`) stay as the connect has them.
- **Hunt start:** every launch ([The free ammunition](#starting-data)) first decides which lodge stacks the game is shown: of the lodge's stacks of one ammunition (older free boxes, a restore) only the oldest; the others stay in the database, marked hidden (metadata key `__hidden`), and are left out of the connect, `Inventory/list` and `Inventory/dict` (`GET /admin/inventory` lists them), and a request naming one (a slot in `Inventory/move_multiple2`'s `mapping`, an event 6, 8, 23, 25 or 33) changes nothing. Nothing is deleted: the launch clears the previous marks before its loadout is put on (the loadout may take any box) and sets them again after it, so with the setting off they are the game's again at the next launch (the website's inventory lists every row). It then fills every ammunition stack the account owns (catalogue category 3, with units), of any type, to a full box in the launch's transaction, before the connect; a larger stack is never lowered. The free ammunition is topped up to one box instead of `boxes`.
- **Ammunition of the weapons the player owns:** as ammunition is not sold, the same launch gives the account one full box, a row of its own listed in the connect that follows, of every ammunition that fits a weapon it owns and has no row yet, so no weapon is without ammunition in the lodge. What fits a weapon is the `fit` list of the ammunition category in the catalogue, or, when the server has no recorded catalogue (or the list is empty), the ammunition among the attachments of the weapon's install definition: the rule never depends on `api_host` or the recordings. An ammunition the game has no definition of (neither a recorded one nor the install's ballistics) is left out: the game closes after the connect for an item it cannot define. An equipped weapon (slots 2 to 4) whose ammunition slot (the weapon's slot plus 6, so 8 to 10) is empty gets a copy of its first fitting ammunition in that slot, marked as a copy like a box the page copied ([Boxes at a lodge or tent](#unlimited-ammunition) below), so the lodge keeps its own stack: a weapon raised with an empty ammunition slot closes the game at the first shot ([#608](https://github.com/yinyin99/hunter-resurgence/issues/608)). A weapon whose slot has an ammunition is left alone.
- **One lodge stack of every ammunition:** last, the launch gives the lodge (slot 0) a full box of every ammunition the account owns that has no row there, also when its only box is equipped or in the backpack: the page lists and copies only what the lodge holds, and copies a stack only when it is the only one there, so the lodge shows each ammunition once as the infinite stack. A launch adds it once, marked as a copy, so the launch after the player put another box of it back into the lodge removes it again; a stack the player already has in the lodge is never duplicated.
- **Boxes at a lodge or tent:** the infinity badge stays on the lodge's stack and the page copies it: dragging it into the backpack or choosing it for a weapon's ammunition slot leaves the stack in the lodge and puts a copy under a placeholder guid (`new_item_<ms>`) where the player dropped it (the page copies only while the lodge holds exactly one stack of that ammunition; while it holds more, a drag moves one of them, until one is left). When the inventory closes or a tab changes, the page sends `Inventory/move_multiple2` with the placeholders in `clonedItems` and every item's slot in `mapping`, and expects `{"<placeholder>": <integer guid>}` (or `null`) back. It then gives each copy that guid, tells the game about the stack (item, guid, slot, units) and only after that updates the game's slots with every item's guid; a guid the game was never told about empties the slot it is put in, and a shot with an empty ammunition slot closes the game ([#608](https://github.com/yinyin99/hunter-resurgence/issues/608)). So each entry creates a stack of one full box, the catalogue's stack size whatever the request says, as a row of the account with a new integer guid (the account's highest plus 1, never above 2^31 - 1, a number the game can hold), and the reply maps each placeholder this request created to its guid; the next connect has the rows. Only a catalogue ammunition the account already owns (with a stack size) is created, and not past 100 rows of one ammunition: an entry for any other item, a name that is no placeholder, or while unlimited ammunition is off, creates nothing. A placeholder that already has its box (a tab change and a close can overlap and the page asks twice) creates nothing and is not in the reply, because the page replaced the placeholder when it got the first answer and stops at a key it no longer knows; the entry's slot in `mapping` still applies to that box. The account's copies and its row count per item are read once per request, and only when it names a placeholder, so a request of any size is one pass under the write lock. A tutorial creates nothing and always answers `null` (its item numbers are not the account's). A copy is marked in its row (metadata key `__clone`, never shown to the game, in `Inventory/list` or `Inventory/dict`), and a launch removes a marked box in the lodge when an older row of the same ammunition is in the lodge too, so boxes taken out and put back do not pile up; a copy in the backpack or in a weapon stays, and the launch fill above fills it like any stack. A loadout's extra boxes at a launch (rows of the connect, which the game knows) are unchanged.
- **Refill by heartbeat:** the refill the game sends by event 6 with a negative `quantity` (used ammunition put back) stops at the item's stack size and never lowers a larger stack; an item with no stack size is not refilled by it. This holds whatever the setting is.
- **Buying:** `Inventory/buy` and `POST /account/buy` refuse an ammunition like a license under `all_licenses` (`{"success": false}`, 409 `refused`), nothing is charged; a bundle that lists one is refused as a whole. In `GET /catalog/store` such an item is `unlimited` and not `buyable`, and the website shows "Unlimited ammunition" and no buy button ([the store catalogue](#the-store-catalogue)). A grant by the admin API is not a purchase and still works.

With it off, ammunition is an item like any other: sold, used up shot by shot, and only the free ammunition is refilled at a launch. (A recorded connect that already carries the service keeps the loadout's extra boxes and the copies on, as before; the launch steps above follow the setting only, so such a server neither fills an equipped weapon's empty ammunition slot nor adds the lodge stacks.)

## Buying from the website

`POST /account/buy` on `web_host`, community server only, with the session cookie and the website's `X-Requested-With` (like the other `/account/` calls, [Upload a backup zip](#upload-a-backup-zip)); the website's server and the launcher send it, a browser page never does. The form is `id`, `count` (1 to 1,000, default 1), `wallet` (`GOLD`, the default, pays em$; `SILVER` pays gm$, the names of `Inventory/buy`) and `bundle=1` for a bundle:

- **An item** the store lists as buyable ([The store catalogue](#the-store-catalogue)) costs `count` times today's em$ price (`GOLD`), or `count` times its gm$ price (`SILVER`, the catalogue's `silver_price`, no discount). An item with no gm$ price of at least 1 is not sold for gm$, so it is never free.
- **A bundle** is one at a time, at its rounded em$ price (bundles have no gm$ price: `SILVER` refuses them), and gives one of each item it lists (a hidden item too); every item must be in the catalogue.

Neither path sells past the catalogue's ownership rules: an item with an `ownLimit` is refused when the player's copies (inventory rows) plus the purchase would pass it, and one whose `ownMultiple` is false when they would pass 1 (a bundle counts each of its items, and is refused as a whole). With `all_licenses` on, a license item is always over the limit ([Licenses](#licenses)). A one-use item (the catalogue gives it `units`: taxidermy and skull-mount orders, the bait-site refill) is exempt from the `ownMultiple` rule, because the original store never showed one as owned. `Inventory/buy` refuses with `{"success": false}` like a balance too low; the check is the original store's (its `STORE_ITEM_STATE_OWNLIMIT_REACHED`). A catalogue item without those fields has no limit.

The charge and the items are one transaction, the one `Inventory/buy` uses (it takes the same `wallet`): only the wallet paid is debited, the change is a row of that wallet's history (`wallet_log`, summary `In-game payment.`, so the totals spent count it), and a running game gets the items (update 10) and the new balance of that wallet (update 15, `em` or `gm`) with its next heartbeat, else the next connect carries them. The answer is 200 `{status: "bought", ems}` (`gms` for `SILVER`) with the new balance of the wallet paid, 409 `refused` for something not for sale, a balance of that currency too low or an own limit reached (nothing changes), 401 `signed_out`, or 400 `invalid` (not from our page, no number id or count, or a wallet other than `GOLD` and `SILVER`). `Inventory/buy` refuses with `{"success": false}` for a balance too low, an own limit reached, or an item that is `notbuyable`, a service or without a price in the wallet (a gm$ price below 1 is no price; unlike the website's call it also sells a hidden item, and an em$ price of 0), and answers `{price, success: true}` with the total charged.

## Sign-in and tokens

With `offline_mode` false (a community server) players sign in with Steam; the endpoints that act for a player need a token that resolves (recorded replies, archives, the mirror, the launcher's calls and the start page are public). With it true none of the following is on (the `/auth/*` endpoints, the start page, the launcher's calls and the replies that carry tokens are the replay's, as before). Steam's OpenID 2.0 needs no key. No Steam name, e-mail or address is read or kept: only the 17-digit Steam id, the handle the player picks and the game data.

**The sign-in, in steps** (always on `web_host`: a start on `signup_host` or `game_web_host` is first sent there; the origin is `https://<web_host>`):

Every page the player's browser sees is the website's ([docs/website.md](website.md#sign-in)); the server answers its sign-in routes with redirects to `/signin/<step>` (`handle`, `confirm`, `done`, `problem?reason=<key>`: a fixed path on `web_host`, never an address a request names) and with no HTML but the launcher's start page. A sign-in started on another host (`signup_host`, `game_web_host`) first redirects to the same path and query on `web_host`, so the browser always finishes on our site. A refused request (a login that ran out, a form without its token or from another origin, Steam not confirming, a banned account, an invalid app link) is a 302 to `/signin/problem?reason=<key>`, no longer a 4xx page; nothing changes in those cases.

1. The browser opens `/auth/steam/login?next=<local path>`. The server keeps a login in memory (15 minutes), sets the cookie `hr_login` (`Path=/`, so the website's pages can read it too) and sends the browser to Steam with `return_to=https://<host>/auth/steam/return?login=<id>`.
2. Steam asks for the password and sends the browser back. The server needs the `hr_login` cookie to match `login` (another browser or a replayed URL fails), then asks Steam to confirm (`check_authentication`) and accepts only an assertion that Steam confirms, whose `return_to` is exactly its own, whose `op_endpoint` is Steam's, whose `claimed_id` is `https://steamcommunity.com/openid/id/<17 digits>` and equals `identity`, whose signature covers `op_endpoint`, `claimed_id`, `identity`, `return_to`, `response_nonce` and `assoc_handle`, with no repeated `openid.*` field, and whose `response_nonce` is at most 5 minutes old (or ahead) and not seen before (kept in memory).
3. A known Steam id gets a session: the cookie `hr_session` (HttpOnly, Secure, SameSite=Lax, 30 days; its SHA-256 is in `web_sessions`, a table of its own, so a cookie is never a game token and a game token never a cookie) and a redirect to `next` (a local path; anything else becomes `/`).
4. A new Steam id is sent to `/signin/handle` (`GET /auth/handle` redirects there too), where the player picks a handle; the page reads `GET /auth/pending` (see below) and posts the form to `POST /auth/handle`; a refused form keeps what was typed (the name cut to 30 characters, the old name to 50) and a reason key (`invalid`, `taken`, `unknown`, `old-taken`) in the login and redirects back to the page, which shows both. (Steam gives none we keep). When the server has an archive ([Archive claims](#archive-claims)) the page also offers "I played before": the player types the old hunter name and may leave the new name empty to take the old one when it is free (else "Choose a name: the old one is taken."). The old name is looked up before any account exists, and it costs no daily lookup (each try is one POST of one sign-in); an unknown name shows the page again, "We did not keep a profile under this name.", and creates nothing. Otherwise the account is created as below, then the claim runs at once with the account's confirmation (`Claims.Claim`, the same rules: restored, or kept for the operator from hunterscore 10,000) and the player's inbox tells which. Without an archive the page only asks for the name. The account is created with the next user id of the server's range (below) and the server's starting data, then step 3. Two tabs of one sign-in make one account.

**`GET /auth/pending`** (the website's step pages read it; needs `X-Requested-With` and the browser's `hr_login` cookie) answers 200 `{step: handle|confirm|app, csrf, ...}` (`handle`: `offer`, `handle`, `old`, `restore`, `error`; `confirm`: `handle`, `code`; `app`: `handle`) or 404 `{status: expired}`; `csrf` is the token the step's form posts back. It changes nothing; a cross-site page cannot read it (no CORS, a `SameSite=Lax` cookie, a JSON type with `nosniff`).

**The launcher's start page** is `GET /` on `signup_host` (the launcher loads it with `#/launcher/start`; the hash never reaches the server). The old launcher's browser (Chromium 25, TLS 1.1) cannot be expected to load Steam's pages, so the page signs in through the player's own browser, in the style of a device code: the page asks `POST /auth/link` for a code and opens `https://<web_host>/auth/steam/login?link=<code>` with `ewlauncher.openURL` (the page is restyled with the website's colours and type in CSS the old browser reads: no grid, variables or flex gap, ES5; the in-window sign-in link is gone, since Steam's pages do not load there). `POST /auth/link` answers `{code, userCode, url, expires}`: the code lives 600 s, and `url` always points the browser to `https://<web_host>/auth/steam/login?link=<code>`. The player's browser runs steps 1 to 4, then `/signin/confirm` shows the code `ABCD-EFGH` and "Sign in the app that shows this code?" (the first 8 characters of the code); the player confirms, and the launcher, polling `GET /auth/link/<code>` every 2 s, gets `ok` with the `hr_session` cookie once and reloads. The confirmation matters: without it, anyone could send a victim a link made from their own code. Signed in, the page shows "Play": `POST /auth/launch` returns `{"url": <launch URL>}`, and the page calls `ewlauncher.startGame(url)`. The page is plain HTML and ES5, English only.

### The loopback sign-in

The launcher and the backup tool sign in as native apps do (RFC 8252 loopback redirect, RFC 7636 PKCE), on `web_host`, `signup_host` or `game_web_host`; the answer can only reach the PC that started the sign-in, so the player compares nothing and a sign-in link sent to someone else gives the sender nothing. The code link above stays for the start page.

1. The app makes a random `verifier` (43 to 128 URL-safe characters), its `challenge` (SHA-256 of the verifier, base64url without padding: always 43 characters), a random `state` (16 to 128 URL-safe characters), and listens once on `127.0.0.1` on a free port.
2. `GET /auth/app/start?challenge=<challenge>&port=<port>&state=<state>` in the player's browser. The server refuses (a 302 to `/signin/problem?reason=app`, no login started) a challenge that is not 43 base64url characters of 32 bytes, a `port` that is not a whole number from 1024 to 65535 and a `state` of the wrong length or characters. Else it starts a login as at `/auth/steam/login` (Steam, the name at the first sign-in), bound to the challenge, the port and the state.
3. The player confirms on `/signin/confirm` ("Sign in the app on this PC?"), which posts `/auth/confirm` (the same CSRF token and `Origin` rules as every form). The server then makes a one-time code (32 random bytes, hex), keeps it with the account and the challenge for 3 minutes (`Lifetimes.AppCode`; at most 10 000 live, the oldest goes first), and redirects the browser to `http://127.0.0.1:<port>/?code=<code>&state=<state>`. The host is a literal and the port a validated number: the redirect never goes to another host. A second confirmation of the same login makes no second code.
4. The app answers the browser a short page "Signed in, you can close this tab" only for a request whose `state` is its own (any other request gets a refusal and the app keeps waiting), then `POST /auth/app/exchange` with the form `code` and `verifier` and the header `X-Requested-With` (or a same-origin `Origin`). A request that is not from our own page gets 400 `{"error": "not from a page of this server"}`. A verifier that is not 43 to 128 URL-safe characters is refused next, and the code stays. Else the server removes the code, so every try with a good verifier spends it, then checks the lifetime and that SHA-256(`verifier`) equals the stored challenge in constant time. A good exchange answers 200 `{"status":"ok"}` with the same `hr_session` cookie as the code link (the app keeps it, the launcher in `session.dat`); anything else answers 400 `{"status":"invalid"}`, whatever the reason.

The server logs the path only, never the query or the form.

**The launch URL** is `<scheme>://<game_web_host>/<session>/lang/en_US/access_token/<access JWT>/refresh_token/<refresh JWT>` ([The current build](#the-current-build)), three fresh tokens of the signed-in account; the scheme (`ProtocolLiterals.LaunchScheme`, the one literal that names the game) carries the name the client's environment check looks for anywhere in the URL. `game_web_host` must not contain `dev` or `beta` (the same check).

**`POST /auth/launch`** needs the session cookie and a page of this server (a same-origin `Origin`, or `X-Requested-With`), and answers `{"url": <launch URL>}`. Without a form it is only the URL, as the start page sends it. With a form it first opens the hunt, as `POST /v1/session/start_single_player` does, through the same step (`State.NoteLaunch`: it closes any open hunt, opens a new one, sets the mission state and puts the loadout on): `reserve` and one of `lodge` (a start of [The launch map](#the-launch-map)) or `tent` (the guid of one of the player's placed tents in that reserve, [A hunt at a tent](#a-hunt-at-a-tent)) are required, `time` (minutes after midnight, 0 to 1439; the hunt's connect carries it as `expedition.start_time`; schema 16, `expeditions.start_time`; as `start_single_player` and `Launch/start` do with their `time`; absent or out of range: the recorded time) and `loadout` (a loadout id of [Loadouts](#loadouts), 0 or absent for the equipment last saved) are optional, each a whole number; anything else is 400 `{"error": ...}` and opens nothing. The launcher sends it when the player picks a reserve and a start. A form with `tutorial` (a tutorial id of the map, 0 is the first) opens that tutorial's session as `start_tutorial` does, with no hunt, and answers a launch URL whose session is that tutorial's; an unknown id is 400. 401 when signed out.

**Multiplayer through `POST /auth/launch`**: the form's `mp` is `host` or `join` (any other value is a 400). `mp=host` takes the fields of a hunt (`reserve`, `lodge` or `tent`, `time`, `loadout`) and the session's own (`name`, `description`, `public_game`, `free_players`, `hs_min`, `hs_max`, `password`, `max_players`); `mp=join` takes `network_id`, `lodge` or `tent`, `loadout` and `password`, and no `reserve` (the session's is used) and, unless it sends a `time`, the session's time. Both answer `{"url"}` as above, the URL's session being the one the game connects with. A refused join is a 400 `{"error": "password" | "full" | "not_allowed" | "own_game" | "host_not_ready" | "gone"}` ([Multiplayer](#multiplayer)) and opens nothing.

**Tokens** (all in `tokens`, hashed; every token resolves everywhere: the lifetimes limit a leak, they are not different powers):

| Token | Handed out by | Lifetime |
|---|---|---|
| session (`X-Hun-Session`) | `Launch/start`, `Launch/start_mp`, `Launch/join`, the start page | 7 days |
| access (`oauth_access_token`) | `Launch/start`, `Launch/start_mp`, `Launch/join`, the start page, `Oauth/token` | 1 day |
| refresh (starts with `r`) | `Launch/start`, `Launch/start_mp`, `Launch/join` | 30 days; the only ones `Oauth/token` renews; `Oauth/token` (`oauth_refresh_token`) returns a new access token and the same refresh token |
| JWT (`Bearer`) | `User/jwt`, on the game host and the API host, for the `oauth_access_token` of its JSON or form body | 30 minutes; three dot-separated parts whose payload has `sub`, `iat` and `exp` (the client reads `exp`); the third part is random, not a signature |
| access JWT (`Bearer`, `oauth_access_token`) | `/auth/jwt/refresh`, the launch URL ([The current build](#the-current-build)) | 900 s; HS256-signed, kept in `tokens` |
| refresh JWT | the same, the cookie | 30 days (7 days when the photo uploader asks with its placeholder and the session); renews only through `/auth/jwt/refresh`; not rotated (the game may keep presenting the one of its launch URL), so it ends with its 30 days, a ban or a delete |
| web session cookie | the sign-in | 30 days |

Expired rows are deleted at startup. `Launch/start`, `User/jwt` and `Oauth/token` answer a request without a valid token as every other state endpoint does (the expired-token reply).

**The launcher's own calls** (`EmoteLauncher/token`, `initialise`, `compatibleHardware`, `ping`, under the game host) are answered without recordings: `err` 0, placeholder `access_token` and `refresh_token` (the launcher only needs them to be something other than `"0"`), no files to download, `compatible` 1. The Steam session ticket that `token` receives is not checked: checking it takes a Steam Web API key (Valve's documentation asks for the game's publisher key, and one page also allows an ordinary key on the public host, rate limited), and the server runs without any key, so any client could send any ticket. Signing in is the browser's Steam sign-in above.

**User ids**: an account of the server's own gets the next id from 2,000,000,000 (`Store.FirstServerId`) to 2,147,483,647 (int32, the game's width); ids that come from a backup are below that, so they never collide. The allocation and the insert are one step under a lock (one server process, [ADR 0001](adr/0001-sqlite-for-profiles.md)). A restore that brings a user id and handle replaces the id and handle of an account that has not played (no row in `expeditions` and `events`, only its starting rows); an account that has played keeps its id and takes only the handle ([ADR 0009](adr/0009-restore-a-zip-onto-an-account-that-has-played.md)). The rest of the account (Steam id, tokens, sessions) stays.

**`web_host` must be the website's public domain** (the website sends the host the browser used, and the server picks its sign-in by it); the game's own web host is `game_web_host`.

**Handles**: 3 to 30 characters, ASCII letters, digits, `-` and `_`, starting with a letter or a digit; unique whatever the case (`Handles.Problem`, the column is NOCASE).

**Endpoints** (the OpenAPI document `game` lists them): `GET /auth/steam/login`, `GET /auth/steam/return`, `GET /auth/pending`, `GET|POST /auth/handle`, `GET|POST /auth/confirm` (GET redirects to the website's page), `POST /auth/link`, `GET /auth/link/<code>`, `GET /auth/app/start`, `POST /auth/app/exchange` ([the loopback sign-in](#the-loopback-sign-in)), `GET /auth/me` (`{userId, handle, hunterscore, rank, avatar, ems, gms}`, the wallet in whole numbers and the avatar as in [Avatars](#avatars), or 401), `POST /auth/signout`, `POST /auth/launch`, on `web_host`, `signup_host` and `game_web_host`; `GET /` on `signup_host` and `GET /launcher` on `game_web_host` (the start page); `POST /auth/jwt/refresh` and `POST /auth/emotelauncher/token` on `game_web_host` only. A state-changing request must come from a page of the same origin: its `Origin` is the origin, or it has no `Origin` and carries `X-Requested-With`. The website reaches them through the proxy; the website's own use is in [website.md](website.md#sign-in).

A restart forgets the logins in progress (the player starts the sign-in again); sessions, accounts and tokens are in the database.

## Import a backup zip

```
dotnet run --project server/Server -c Release -- [--settings <file>] import backup <zip> [--account <id>]
```

Restores a [backup zip](backup.md) into `state.db` in `data_dir` and prints the report: what the reader found (restored, unsupported, missing, warnings), the rows stored per table, and what was dropped and why. It runs on its own, with no server running, and needs the recordings like `admin` does. Any zip is accepted, and it replaces the account's profile (items, wallet, skills, profile, statistics, achievements, trophies, lodges, loadouts, missions, challenges, saved replies); hunt history stays, no merge (only the friend edges of its lists are added to the ones the account has, [Friends](#friends)), and the server hunts still add to the restored statistics ([The statistics](#the-statistics)). When the account exists, the old database is copied first to `state.db.bak-<UTC time>`; the zip is kept as `restores/<account id>/<SHA-256>.zip`; importing the same zip twice gives the same rows (and a second audit row). The account is the zip's user id (created from the zip's handle when it does not exist), `--account <id>` names an existing one, and a local server (`offline_mode` true) restores into the local account, the one the game connects as. Exit code 1 for a refused zip, an unreadable file, a missing `--account` target or a handle another account has. The model, the dropped fields and what the server then answers from the rows are in [docs/restore.md](restore.md#storing-the-model).

```
dotnet run --project server/Server -c Release -- [--settings <file>] import pictures <zip> --account <id>
```

Restores only the pictures of a backup zip onto an existing account (refused when it does not exist), for an account restored before the server stored pictures that has played since: its items, wallet, skills and the rest stay as they are. It only adds: no picture of the account is removed, and a picture it already has (the same file hash) is not added twice, so a second run adds nothing. The gallery links the zip lacks a file for are read from the pictures an upload kept with the zip, or fetched now from the `picture_link_hosts` ([Pictures from links](restore.md#pictures)). It sets its avatar from the zip's profile ([Avatars](#avatars)) and prints the `pictures stored:` line (with `pictures from links: <ok> of <n>`) and the avatar link. The server may be running; the zip is kept under `restores/<account>/` like a restore's.

```
dotnet run --project server/Server -c Release -- [--settings <file>] admin gallery-details [--account <id or handle>]
```

Sets the details of the restored gallery pictures of every account that has kept zips (`restores/<account id>/*.zip`), or of one: the species, the score and the kill id a saved gallery entry holds (`photos.saved`, [Gallery](#gallery)), for an account restored before the server read the entry's `animal` object. It reads the kept zips (newest first) and the pictures already on disk, finds each picture by its file hash and rewrites its row's details; no picture is fetched, added or removed, and nothing else of the account changes. It prints one line per account, `<id> <handle> <n> of <m> gallery pictures updated`, and can be run again. It also re-applies the profile background and ribbon: an account with no saved v2 profile (`game_user_<uid>_profile.json` in `extras`) gets the newest kept zip's, and the line ends `, profile background restored`; items, wallet and the rest are not touched.

**Wallet floor.** Every restore (this command, an approved upload, [an archive claim](#archive-claims)) leaves the account with at least 15,000 gm$, the starting wallet's amount: a lower restored amount, or the missing wallet of a public zip, is raised to it, and the report says so. A higher one is kept. The same holds for the starting kit: each `start.items` id the restored items lack is added like a new account gets it (`start items added: <n>` in the report). The em$ are the zip's (0 for a zip without a wallet), except that a zip never takes the start em$ the account has not spent: an account that no zip restored before keeps up to 1,000 em$ (`Restorer.StartEm`) of its own balance when the zip holds less (`wallet: em raised from <old> to <n>`). Spent em$ are not given back, and a second zip replaces the first one's em$.

## Upload a backup zip

On a community server (`offline_mode` false) a signed-in player uploads their own backup from the website ([docs/website.md](website.md#restore-and-your-data)) or from the backup tool ([docs/backup.md](backup.md)). The website's server calls these endpoints over `SERVER_URL`, with the player's session cookie (`hr_session`), on `web_host` under `/account/`; the backup tool and the launcher call them on the public domain, where the reverse proxy routes `/account/*` to the server (with `/auth/`, `/hunters`, `/catalog/`, `/photos/` and the minigames' `/leaderboards/`, [docs/deploy.md](deploy.md#the-community-server)). Every route under `/account/` answers 401 without the session cookie, and every write also needs `X-Requested-With` or a same-origin `Origin`, else 400. An upload is never restored by itself: an operator approves it (below). With `offline_mode` true they do not exist (the replay answers), and `import backup` above is the local way.

**Limits.** Each request fits a proxy's 100 MB request limit: a body over 90 MiB is `413` (`too_large`) and is not read. A zip is at most 1 GiB: a part that takes it over is `413` and ends the upload. One upload at a time per account and four on the whole server, from the start to the finish (`429`, status `busy`); an upload that gets no part for 30 minutes is deleted and frees both (a later request for it is `404` `invalid`: start again). A new start, or a delete of the account, drops the account's upload that waits for its next part, so an interrupted upload can start over at once. The parts are joined in a file of `data_dir/uploads-tmp`, deleted when the upload ends (a file a stopped server left there is deleted 30 minutes after its last write); the finish reads the zip from that file, so memory stays bounded whatever the zip's size. The reader's caps apply (`Limits`: 1 GiB of content, 100,000 entries, 100:1 compression, JSON depth 64), so a zip bomb is `400` (`invalid`) before anything is parsed. Stored zips are limited (settings `upload_account_files`, `upload_account_bytes`, `upload_total_bytes`, `upload_min_free_bytes`; restored zips do not count): an account may store at most 3 zips for the operator (waiting plus refused, below) and 1 GB of them; the server at most 5 GB, and none when the data disk has less than 10 GB free. A start over the account's limits is `429` `quota` ("You have 3 backups waiting for the operator. You can upload again once the operator has reviewed them." or "Your backups waiting for the operator already use 1 GB."), over the server's `429` `paused` ("Uploads are paused for now, try again later."). The same checks run on every part (the received bytes may not pass what the account has left, nor the server's room or the disk's floor: the upload ends) and when the zip is kept; a quota keeps no file and sends no alert. The operator frees room with `review reject`; a player cannot remove a stored zip (only "Delete my data" deletes the account with its zips).

**Rules.** Every zip that the reader accepts is kept for an operator and never restored automatically. Whether the zip's Steam id is the one the player signed in with is shown to the operator as information, not as proof: anyone holding the zip can edit the field.

| The zip | Result | `status` |
|---|---|---|
| Not a zip, or refused by the reader (caps, unsafe names, not a backup zip, a claim key that does not match) | `400`, nothing kept | `invalid` |
| A user id that was restored before (by this account or any other) | Refused, nothing kept: "a backup can be restored once" | `already` |
| A user id another account holds | Refused, nothing kept | `taken` |
| Any other zip (ours, or another tool's: [restore.md](restore.md#backups-of-other-tools); the Steam id in our manifest is the only claim of ownership, so another tool's zip is never a Steam match) | Kept as `restores/<account id>/<SHA-256>.zip`, a row in `uploads`; nothing is restored. The gallery pictures the zip lists by link and does not hold are fetched first from the `picture_link_hosts` and kept beside it as `<SHA-256>.pictures.zip` ([Pictures from links](restore.md#pictures)). The player is told that an operator will check it | `review` |

When a zip is kept, the server also sends one message to the `review_webhook` of the settings file, if set: a `Backup waiting for review` alert (see [Discord alerts](#discord-alerts)). The refusals above (`already`, `taken`) are `409`. A user id outside 1 to 1,999,999,999 is kept like any other zip and refused when the operator approves it (below).

The reason of a zip that is readable but holds no backup (the reader's "not a backup zip") is what the player can act on, found from the entry names alone: `Your backup is inside another folder or zip: upload the backup zip itself` (a `.zip` entry, or a `manifest.json`, `index.json` or `ARCHIVE_MANIFEST.json` deeper than one folder), else `This zip holds a program, not a backup: upload the file the program made (it ends in _PRIVATE.zip)` (a `.py`, `.exe`, `.bat` or `.dll` file), else `This zip holds only pictures, not a backup` (only `.jpg`, `.jpeg`, `.png`, `.gif`, `.webp` or `.bmp` files); any other reason keeps `This file cannot be read as a backup: <reader's reason>. Nothing was changed.`

A zip that arrived whole but cannot be read as a backup (the two `invalid` rows above about the content, not a missing or short part, which the player just sends again) is also recorded: one `upload_results` row `kind = refused` with the reason, shown on the restore page as "Your upload of <date> could not be read" (the `decisions` of `GET /account/restore`, no inbox message), one `Upload refused` alert to the `review_webhook` (see [Discord alerts](#discord-alerts); its `kept` line is `r<account id>-<first 8 hex of the zip's SHA-256>`), and the file moved to `data_dir/refused/<account id>/<SHA-256>.zip` (its reason beside it as `<SHA-256>.reason`) instead of being deleted. It counts in the account's stored zips; the same bytes again are kept once; when a quota leaves no room it is not kept and no message is sent. It stays until the operator rejects it (`review reject r<account id>-<8 hex>`): nothing deletes it by time. "Delete my data" and the account's deletion remove that folder too.

Every outcome of an upload except a received part writes one console line, `upload of account <id>: <status>: <message>`: a zip refused by a quota keeps nothing, so this line is its only record (the reader's reason for `invalid`, which of the `busy`, `quota` and `paused` cases). On the VPS the console goes to the host journal ([deploy.md](deploy.md#logs)).

**Review.** The operator works the kept zips with the server's command line (no web page):

```
dotnet run --project server/Server -c Release -- [--settings <file>] review list | approve <id> [--keep-handle] [--account <account id>] | reject <id> [--account <account id>] [reason]
```

Upload ids are never reused (`uploads.id` is AUTOINCREMENT, from 100 at least on a database migrated from before). `--account <account id>` (the account in the alert) makes `approve` and `reject` refuse, changing nothing, when the waiting zip belongs to another account; both print `approved|rejected <id>, account <account id>`.

`list` prints, per kept zip: its id, the account, the zip's user id and handle, the time, the note, and whether the zip's Steam id equals the account's verified one (information only); then each refused zip as `r<account id>-<8 hex>`, `refused`, `account <id>`, `handle <handle>`, the time, `<n> bytes`, the reason (tab separated). `reject r<account id>-<8 hex>` deletes that refused file. `approve <id>` runs the restore with the rules below and prints the restore report or the reason it refused; with `--keep-handle` the account keeps its own name instead of taking the zip's (the player's notice says so). `reject <id> [reason]` deletes the kept zip and its `uploads` row and keeps the reason (the rest of the line) for the player. Like `import backup` it runs on its own and needs the recordings.

**What the player is told.** A refused approve stores its reason as the zip's `note`; an approve that restores, and a reject, add a row to `upload_results` (the `decisions` above) and every one of these three leaves a message from the server's notice sender in the account's inbox, the thread `Chat/conversations` lists: "Your backup was not restored: <reason>" (once per reason: the same refusal again adds nothing), "The backup was restored: …" with the user id and the name, or "Your backup was rejected by the operator", with the reason when there is one. The website's restore page shows the same. The messages are English, like the server's other notices.

| `approve` | Result |
|---|---|
| The user id was not restored before, is not held by another account, is from 1 to 1,999,999,999 | Full restore, once per game user id: the profile rows are replaced (uploading is the player's consent; hunts, kills and photos made here stay) and the account takes the zip's handle when it is a plain name of at most 32 characters nobody else has (otherwise it keeps its own). An account that has not played (no row in `expeditions` and `events`) also takes the zip's user id: the Steam id, tokens and sessions follow it, and so do the account's photos: `photos/<old id>/` is merged into `photos/<new id>/` (a name clash keeps the account's own photo). An account that has played **keeps its own user id** ([ADR 0009](adr/0009-restore-a-zip-onto-an-account-that-has-played.md)): nothing moves, and no id of the zip can clash with the ids handed out here; the notice and the `decisions` entry carry the account's own id. One audit row, one row in `restored_ids` (the zip's user id, for either kind of account); the row in `uploads` goes, the zip stays. The whole database is **not** copied (`Store.Backup` is the local rule): the kept zip is the way back |
| A user id restored before, held by another account, or outside that range | Refused with the reason, which becomes the zip's note; the zip stays kept until the operator rejects it |

A user id is restored once, enforced by the primary key of `restored_ids`, so two uploads at the same moment cannot both win. If a restore turns out wrong, the operator deletes the account's rows (or the account) and imports the kept zip again with `import backup <zip> --account <id>`; deleting the account frees its user id.

**Delete my data.** `POST /account/delete` deletes the `accounts` row, and with it, by the foreign keys, every per-player row (the crash reports too), the tokens, the cookie sessions, the review rows, the decisions and the restored user id; then the account's `restores/<id>/`, `photos/<id>/` and `reports/<id>/` folders (the pictures a restore unpacked are in the second, [Pictures](restore.md#pictures); the last holds the problem reports). A restore that changed the account's user id moved the folders and the crash reports to the new id (a report's reference and file names change with it), so none is left under the old one. The Steam id and handle go with the row, so signing in again makes a new account. It refuses (`429`) while an upload or a report of the account is running. The replies are `{status, message}`; the cookie is cleared.

## Problem reports

When the game fails on a player's PC the launcher builds one zip (its contents: [launcher.md](launcher.md)) and sends it from the signed-in player. `POST /account/report` on `web_host`, signed in with the `hr_session` cookie, header `X-Requested-With: launcher` (or any value: a form of another site cannot set it), header `X-Report-Trigger: <trigger>`, the body the zip (`Content-Type: application/zip`).

| Trigger | Sent when |
|---|---|
| `manual` | The player pressed "Report a problem" in the launcher's Settings |
| `short` | The game ran less than 60 s |
| `exitcode` | The game's exit code was not 0 |
| `nowindow` | No visible game window was ever seen |

| Reply | When |
|---|---|
| `200` `{"reference":"p<account>-<sha8>"}` | Kept. `sha8` is the first 8 hex digits of the zip's SHA-256, so the same zip sent twice is one report |
| `401` | Not signed in |
| `400` | A trigger that is none of the four, a request from no page of this server, or a body that is no readable zip (the zip is opened, not unpacked) |
| `413` | Over 6 MiB (`Content-Length` over it is refused unread; a chunked body stops at the limit) |
| `429` | A report of the account is being received (one at a time, from the start of the request to the end), or the account sent 5 in the last 24 hours |
| `507` | The data disk would have less than `upload_min_free_bytes` free after it (the setting of [Upload a backup zip](#upload-a-backup-zip), counting the declared size) |

A report is `reports/<account id>/<reference>.zip` with `<reference>.json` beside it (`{ts, trigger, size}`, `ts` in epoch seconds); the 24-hour limit counts those notes. It is only read by the operator: never through `/account/restore/*`, never restored. It is deleted 30 days after `ts` (a zip without a note, by its file time), at server start and once a day, and with the account (`POST /account/delete`). When a new report is kept the server posts one `Problem report` alert to the `review_webhook` (see [Discord alerts](#discord-alerts)).

**Review.** `GET /admin/reports` lists the reports (`{reference, account, handle, ts, trigger, size}`, newest first) and `GET /admin/reports/<reference>` downloads the zip ([Admin API](#admin-api)). On the command line:

```
dotnet run --project server/Server -c Release -- [--settings <file>] review reports | reports <reference> <file> | diagnostics <account>
```

`review reports` prints one tab-separated line per report: the reference, `account <id>`, `handle <handle>`, the time, the trigger, `<n> bytes`; with a reference and a file it copies that zip to the file (which must not exist). `review diagnostics <account>` (and `GET /admin/diagnostics?account=`) shows what the server knows of the account in the last 30 days, to read beside a report:

- the kept [crash reports](#crash-reports): time, kind, module, the top frames and the message;
- the hunts that ended without the game's disconnect call: closed hunts whose end is their last heartbeat (the server closed them after 30 s of silence, or the player's next start replaced them; at most 100). A hunt that got no heartbeat and ended by a disconnect is not in the list: the server cannot tell it from a replaced one;
- the closed hunts that lasted under 60 s (at most 100);
- how many times the game sent event 30, "the connection to the host failed" ([Multiplayer](#multiplayer)).

## Crash reports

The game sends its error reports to `crash_host` as envelopes: a header line, then per item a header line (`type`, and `length` in bytes) and its payload. With player state the server reads them instead of appending them whole to `telemetry.jsonl` (it held every report's install paths and device hash and was never pruned). The game gets 204 whatever happens.

- **Kept:** `event` items whose `level` is `fatal` or `error` (no level counts as error), and `session` items whose `status` is `abnormal` (a run that ended without a crash report or a clean exit). Everything else is dropped: warnings, info, other sessions, dumps and other attachments, transactions. An envelope is read to its first cut or garbled item, at most 8 items.
- **Whose:** the `user.id` of the event, or the `did` of a session, when it is the user id of an account of this server. A report with none, or of an account that does not exist, is dropped.
- **What is stored** (`crash_reports`, schema 27, one row per account and event id; the same id again changes nothing): `ts` (the report's own time, never later than its arrival; a report older than 30 days is dropped), `kind` (`fatal`, `error`, `abnormal`), `module`, `frames`, `message` and `release`. `frames` are the top 8 frames of the exception's stack, the crashing one first, each `module!function` or, when the report names no function, `module+offset` (hex), the module found by address in the report's own list of loaded images, shown by its file name. `message` is the exception's type and value (else the event's message), at most 300 characters. Every Windows path in a stored text or image name (a drive such as `C:\`, a share such as `\\pc\c$\`, or a device or extended form: `\\.\`, `\\?\`, `\\?\UNC\`) is reduced to its file name when that has a known extension (`dll`, `exe`, `log`, `ini`, `dat`, `sav`, `pak`, ...) and does not sit directly in a `Users` or `home` folder; any other path (a folder, or a name with another dot such as a profile folder) becomes `<path>` together with the rest of its line, so a user name never stays. Nothing else of a report is stored: the device hash, user name, address, machine name, other contexts and breadcrumbs are dropped.
- **Kept** the newest 200 per account and kind (a flood of harmless errors never pushes out a fatal report or an abnormal session) and 30 days; a purge at start and once a day deletes the older ones. The rows go with the account (`POST /account/delete`).

`telemetry.jsonl` keeps the telemetry host's requests (the death types and organ data the heartbeat does not carry), each body cut at 64 KB. At start the file is rewritten once when it holds crash host lines (an older server appended them whole) or is over 32 MiB: the crash host lines go through the rules above first (those of the last 30 days; the rest is dropped) and the newest 32 MiB of the other lines stay. A server without player state keeps the crash host's requests in the file like the telemetry host's.

## Archive claims

Players can no longer make a backup, so a signed-in player may claim the public profile the operator's archive kept for them ([ADR 0008](adr/0008-archive-claims.md)). The archive is one SQLite file, `archive.db` (the setting `archive_db`, default `<data_dir>/archive.db`), made on the operator's PC and copied into the data folder. The server opens it read only, and no route serves it. No file: claims are off (lookups answer `found: false`, the website hides the claim box). The file is looked for at every call, so copying it in needs no restart.

```
meta(key, value)                                  -- 'format' = '1'
player(uid, handle, hostname, hunterscore)        -- hostname = the handle in lower case, unique: the lookup key
reply(uid, path, endpoint, params, status, body)  -- the replies a public-mode backup zip of that player would hold, file by file
```

A claim reads the player's `reply` rows with the same reader as a public zip (`Importer.FromReplies`, [restore.md](restore.md)) and writes them with the same restore (`Restorer.Apply`).

**Rules.**

| | |
|---|---|
| Lookup | The name must match a handle exactly, in any case. 5 lookups per account per UTC day, counted in the table `claim_lookups` (schema 18), so a restart keeps them. A claim of a name the archive does not have costs one too |
| One claim per account, ever | A row of the account in `claims` (any state, also a rejected one) refuses another claim |
| Hunterscore below 10,000, and nobody else claimed the player | Restored at once |
| Hunterscore 10,000 or more, or another account already has a `claims` row for that archived player | Kept as a `waiting` row for the operator; nothing is restored. The player gets a notice in the inbox and the `review_webhook` gets a `Claim waiting for review` alert (see [Discord alerts](#discord-alerts)) |
| The account has played (a hunt was opened or an event came in) | `409` `confirm` until the player confirms the overwrite (`confirm=overwrite`) |

**What a claim does.** It replaces the account's items, skills, achievements, trophies, lodges, loadouts, missions and challenges, and the saved replies kept as extras, with the archived ones (the restore of [Upload a backup zip](#upload-a-backup-zip), no merge). The statistics are the archive's, and the hunts made here count on top of them ([ADR 0003](adr/0003-statistics-are-a-base-plus-server-hunts.md)). Hunts, kills and photos made here stay. The account's wallet stays too (an archived profile has none), with gm$ raised to at least 15,000 like after every restore. **The account's user id never changes**: no `restored_ids` row is written, so an own-mode zip of the same player can still be approved later, and a claim never changes the user id, whether or not the account has played ([ADR 0008](adr/0008-archive-claims.md)). No zip is kept; the audit row's `zip_sha256` reads `archive:<archived user id>`. The handle is the archived one when the player asked for it, it is a plain name of at most 32 characters and no other account has it (any case); otherwise the account keeps its own, and the notice says so. The player gets a notice in the inbox, like an approved upload.

| Endpoint (`web_host`, session cookie, as under [Upload a backup zip](#upload-a-backup-zip)) | |
|---|---|
| `GET /account/archive?name=<name>` | One lookup: `{found: false}`, or `{found: true, handle, hunterscore, items, trophies, lodges, skills, statistics, achievements, nameFree}`: the counts are what a claim would restore, the three flags say whether the archive has that part, `nameFree` whether the archived handle could be taken. `429` `{status: limit}` over the limit; 401 when signed out |
| `GET /account/archive` | `{enabled, claimed}`: `claimed` is null, or the account's claim `{state: waiting\|restored\|rejected, handle, ts}`. 401 when signed out |
| `POST /account/archive/claim` | Form `name`, `old_name=1` (take the archived handle) or `0`, `confirm=overwrite` (optional), same checks as `POST /account/restore`. `{status, message}`: `restored`, `review` (200), `refused` (409: the account has its claim already, or the profile cannot be restored), `unknown` (404), `limit` (429), `confirm` (409) |

**The operator.**

```
dotnet run --project server/Server -c Release -- [--settings <file>] review list | approve c<id> [--keep-handle] | reject c<id> [reason]
dotnet run --project server/Server -c Release -- [--settings <file>] claim <account> <archived handle or user id> [--keep-handle]
```

`review list` prints a waiting claim as `c<id>`, `claim`, `account <id>`, `archived <uid>`, `handle <handle>`, `hunterscore <n>`, the time and the note (why it waits), tab separated, after the kept zips. `review approve c<id>` runs the restore above (the player's choice of name stands unless `--keep-handle` keeps the account's own) and the row becomes `restored`. `review reject c<id> [reason]` marks the row `rejected` and keeps the reason; the player gets it in the inbox, and the claim stays the account's one. `claim` restores an archived player onto an account (its user id or handle) at once: no lookup limit, no review, no confirmation, and it replaces the account's earlier claim row. All of them run on their own and need the recordings, like `import backup`. Deleting an account deletes its `claims` and `claim_lookups` rows, so the archived player can be claimed again.

Claim ids are never reused (`claims.id` is AUTOINCREMENT, from 100 at least on a database migrated from before), so a `c<id>` in an old alert never names another player's claim after an account is deleted.

## Discord alerts

Every alert to `review_webhook` and `signup_webhook` is plain text (no embeds) in one layout, built by `Alerts.Text`: a bold title with one emoji for the kind, then one `label: value` line per fact, then the exact command to run in a code span when there is one. A handle is in a code span (a `_` in it stays a `_`) and only plain name characters; the Steam profile is a `[profile](<link>)` link (the angle brackets keep Discord from adding a preview), or `none`.

| Alert | Channel | Lines after the title |
|---|---|---|
| `📦 Backup waiting for review` | review | `id`, `handle`, `account`, `backup user id`, `steam`, `run: review list` |

## Behind a reverse proxy

A proxy in front of the server speaks plain HTTP to it (a listener without `cert`). The game routes by host name, which a proxy hides, so a local forwarder in front of the proxy puts the name the client asked for in a request header. The server reads `host_header` (default `X-Game-Host`) and routes by its value, only when the peer address is in `trusted_proxies`; from any other peer the header is ignored. A value that is not a host name (optionally with a port) is ignored too.

## Admin API

`/admin/*`, Swagger UI (`/swagger`) and the OpenAPI documents are for a person at the server's machine. A request is served only when all of these hold: its `Host` is `localhost` or `127.0.0.1`; it came in on a listener marked `"admin": true`; its peer address (not a header) is a loopback address; and it carries no header that says a proxy relayed it (`X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `Forwarded`, `Via`, `X-Real-IP`, the `host_header`). Any other request for those names gets 403. No listener is an admin listener unless marked, and a proxy on the same machine is a loopback peer too, so keep the listener a proxy connects to unmarked and give the admin API its own loopback listener (for example `127.0.0.1:8081`, reached from the VPS through an SSH tunnel). Admin bodies are limited to 64 KiB.

The routes (Swagger UI describes each; `account` is a user id or handle, left out: the local account, except `/admin/rescore`, where left out means every account). Except `status` and `misses`, they answer 503 when the player state is off (no connect to seed it from) (`reports` also when the server is offline, not a community server), and the ones that take `account` answer 404 for an account that does not exist:

| Route | Does |
|---|---|
| `GET /admin/status` | What the server serves from: the player state database, the recordings loaded, the recorded keys, the install's archive entries and the lines of the miss log |
| `GET /admin/wallet?account=`, `GET /admin/inventory?account=` | The account's balance per currency (`em`, `gm`); its owned items |
| `GET /admin/items/<item id>` | The item's definition as heartbeat update 10 sends it; 404 for an item with none |
| `POST /admin/grants/items?account=` | Body `{itemId, count}` (count 1 to 1,000 full stacks, default 1) in slot 0; not idempotent |
| `POST /admin/grants/currency?account=` | Body `{currency: "em" or "gm", amount}` (negative takes; 409 when the balance would drop below 0); not idempotent |
| `POST /admin/rescore` | Below |
| `POST`, `GET` and `DELETE /admin/spawn` | Add a group of animals to the next hunt (the fields of `admin spawn`: `reserve`, `animal`, `males`, `females`, `x`, `z`, `radius`; and `minWeight`, `maxWeight`, `wounded`, `dormant`), list the entries and where the last connect put them, remove one entry (`?id=`) or all |
| `POST /admin/spawn/wake?account=` | Body `{populationId, group}` (from the list, `group` 1 or more): the running hunt wakes a dormant group with its next heartbeat |
| `GET /admin/misses?limit=` | The newest requests nothing could answer, keys only (1 to 1,000, default 50) |
| `GET /admin/reports`, `GET /admin/reports/<reference>` | The problem reports ([Problem reports](#problem-reports)), newest first; the zip of one by its reference (404 for a reference that is none) |
| `GET /admin/diagnostics?account=` | The account's last 30 days: crash reports, hunts that ended without a disconnect, hunts under 60 s, the event 30 count ([Problem reports](#problem-reports)) |
| `GET /admin/taxidermies?account=` | The account's taxidermized harvests, newest first: `{kill, species, harvested, done, currency, paid, ts}` ([Taxidermy](#taxidermy)); `currency`, `paid` and `ts` are null for one marked before the price existed |
| `POST /admin/taxidermies/<kill>/undo?account=&refund=` | Takes a taxidermy back: the harvest is a plain one again, and `refund` (default true) gives the price back with a wallet row (`{kill, currency, refunded}`); 404 for a harvest that is not taxidermized |
| `POST /admin/season/start` | Ends the current leaderboard season one second before now and starts the next number now: `{no, start, end}` of the new one; 409 when the current season started this second or later ([Leaderboards and seasons](#leaderboards-and-seasons)) |

`POST /admin/rescore?account=&kill=&dry_run=`: scores the stored harvests again with the rules of today (`Scoring`, the ammunition check, the stored kill events: the same step the heartbeat runs), for the account named (user id or handle) or, without `account`, every account. A harvest whose score or score type differs gets its stored harvest page updated (one that now scores nothing gets 0, so the boards stop listing it; the kept boards are dropped after a real run); when its css rounds to more than 0 and the account has no `wallet_log` row `CSS Reward (Animal Id: <kill id>)`, that gm$ is paid through `State.AddCurrency` with that summary (and sent as update 15). A reward already paid is never taken back. A disqualified harvest, or one with no score before and now (no antlers, a species without rules), is left as it is. Running it again pays nothing more. One transaction per account. `kill` (needs `account`, answered 400 otherwise, kill ids being per account) rescores that harvest alone (an unknown kill lists nothing), so an operator can apply just the harvests a dry run listed for a known cause. `dry_run` defaults to `true` and writes nothing; the reply is `[{account, rescored, paid, gms, harvests}]` with the same counts a real run would write; `harvests` lists each rescored harvest as `{kill, species, oldScore, newScore, gmsPaid}` (the gm$ its kill was paid before, for the record).

The same step from the command line, for a server whose admin API is not reachable (the community server's listener has no `admin`): `admin rescore [--account <id or handle>] [--kill <id>] [--apply]`, e.g. `cd ~/web && docker compose exec -T server dotnet server.dll admin rescore --account <id> --kill <kill id>` (the image's entry point is `dotnet server.dll`, the compose service is `server`). It runs `State.Rescore` on `data_dir` with the same rules, a dry run unless `--apply` is given, and `--kill` needs `--account`. It prints one JSON line per harvest whose score changes, `{"account","kill","species","oldScore","newScore","gmsPaid"}`, then, right after its harvests, one line for each account that changed or would be paid, with `rescored`, `paid`, `gms` and `applied`, then a last line saying dry run or applied. A running server drops its kept boards only when its own route runs: after `--apply` they show the change within 15 minutes (24 hours for an ended season's boards), or at once with `docker compose restart server`. Take a [backup](deploy.md#backups) first.

## Tests

`dotnet test --project server/Server.Tests -c Release`: xUnit v3, no network and nothing outside a temporary folder. Fixtures are built in code. CI runs them on `windows-latest` (with the rest of the solution) and on `ubuntu-latest` ([CONTRIBUTING.md](../CONTRIBUTING.md#ci-and-updates)). `EndToEndTests` plays the whole journey over HTTP: a made-up backup is uploaded and approved, the account launches, connects, harvests an animal and disconnects, and the new kill is read in the hunterscore, the statistics, the trophies and the hunt history by the player and by a second account (the second account reads the trophies on the website and, in the game, in the lodge the harvest is mounted in).
