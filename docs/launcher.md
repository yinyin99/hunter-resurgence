# Launcher

`src/Launcher/` is a Windows desktop app that will replace the old launcher once the community server exists. It runs beside the old launcher and does not change it. It never writes into the game folder.

It is a Blazor app shown in a WPF window (1280 x 760 the first time, then where and how large it was when it last closed, if that place is still on a screen; its title ends with the launcher's version, `Hunter Resurgence v0.33.0`) through the WebView2 control, so the Microsoft Edge WebView2 runtime must be installed (it comes with Windows 11; without it the launcher offers the download, see [When the launcher's page fails](#when-the-launchers-page-fails)). The screens are shared with the [website](website.md) and live in `src/Ui/`; the launcher only adds the window and the real services below.

## State

The screens follow the old launcher and its website screen for screen: the same theme, the same places for things, the same navigation and the same English texts (French uses the original French texts). Where the original had a defect or a text that cannot be reused, the screen does the sensible thing instead.

Behind the screens the data is a **mock** (fixed, fictional data and fake actions) unless `server_url` is set; then the services listed under "What is real" are the community server's. The pictures are not included: the launcher shows the operator's pictures from the website at `server_url` ([images.md](images.md)); without it, or when the website does not answer within 5 s, each one is a neutral labelled box. To play on the community server the launcher also sets up the PC and answers the game ([The player kit](#the-player-kit)).

Until the official servers closed (2026-11-11), a large orange backup tool button showed under the top bar's logo; see [website.md](website.md#backup-tool).

## The service layer

Every screen talks to an interface in `src/Services/Contracts/` (one per area: session, sign-in, signup, news, Discord invitation, servers, store, inventory, wallet, bank, missions, seasonal events, competitions, leaderboards, profile, friends, messages, account, backup restore, help, patch, game settings, launcher bridge, player kit, Steam launch option, cleanup). `src/Services/Mocks/` implements each of them with fixed data; `AddMockServices()` registers them all. A host replaces a registration with a real one when it exists. The launcher does that for the launcher bridge, the patch panel (its own update), cleanup, the Steam launch option, game settings, the player kit, the news (`DiscordNewsService`, the Discord frame, from `link_discord`), and for the `Server*` services when `server_url` is set (with its own session service for the sign-in).

## Build and run

```
dotnet build hunter-resurgence.slnx -c Release
dotnet run --project src/Launcher -c Release
dotnet test tests/Resurgence.Tests -c Release
```

The exe is `resurgence-launcher.exe`. To make the release: `src\Launcher\publish.cmd <your settings.json> [version]` publishes the self-contained exe, copies your `settings.json` next to it and packs `resurgence-launcher.exe`, `settings.json` and `wwwroot` (the page the exe shows; the exe does not start without it) with Velopack (the dotnet tool `vpk`, installed with `dotnet tool install -g vpk --version <the version of the Velopack package in the csproj>`) into `src\Launcher\bin\Release\net10.0-windows10.0.17763.0\win-x64\releases`: `HunterResurgence-win-Setup.exe`, the full package `HunterResurgence-<version>-full.nupkg`, a delta package `HunterResurgence-<version>-delta.nupkg` when the folder already holds the packages of an older release, and `releases.win.json`. The release workflow does this for a tag when the repository secrets `PLAY_SERVER_URL` and `STEAM_APP_ID` are set (without `STEAM_APP_ID` the release has no launcher), with the example `settings.json`, `server_url` from that secret and `steam_app_id`, `client_exe`, `graphics_file`, `options_file`, `options_key_prefix`, `game_web_host`, `crash_host` from the secrets `STEAM_APP_ID`, `LAUNCHER_CLIENT_EXE`, `GRAPHICS_FILE`, `OPTIONS_FILE`, `OPTIONS_KEY_PREFIX`, `WEB_HOST`, `CRASH_HOST` (all required with the launcher), and `link_discord`, `link_backup`, `link_source`, `game_name`, `game_full` from the optional secrets `LINK_DISCORD`, `LINK_BACKUP`, `LINK_SOURCE`, `GAME_NAME`, `GAME_FULL` (an unset one stays a placeholder, i.e. not configured; the other links stay placeholders). It first downloads the earlier releases (`vpk download github`) so that the delta can be made, uploads the Setup, the packages of this version and `releases.win.json` to the tag's release, attests the Setup and puts its SHA-256 in the release notes; CI packs the launcher with the example settings, checks the publish folder and the release folder, and runs the Setup silently (see deploy.md).

The launcher's tests (folder `LauncherApp` of `tests/Resurgence.Tests`) use a temporary Steam folder tree, temporary settings files, temporary backup zips, a test website on 127.0.0.1 (the list of pictures), a local update feed (a folder with `releases.win.json` and a package) and a temporary registry key for the link scheme. They read and change nothing else on the PC, with one exception: `LauncherServicesTests`, `LauncherStoreTests` (a purchase through the real client and cookie against a test server on 127.0.0.1) and `LanguageSwitcherTests` build the launcher's real services, so they read `launcher.json` (`LanguageSwitcherTests` points it at a temporary file), the Steam registry keys and the game search the way a start does (missing sources give the defaults); they write nothing but that temporary file. `dotnet test` exits 0 when every test passes.

### Icon

The icon is `src/Launcher/wwwroot/favicon.ico`: the website's paw (`src/Web/wwwroot/favicon.svg`) in #1f1a17 on a #f2ebe3 rounded tile, at 16, 20, 24, 32, 40, 48, 64, 128 and 256 px. It has a light tile because the website's transparent dark paw would barely show on a dark taskbar.

The csproj's `ApplicationIcon` puts it on the exe, and WPF uses the exe's icon for the window's title bar and the taskbar. `wwwroot/index.html` links the same file as its favicon.

When `favicon.svg` changes, regenerate the icon. In an empty folder outside the repo run `npm init -y` and `npm i @resvg/resvg-js`, save this as `make-icon.mjs`, and run `node make-icon.mjs <repo folder>`:

```js
// node make-icon.mjs <repo>: writes src/Launcher/wwwroot/favicon.ico from src/Web/wwwroot/favicon.svg
import { readFileSync, writeFileSync } from 'node:fs';
import { Resvg } from '@resvg/resvg-js';
const repo = process.argv[2];
const paw = readFileSync(`${repo}/src/Web/wwwroot/favicon.svg`, 'utf8').match(/<g class="paw">[\s\S]*?<\/g>/)[0];
const svg = `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 64 64"><rect width="64" height="64" rx="12" fill="#f2ebe3"/><g fill="#1f1a17" transform="translate(8 9) scale(.75)">${paw}</g></svg>`;
const sizes = [16, 20, 24, 32, 40, 48, 64, 128, 256];
const pngs = sizes.map(s => new Resvg(svg, { fitTo: { mode: 'width', value: s } }).render().asPng());
const head = Buffer.alloc(6 + 16 * sizes.length);
head.writeUInt16LE(1, 2);
head.writeUInt16LE(sizes.length, 4);
let offset = head.length;
sizes.forEach((s, i) => {
  const e = 6 + 16 * i;
  head.writeUInt8(s % 256, e);
  head.writeUInt8(s % 256, e + 1);
  head.writeUInt16LE(1, e + 4);
  head.writeUInt16LE(32, e + 6);
  head.writeUInt32LE(pngs[i].length, e + 8);
  head.writeUInt32LE(offset, e + 12);
  offset += pngs[i].length;
});
writeFileSync(`${repo}/src/Launcher/wwwroot/favicon.ico`, Buffer.concat([head, ...pngs]));
```

### Development switches

| Switch | Effect |
|---|---|
| `--route=/store` | opens that page first (the default is `/splash`, which goes on to the sign-in check) |
| `--mock=<state>` | puts one mock service in a state, to see a screen that is hard to reach |

States: `patch:new-patch`, `patch:new-patch-notes` (the same with a list of release notes), `patch:full-download`, `patch:launcher-update`, `patch:verifying`, `patch:extracting`, `patch:checksum`, `patch:files`, `patch:finishing`, `patch:done`, `patch:steam-update`, `patch:steam-only`, `patch:error`, `patch:launcher-ready`, `patch:exit-<code>` (the game ended with that code, for example `patch:exit-16001`), `settings:first` (the first-start dialog, on the mock settings), `signup:confirmed`, `profile:photos`, `profile:ongoing` (the latest hunt is in progress, with a kill and a pickup so far and no distance: its page says "In progress", and the start screen shows the current-hunt panel), `taxidermy:late`, `taxidermy:already`, `taxidermy:fail` (every taxidermy purchase on a hunt page is refused that way, [website.md](website.md)), `start:hold` (stay on the start screen), `session:signup` (an account without a username), `session:out` (signed out), `eula` (an account that has not accepted the agreements), `poll:fast` (the status bar and the messages page read again every 2 seconds instead of 30), `browser:hold` (the browser pages stay in their progress state).

Social and content: `friends:requests` (three friend requests), `friends:incoming` (a request arrives after five seconds), `messages:unread` (one unread conversation), `messages:incoming` (a message arrives after five seconds), `missions:resume` and `missions:noresume` (the resume item is offered, with one owned or none), `missions:soon` (the day ends in a few seconds).

Seasonal events: `events:running` (a Halloween 2026 event runs on the game's reserves 0, 1, 2, 8 and 9, so the launch map asks for the event's badges).

Store, wallet and bank: `store:fail` (every purchase fails), `store:nosales` (nothing is on sale, so no Sales entry), `wallet:many` (more than one page of wallet rows), `bank:steam206` and `bank:steamerror` (the two Steam errors of a bank purchase). Buying in the store or the bank changes one mock wallet that the status bar and the wallet show (per website session, or per launcher run). The bank codes are `SAVE20` (20 % off) and `GIFT` (500 em$, once); a payment reference with `fail` in it, as in `/steam_callback/fail-1`, is a failed payment.

The same states work on the website with `?mock=<state>`; see [website.md](website.md#development-switches), which also lists the states that exist only there.

## settings.json

`settings.json` sits next to the exe. Start from `src/Launcher/settings.example.json`; the build copies it with placeholders. The real file is git-ignored and never committed. Every value is a string. A missing key, a missing file or a value that still has `<placeholders>` means "not configured": only the part that needs it stops, the launcher still starts.

| Key | Meaning |
|---|---|
| `steam_app_id` | Steam app id of the game. Digits only (the release fails otherwise). |
| `client_exe` | Path of the game's client exe, relative to the game folder. (The [backup tool's](backup.md#settingsjson) own `settings.json` uses the same key for a bare exe name.) |
| `graphics_file` | Name of the game's graphics settings file, relative to `%APPDATA%`: the one the client reads with `/steam`. The file of a start without Steam is the same name without `_steam` (a name without it is one file for both modes). |
| `options_file` | Name of the game's options file, relative to `%APPDATA%`. |
| `options_key_prefix` | The text that precedes each key name in the options file. |
| `server_url` | The community server's `https://` address (its website shares it). At each start the launcher reads the list of the operator's pictures from its `/images.json` and shows them from its `/images/` ([images.md](images.md)). Only the scheme, host and port are used. Also switches the launcher's services to the community server's (see [What is real](#what-is-real-and-what-is-mock)), and is where the player kit forwards the game to. Not set: every picture is a labelled box and every service is a mock. `http://` is accepted only for a website on this PC (`localhost`, `dotnet run`); the player kit needs `https://` and is off without it. |
| `game_web_host` | The game's server name for everything it sends: the current build needs this one and `crash_host`. Never `web_host`: that is the community server's own website. For the player kit only ([the player kit](#the-player-kit)). |
| `crash_host` | The game's server name for crash reports. For the player kit only. |
| other `*_host` keys | The older `*_host` keys of the server's `settings.json` ([server.md](server.md#run-it)) are only for the old build. Every `*_host` key goes into the hosts block and into the certificate; only plain host names are accepted, and a name starting with `www.` also redirects the bare name. The host list is data: a new name needs a new `settings.json`, not a new build. |
| `game_name` | The short name shown wherever the screens say "the game" (the fallback when empty). |
| `game_full` | The name with its edition (falls back to `game_name`). |
| `link_*` | External links of the footer, the help pages and the menus; the key is `link_` plus `support`, `support_connections`, `support_request`, `wiki`, `wiki_de`, `wiki_fr`, `wiki_es`, `steam_store`, `discord`, `trailer` (the "Watch the trailer" button of the news), `backup` (the backup tool's release zip, linked from the news), `source` (the project's repository: the news, and the download page's launcher button and player guide link), or a numbered one: `link_guide_1` ..., `link_video_v1` ... (the launcher's help page only) and `link_community_1` .... A link that is not set is not shown. The footer's "Developed by" links the maintainer's GitHub profile, fixed like the credit line. |

Texts say `{game}`, `{GAME}` or `{game_full}` where the original named the game; they are filled from `game_name` and `game_full`. Absolute paths and paths with `..` in the file names are rejected.

## What is real and what is mock

Real today:

- **Game settings** (the dialog from the Settings menu and the first-start dialog): reads and writes the game's graphics and options files; see below. At its top: the **Game folder** line (the folder in use, `ILauncherBridge.GameInstall`, and a button that opens the Game folder window, left out of the dialog shown before the first game start (closing the Game folder window there would cancel the pending start); the install check's fix button opens the same window) and the **Start the game using Steam** box (`GameOptions.StartWithSteam`, `launcher.json` `start_with_steam`, default checked, kept across updates and restarts). The other options are read and written in the graphics file of the chosen mode: unchecked, only the no-Steam file (`Settings.StartGraphicsFiles("nosteam")`).
- **launcher.json**: the language chosen in the language dialog or on the Settings page is saved and applied at once (see [Languages](#languages)); so is whether game settings were saved once (the next game start no longer asks). The game folder chosen by hand is saved there too and used at once (the game is found again).
- **Finding the game** (`GameFinder`: the folder chosen by hand, the command Steam passes, Steam's own library files and the app manifest). It runs at start and again after a folder change, and reports `GameInstallInfo` (`ILauncherBridge.GameInstall`): the folder in use, its source (`manual`, `steam-option` or `steam-library`), `Gone` (the folder chosen by hand when it no longer holds the client: the automatic install is used and the window says so) and `Others`, every other game folder seen (all Steam libraries holding the client, the launch-option path, the manual folder), each once and only if the client exe exists. `ChooseGameFolder` opens the folder picker (on the window's thread); the player may pick the install root or the folder of the exe (or a folder inside the install), it must lead to the client exe (else `Settings.FolderNoGame`, nothing saved), then it is saved as the manual folder in launcher.json and the game is found again; cancelling changes nothing. `UseAutomaticGameFolder` clears the manual folder. A manual folder that no longer holds the client is ignored: the automatic install is used (if any), `Source` is its own and `Gone` names the stale folder (`Source` is null only when nothing is found). Tests: `GameFinderTests` (temp folders, a fake Steam library file).
- **Settings: folders and caches**: Screenshots, Logfiles, Clear launcher cache and Clear game cache are real, see [Settings: folders and caches](#settings-folders-and-caches).
- **Sign-in** (only with `server_url`): the sign-in page has one button, "Sign in with Steam"; no code is shown or typed. It uses [the loopback sign-in](server.md#the-loopback-sign-in) (RFC 8252 with PKCE, RFC 7636): the launcher makes a random verifier, listens once on `127.0.0.1` (a free port) and opens the server's sign-in (`/auth/app/start`) in the player's browser with the verifier's SHA-256, the port and a random `state`. The player signs in with Steam there and presses "Yes, sign in"; the server sends the browser back to `http://127.0.0.1:<port>/?code=…&state=…`, the launcher checks the `state` (a request with another one is refused and the wait goes on), answers the browser "Signed in, you can close this tab" and trades the code and the verifier for the session cookie (`POST /auth/app/exchange`), so a sign-in link sent to someone else gives the sender nothing. While it waits the page says the browser is open and has a Cancel; after 5 minutes it says the sign-in was not completed in time. The cookie is stored in `%APPDATA%\hunter-resurgence\session.dat`, protected by Windows DPAPI for this Windows user, and read again at the next start; `GET /auth/me` says whether it still signs in. Sign out deletes the file and calls `POST /auth/signout`. The cookie is also in `ServerCookie`, for the services that read the server; the first 401 of one of them drops it from `ServerCookie` for the rest of the run (so the account services stop asking and logging), while `session.dat` keeps it until the next sign-in or Sign out. Without `server_url` the sign-in stays the mock.
- **Opening an address** (`OpenExternal`, used by the fix buttons: Open Steam is `steam://open/main`, Verify files is `steam://nav/games/details/{steam_app_id}`, the early-exit window's "Verify the game's files in Steam" is `steam://validate/{steam_app_id}`, "Windows blocked the game" opens `windowsdefender://appbrowser`): only `https://` and `steam://` addresses and exactly `windowsdefender://appbrowser` (Windows Security's app control page) are opened (with Windows' default program); any other, and a failure to open, is ignored. `{steam_app_id}` in the address is replaced by `steam_app_id` of settings.json, so the id is not in the code.
- **Starting the game**: `LauncherBridge.StartGame` runs `<game folder>\<client_exe> /connect:<url> /param:<n>` (plus `/steam` in Steam mode, see [With Steam or without](#with-steam-or-without)) in the exe's own folder (the client finds its data there) with `SteamAppId` and `SteamGameId` set to `steam_app_id` in its environment, so the client does not ask Steam to start it again (which would run Steam's launch option), in either mode. `<n>` is a random non-negative number with bit 128 clear. Before that it runs the blocking checks of [the install check](#the-install-check) (version, files, setup); a blocked start returns that check's text (Steam is not one: the game starts without it). While that exe already runs, the start returns `Launch.AlreadyRunning` when one of its processes has a main window (`ClientProcess.Window`; that window is brought to the front, `GameProcess.BringToFront`) and `Launch.LeftOver` when none has ("A copy of the game is still running in the background without a window, probably after a crash"); nothing is started either way and the dialog offers **Close the game**. That button is `ILauncherBridge.CloseGameAsync`: `GameFiles.StopClientAsync` (the call of the close-launcher dialog: asks each process to close like its ×, stops those still running after 10 s, and first ends a `WerFault.exe` whose command line names the process, `-p <id>`, since a client that crashed while closing can stay alive behind Windows' error reporting). It starts nothing: the refused link is not kept, and the dialog says the game is closed (`Launch.Closed`) so that the player starts again from the page, where the picked reserve and lodge are sent anew (a replayed link had opened the hunt in another reserve: the first game's end closes the hunt the second start had already opened on the server, and the replayed connect found none). `Launch.CloseFailed` when the game is still there. When the exe is missing or fails to start, the start returns a failed `Result` (a translated text the page shows in a dialog) and the launcher keeps running. Each start button (Start game and create game on the launch map, join, the tutorials, sign-up page 4) is disabled and ignores clicks while its start runs, and works again when it ends, whatever the result, so a quick second click never opens another hunt (`MultiplayerPagesTests`).

  **The log lock** (`LogLock`, `GameProcess.Start`). The game's log file writer has no lock of its own: when one of the game's threads writes a log line while another writes or flushes the log, the game can crash (in hunts, most often with the inventory or the mission list open). So the launcher starts the known exe (its SHA-256 is `LogLock.Known`) suspended, with the same arguments, folder and environment, and before it runs wraps the writer's write and flush entries in the game's own memory lock: it writes two small functions into a page of the game's memory (each takes the lock, calls the original entry, releases the lock) and points the writer's table at them, then resumes the game. Before writing anything it checks that the table holds the three expected entries for the address the exe was loaded at; on another exe, other values or any failure nothing is written (or only the unused page), the game starts without the lock and the launcher's log says why (`The game's log lock is not applied, the game starts without it: <why>`). Nothing on disk changes, so Steam's file check stays clean. A game that cannot be resumed is ended and the start fails like a game that does not start.

  **The goose call patch** (`GooseCall`, `GameProcess.Start`). In the current game the Snow Goose's call animation raises an event of its own instead of the one the other birds' call animations raise, so its call is heard but can never be identified as a clue (and an objective that asks for it cannot be finished). On the same known exe, in the same suspended start, the launcher points the game's registration of an animation's events at a small function in a page of the game's memory: when an event's name is exactly the Snow Goose's call event, it is registered under the other birds' call event name instead; every other name passes through unchanged. The player gets a Snow Goose's call the HunterMate can identify again, with one call sound per call, as before the game's update. Before writing anything the launcher checks five places of the game's memory against their expected values; on another exe, other values or any failure nothing is written (or only the unused page), the game starts without the patch and the launcher's log says why (`The game's goose call patch is not applied, the game starts without it: <why>`). The four start-up patches are independent: one that is not applied does not stop the others. Nothing on disk changes. Tests: `GooseCallTests`.

  **The rabbit sound patch** (`RabbitSound`, `GameProcess.Start`). In the current game one of a rabbit's nervous standing animations plays a loud honk where the game before played a quiet foot stomp, so with a dozen rabbits around the player hears constant screaming; before, only the seasonal event's possessed rabbits had that sound. On the same known exe, in the same suspended start, the launcher points the start of the game's function that plays an animal's sounds at a small function in a page of the game's memory. For every sound but the rabbit's honk the function runs the game's own code unchanged. For the honk it looks at the animal that makes it: an animal whose behaviour profile is one of the event's keeps the honk, and any other animal, and any case that cannot be identified (every step to the profile is guarded), gets the rabbit's quiet stomp, which the function finds in the game's own table of sounds and plays instead (a game whose table has no stomp plays the honk as before). The player gets normal rabbits that no longer honk loudly while they stand nervous, and the event's possessed rabbits keep the sound. It is decided per animal at the moment the sound plays, so it depends on no event, reserve or setting: normal rabbits are quiet in every hunt, and each player's game decides from its own animals (in multiplayer a guest without the event hears the stomp). The possessed rabbits' own call is not covered: the rabbit has no call animation, so it never plays. The function is built for the address the exe was loaded at; it does not depend on the address of its page, only the jump written at the start of the game's function does. Before writing anything the launcher checks 19 places of the game's memory against their expected values; on another exe, other values or any failure nothing is written (or only the unused page), the game starts without the patch and the launcher's log says why (`The game's rabbit sound patch is not applied, the game starts without it: <why>`, for example `check 7 holds other values`); when it is applied the log says `The game's rabbit sound patch is applied`. Nothing on disk changes. Tests: `RabbitSoundTests`.

  **The coat table patch** (`CoatTable`, `GameProcess.Start`). Since the game update of late October, the snowshoe hare's coat tables are filed under a texture name whose letter case differs from the name the hare's model uses. The game looks a coat table up by that name with an exact, case-sensitive comparison, finds nothing, and falls back to one of the model's three skins at random with equal chances: the normal one, the albino one and the seasonal event's (a Halloween skin). With "Play seasonal events" off, about a third of the hares on the winter reserve wore the event's skin and another third were albino, and a player who took such a hare for an event animal and loaded silver ammunition had the kill disqualified; with the event on, the event's own file uses the right case and every hare gets the event's skin as intended. The server plays no part (it asks for any coat), so this is fixed in the launcher. On the same known exe, in the same suspended start, the launcher points the two calls where the game compares a coat table's texture name (the table lookup, and the match of the picked layer's name) at one small function (16 bytes) in a page of the game's memory. The function takes the same arguments the same way as the game's exact comparison (the two names' addresses in `ecx` and `edx`, the length on the stack, removed by the caller) and calls the case-blind compare the game already imports (`_memicmp`) on the same bytes in the same order; it returns that compare's result, and the two callers only test it against zero. The third comparison, which groups the tables when the file is loaded, is not touched: it stays exact, so that two tables whose names differ only by case (the mule deer's) stay apart. The player gets the weights of the game's file again: the normal hare 9,999 times in 10,000, the albino about once, the event's skin never without the event, and the same with the event on as before; every other species keeps its choice. The function does not depend on the address of its page, only on the address the exe was loaded at (the import's slot). Before writing anything the launcher checks 6 places of the game's memory: both calls with the instructions around them, the first and last instructions of the game's comparison, the import's slot (checked before the game runs, when it still holds the place of the import's name) and that name; on another exe, other values or any failure nothing is written (or only the unused page), the game starts without the patch and the launcher's log says why (`The game's coat table patch is not applied, the game starts without it: <why>`, for example `check 3 holds other values`); when it is applied the log says `The game's coat table patch is applied`. The two calls are written last and the layer match's first, so a failed write never leaves the table lookup redirected alone. Applying it to a process that already has it changes nothing (the first check fails). A game started without the launcher keeps the error, and the server's judgement of a hare in the event's skin stays right (it goes by the hunt's event). Nothing on disk changes. Tests: `CoatTableTests`, which include the coat choice itself on a reduced fixture of the shipped tables (a test of the reasoning, not of the bytes).
- **"Done hunting for now?" and "The game closed right away"** (`GameStartedModal`, `GameExitDialog`, `ModalService.GameStarted`): open once the started game has closed. `LauncherBridge.WhenGameExitsAsync` watches the process `StartGame` started last, by the handle the launcher holds from the start (after a 16010 fallback that is the retry, never the first process that already exited; the exe is not looked up by name while a handle exists). Only a game the launcher did not start (no handle) is looked up by its exe: it waits up to a minute for it to appear, then until it is gone; one that never appeared opens no window and completes with null. The watch checks every second and answers a `GameExit` (exit code, seconds, the process's mode, `Early`, `Cause`, `ClockAhead`). **Early** is: it ended within 20 seconds of its start, with a known exit code; the UI then opens "The game closed right away" (one action per `Cause`) instead of "Done hunting for now?". Neither opens for a game the player closed with **Close the game** (`ModalService.FixAsync` remembers it until the next start), nor for the exit of an older start once a newer one is watched (`ModalService.GameStarted` serializes them). The old app opened the latter five seconds after the start, whose texts ("Was there a connection issue?") then read like an error while the game still loaded, and players started it again. ## The player kit

The launcher lets the game reach the community server from your own PC, with your own copy of the game. It was a separate tool (`tools/play`, `play-win-x64.zip`); its code is now part of the launcher (`Hosts.cs`, `Pki.cs`, `Forwarder.cs`, `KitSettings.cs`, `Kit.cs` and `LauncherKit.cs` in `src/Launcher/`) and behaves as before. The game's files are never changed. While the PC is set up, the game talks only to the community server; Remove gives the official servers back. Make your backup with the [backup tool](backup.md) **before** the setup: it needs the official servers.

The kit exists only when `server_url` is an `https://` address (without it, or with an `http://` development server, Settings has no Set up and Remove and nothing below happens).

### For players

1. On its first start (and at every start while the PC is not set up) the launcher opens **Set up for the community server**: it lists what it changes and the game's server names. Choose **Set up**. Windows asks twice:
   - "Do you want to install this certificate?": choose **Yes**. This is the certificate authority that only your PC knows ([what it is](#what-setup-changes)).
   - A permission window for the launcher (administrator): choose **Yes**. Only the edit of the hosts file runs as administrator.

   You do this once. **Not now** keeps the launcher usable, but the game cannot reach the community server until you set up: Settings, **Set up for the community server** opens the same window again.
2. **Keep the launcher open** while you play, and start the game from it. The forwarder starts with the launcher and stops when it closes. So while the game runs (`GameFiles.ClientRunning`), closing the launcher window (the X, Alt+F4, the taskbar's close) asks "Are you sure you want to close the launcher and the game?" in a small dialog of the launcher's own (`CloseDialog`, a WPF window in the launcher's colours, centred on the launcher; a Windows message box cannot disable a button). **Yes** is disabled for the first 3 seconds after the dialog is drawn, so a quick double click, Enter or Space cannot close the game by accident; its label counts down ("Yes (3)", "Yes (2)", "Yes (1)", then "Yes"). **No** is the default button; Escape and the dialog's × mean No too. **No** minimizes the launcher to the taskbar and the game keeps playing. **Yes** asks the game to close like its window's ×, so the hunt ends as a normal quit (the launcher keeps running, minimized, meanwhile, so the game can still reach the community server), stops the game only if it is still running after 10 seconds (`GameFiles.StopClientAsync`), and then closes the launcher. Once the game has exited the window closes at once without a question, and a Windows shutdown or sign-out is never held up (`MainWindow.Decide`).
3. The first time the game starts, **Windows Firewall asks about the game: click Allow**. Without it the game cannot hunt.
4. To undo everything, choose Settings, **Remove the setup**. Windows asks to remove the certificate authority (choose Yes) and, as in setup, for administrator permission to edit the hosts file (choose Yes). After that the game talks to its own servers again (if they still exist).

If something does not work, see [Problems](#player-kit-problems).

### What setup changes

The setup window prints this before it starts. It changes three things on your PC and nothing else:

1. **The Windows hosts file** (`C:\Windows\System32\drivers\etc\hosts`): the game's server names (listed in `settings.json`) point to your PC (`127.0.0.1`), between two marked lines (`# >>> hunter-resurgence play (undo: play setup --remove)` and `# <<< hunter-resurgence play`; the lines keep the names of the old kit's block so that a block it made is found and removed too). Your other lines are not touched. Remove takes the block out again and leaves the file byte for byte as it was. If the end line is missing (a hand edit), the block ends at the first line that is not a `127.0.0.1 ` line: your lines after it stay.
2. **Your Windows trust list** (the current user's only, not the whole PC): a local certificate authority named `Hunter Resurgence local CA`. It is made on your PC, valid for two years, and **name-constrained**: Windows accepts a certificate it signed only for the game's server names, never for any other site. Its private key is created in memory, used once to sign the next item and then thrown away: it is never saved, so nobody can export or reuse it.
3. **A certificate for those names**, signed by that authority. Its public part is the file `%LOCALAPPDATA%\hunter-resurgence-play\leaf.cer`; its private key is a non-exportable key in your Windows key store. The forwarder uses it to answer the game over HTTPS.

Setting up again replaces all of it (and asks again). It is needed again when the certificate has expired, was made for other names than `settings.json` lists, or its authority is no longer trusted (removed, or you said No at the certificate prompt): the launcher says so at its start and opens the window. The check of the hosts block looks at the block only (its names, in any order); lines of other tools before or after it do not matter.

The administrator window: setup itself runs as you, so the certificate lands in your own trust list. Only when it needs to write the hosts file does the launcher start a second copy of its exe through the Windows permission window, with exactly the command line `--hosts on` (Remove: `--hosts off`); that copy edits the hosts file and exits, without a window or any other work. Any other command line starts the launcher normally. If the launcher itself runs as administrator, no window appears. The forwarder never needs administrator rights.

### When the launcher's page fails

If WebView2's renderer, its GPU process or it stops responding, the launcher logs the kind and reason and reloads the page (the app restores its state from the server); if its browser process exits, the launcher replaces the page control. Neither touches the forwarder, which belongs to the launcher process, so a running game keeps its connection (test: `WebViewRecoveryTests`).

If the browser cannot start, or draws nothing, the launcher says so in a plain Windows message instead of leaving a black window (`WebViewStart`; the texts are the `WebView.*` keys of the 19 `src/Ui/Strings*.resx`). Every case is first written to `launcher.log` (an error line, with the exception for a failed start), which a [problem report](#report-a-problem) holds, so it shows in a report sent after the launcher has been made to start.

| What happened | What the player is offered |
|---|---|
| No WebView2 Runtime is installed (checked first thing at start: `CoreWebView2Environment.GetAvailableBrowserVersionString` throws or finds none) | "Install it now?": Yes opens Microsoft's Evergreen bootstrapper (`https://go.microsoft.com/fwlink/p/?LinkId=2124703`) and closes the launcher; No closes it. The window is never opened. |
| WebView2 fails to start (the control's `CoreWebView2InitializationCompleted` reports a failure before the page has loaded once; the same Runtime-not-found exception counts as no Runtime). A control that is created again after a crash during the session is not a start problem: the game's close question stays | Hardware acceleration still on: "Restart without hardware acceleration?" Yes saves the choice and restarts, No closes the launcher. Already off: the "Install it now?" message, since the Runtime itself is broken. |
| The start fails with ERROR_INVALID_STATE (Windows error 5023: an older browser process still holds the user data folder with other arguments, for example right after a restart) | Never the download page. The launcher builds the control once more after 3 seconds; if that fails the same way too, the plain final message (the one for a page that does not load with hardware acceleration off, `WebView.Last`) and no further try. |
| The page has not loaded 20 seconds after the start (no successful first navigation), or the browser's environment could not be created at all (a failure inside `CoreWebView2Environment.CreateAsync`, such as the user data folder or bad options, raises no initialization event: only this timer catches it) | Hardware acceleration still on: "Restart without hardware acceleration?" Yes saves the choice and restarts, No keeps waiting (the page may only be slow). Already off: only a message that says so and names `launcher.log`; the launcher never offers a second restart. The timer does not fire over the close question, and an answer Yes is ignored when the page has loaded while the message was open. |

The restart without hardware acceleration sets `disable_gpu` to `true` in `launcher.json`, disposes the page control and waits up to 10 seconds for its WebView2 browser process to end (a new browser with other arguments cannot start on the same user data while the old one runs): after a successful start through `CoreWebView2Environment.BrowserProcessExited`; after a failed start no environment is handed out, so the launcher's own `msedgewebview2.exe` child processes are looked for until none is left (`WebViewStart.BrowserChildrenGone`, WMI). Then it starts the launcher again with the same command line plus `--wait-for=<process id>` and closes. When that restart itself fails (for example the process cannot be started), the error goes to `launcher.log` and the player gets the plain final message instead of an empty window. The new copy waits up to 20 seconds on the single-instance mutex itself (an abandoned mutex counts as acquired); when the old launcher is still there after that, it logs it and behaves as a second start (brings the old one forward and exits). `--wait-for=` is dropped from the arguments of every later restart, the update's included (`WebViewStart.ForwardedArgs`). The message boxes of the window have it as their owner. From then on every start gives WebView2 the browser argument `--disable-gpu` (`BlazorWebViewInitializing`, `EnvironmentOptions.AdditionalBrowserArguments`). To get hardware acceleration back, set `disable_gpu` to `false` or delete the line. A page that loaded but is drawn black is not detected: only a navigation that never succeeds is. Tests: `WebViewStartTests` (which message for which problem, the ERROR_INVALID_STATE classification, no second restart, every text exists, the `--wait-for=` parsing and the restart's arguments) and `PrefsTests` (the `disable_gpu` key).

### How the forwarder works

While the launcher is open it listens on `127.0.0.1` port 443 (HTTPS, with the certificate above) and port 80 (plain HTTP: the game's built-in browser sends some requests that way). Both speak HTTP/1.1 only. Each request is relayed unchanged (method, path and query exactly as sent, headers, body) over normal HTTPS to the community server at `server_url`, and the reply is relayed back with its length in `Content-Length` (never chunked, the game cannot read that) and without `Alt-Svc`, otherwise unchanged. The name the game asked for travels in the header `X-Game-Host`, because the community server sits behind a proxy that hides it; the server reads it only from that proxy ([server.md](server.md#behind-a-reverse-proxy)). The connection to the server tries IPv4 first (`Forwarder.ConnectIPv4First`): the server records the address of the host's connect and gives it to the players who join, and the game's networking cannot use an IPv6 one. The name's addresses are tried one after the other, IPv4 before IPv6, so a PC with no IPv4 route (IPv6 only, NAT64) still reaches the server (the server then lists that host's game as not joinable); when none connects, the game gets a 502. Redirects, cookies and compression are not touched. A request the server cannot be reached for gets a 502.

It starts when the launcher starts and the PC is set up (the certificate exists and is valid); a busy port or an expired certificate shows a message at the start (below). The kit sends everything the game sends, including your sign-in tokens, to the one address in `settings.json` and nowhere else, and keeps no log or copy of it. On a busy PC the HTTPS handshake with the game may take a while; the forwarder waits up to a minute for it (Kestrel's default is 10 seconds, which suits strangers on the internet, not this PC's own game).

### Player kit problems

- **"Could not listen on port 80 or 443"** at the launcher's start: another program uses the port (a web server, Skype, a local server of this project, a second copy of the launcher). Close it and start the launcher again.
- **"The certificate has expired"**: the setup window opens with that message; choose Set up, which makes a new one.
- **The game still reaches the official servers**: the hosts file has no block from setup (not set up, or removed): the setup window opens at the start. Some antivirus programs block edits of the hosts file; allow it or turn the protection off for the edit.
- **The game cannot connect**: check that the launcher is open and that you clicked Allow in the firewall prompt (Windows Defender Firewall, "Allow an app through the firewall", the game's exe).
- **The administrator window does not appear or you said No**: setup stops with a message; set up again. The certificate may already be installed: Remove undoes whatever was done.
- **A `settings.json` message** (not valid JSON, a key missing or still a placeholder, an `server_url` that is not `https://`, a name that is not a host name): fix the file; the player kit shows it at the start.

### Player kit tests

The tests (`tests/Resurgence.Tests/LauncherApp`: `HostsTests`, `PkiTests`, `ForwarderTests`, `KitSettingsTests`, `KitTests`) use temporary files and servers on this PC's loopback addresses only (`127.0.0.1`, and `::1` for the IPv6 fallback): the hosts block round trip on a temporary file (byte for byte), the name constraints of the authority (the extension, and that Windows refuses another name signed by the same authority), the leaf's key being non-exportable, the relay (method, raw target, query, body, headers, `X-Game-Host` set, `Host` dropped, the reply unchanged except for its length and `Alt-Svc`, a chunked body, `HEAD`, a dead server, the connection going to the IPv4 address of a name that has both and falling back to IPv6 for one that has only that) against a local test server, the HTTPS answer with a leaf whose key is in the key store (the test makes that key and deletes it again), the settings rules, and that only exactly `--hosts on|off` is the elevated copy. Nothing edits the real hosts file or trust list; setup, the administrator window and Remove are checked by hand on a real PC.

## Report a problem

When the game fails on a player's PC (it closes, never shows a window), one zip holds what is needed to find out why, instead of questions and commands in a chat. `Diagnostics` builds it, `ProblemReporter` saves or sends it, and `LauncherBridge` watches the starts (`BuildReportAsync`, `SendReportAsync`, `SaveReport`, `ReportConsent`, `LastRun` of `ILauncherBridge`). The screens that offer it are in [website.md](website.md); the server's side (storage, limits, the review channel) is in [server.md](server.md).

**What the launcher records.** `WhenGameExitsAsync` follows the process the launcher started last (see "Done hunting for now?" above; a game it did not start is found by its exe name, up to a minute late when Steam starts it) and, in the same one-second checks, looks for a visible top-level window of that process (`EnumWindows`, `GetWindowThreadProcessId`, `IsWindowVisible`). When the game is gone it keeps one `GameRun`: the start, how long it ran, the exit code (read from the launcher's own process handle; empty when Windows does not tell), whether a window was ever seen and the mode of that process (the retry after a 16010 reads `nosteam`). `runs.json` keeps the last 10. The watch ends when that process has exited (without a handle: when the exe is gone or the process found has exited). The run's **trigger** says why it looks failed, first match wins:

| Trigger | When |
|---|---|
| `nowindow` | no visible game window was ever seen |
| `exitcode` | the exit code is not 0 |
| `short` | the game ran less than 60 seconds |
| `manual` | not a run: the player pressed Report a problem |

A normal run has none. After a failed start the launcher sends the report by itself when the player agreed (`report_consent` is `auto`, set by the first-launch dialog and Settings); without that agreement (`unset` or `ask`) the "Done hunting for now?" window offers Save and Send, and Settings, Report a problem works at any time. Nothing is built or sent before one of these.

**What is in the zip** (`Diagnostics.Build`; the entry names are listed in the dialog and in `report.json`):

| Entry | Content |
|---|---|
| `game/debug.log`, `game/console.log` | the last 2 MB of each, from the start of a line |
| `game/cef.log` | the game's browser log (last 2 MB) |

| `game/.sentry-native/last_crash` | the game's last crash marker |

**The launcher's log.** The launcher writes `%APPDATA%\hunter-resurgence\launcher.log` (`LauncherLog`, next to `launcher.json`): a line per event, a time in UTC, the level and the text, then each exception with its type, message, stack and inner exceptions. It holds: the launcher's start (with its version) and its close (with the exit code), or, when an update restarts it (`LauncherUpdater.ApplyAndRestart` ends the process without closing the window), a line that says so first; the exceptions nothing handled: `AppDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException` (`WatchProcess`, first thing in `Program.Main`, so that a failure while the launcher starts is in it; not for the elevated `--hosts` copy, which writes no log) and the UI thread's, from the dispatcher's `UnhandledException`, which `Application.DispatcherUnhandledException` comes from (`WatchUi`, in `App.OnStartup`); they are only logged, the launcher closes or goes on as it would without; WebView2's `ProcessFailed` events (kind, reason and exit code); the forwarder running (the addresses), stopped (setup and removal) or stopping with the launcher when it closes, and failing to start (for example when a port is busy); every game process the launcher starts (its mode, and whether the game's log lock, goose call patch, rabbit sound patch and coat table patch were applied or why not, see "The log lock", "The goose call patch", "The rabbit sound patch" and "The coat table patch" under [What is real and what is mock](#what-is-real-and-what-is-mock); a start with Steam that quit with 16010 is logged with its code and seconds before the start without Steam) and the game's exit (code, seconds, whether a window was seen). `LauncherLog` is also the launcher's logging provider: only what classes in the `Resurgence.Launcher` namespace log at Information or above is written, nothing of the pages' server calls. **Scrub:** every text and exception message goes through the report's line scrub before it is written (a credential line is replaced as a whole, the Windows user name becomes `<user>`), and only then is the entry cut at 64 K characters (a credential is never cut in two). The frames of an exception's stack are not taken from its text (a type may override it and a caller may set a remote stack text) but written from each frame's own metadata (type, method, parameter types and names, file, line), cleaned of the Windows user name, with the word Token written `Tk` (a `CancellationToken` parameter is in every async frame, and the line scrub, which stays strict for every text, would take the frame for a credential). The report runs the same strict line scrub over `launcher.log` and `launcher.1.log` as over every text, and a Windows event is scrubbed before it is cut at 2000 characters. Events that name `msedgewebview2.exe` can also come from another program that uses WebView2: the report lists them all. A log that cannot be written is skipped, never an error. When an entry would take the file over 1 MiB the file becomes `launcher.1.log` (the older copy is dropped), so each file stays within 1 MiB and the launcher keeps about 2 MiB at most. The report dialog's texts (the notice `Data.Reports.Launcher`, the send dialog's `Report.Info` and the first-launch consent `Report.ConsentIntro`) name the launcher's log and the crash events of the launcher and WebView2.

The folder of the game's exe (`client_exe`) is only read.

**What is never in it.** `jwt.json` and anything outside the places above are never read. The one file that is not cleaned is the crash dump (it is a copy of the game's memory, so it may hold what the game held, a sign-in included; it goes in whole when the zip fits 5 MB, else it is left out). Every line of every text file that looks like a credential (a JWT, a run of 32 or more hexadecimal digits such as the game's session id, or one of the words token, cookie, bearer, authorization, jwt, secret or password) is replaced as a whole by `[line removed: it may hold a credential]`; the other lines stay. The Windows user name is replaced by `<user>` in every text (the profile folder in `C:\Users\name` or `\\share\Users\name`, the `%USERPROFILE%` path, the account name wherever it stands), the rest of the line staying. A text in UTF-16 (a byte order mark, or a quarter of its first 4 KB zero bytes that sit on one side, as in ASCII text) is decoded first so that its lines are scrubbed too, and is stored as UTF-8; any other file keeps its bytes. The Steam sign-in, the hosts file and the launcher's session are not read at all.

**A file that cannot be read** (missing, locked against reading, no rights, no game folder; a log the game is still writing is read anyway) never stops the report: it is listed under `missing` in `report.json` and in the dialog, and the rest is built. A probe that fails (the event log, Windows Management) is listed the same way. When the zip itself cannot be written (the temp folder is full, locked or not allowed) the report has no file: its path is empty, `missing` has `report zip`, Send answers `Report.ErrSave` without asking the server and Save throws `FileNotFoundException` (so does Save of a report that a newer one has replaced). The zip is at most 5 MB: over that, every file is cut to a quarter of its size, again and again until it fits (a few rounds at most).

**Send and Save.** Send is `POST /account/report` on the community server (the launcher's session cookie, `X-Requested-With: launcher`, `X-Report-Trigger: <trigger>`, the zip as `application/zip`); it answers a reference to quote (`p<account>-<8 hex>`) or a text key: `Report.ErrSignIn` (not signed in, or 401), `Report.ErrFormat` (400), `Report.ErrSize` (413), `Report.ErrLimit` (429: one at a time, five in 24 hours), `Report.ErrDisk` (507), `Report.ErrSave` (the zip file is not there), `Report.ErrNetwork` (no answer or anything else, and without `server_url`). Save copies the zip to the player's Downloads folder (the one Windows says) and returns the path. After Send the dialog shows the reference alone in a read-only monospace box with a Copy button (the clipboard call of the Steam launch option dialog, `shell.js`; the button says "Copied" for 2 seconds, and when the clipboard refuses the text stays selectable) and under it "Give this reference on Discord". After Save the path has an Open folder button: `ILauncherBridge.ShowFile` opens Explorer with the file selected (`explorer.exe /select,`), `Report.ErrShow` when the file is gone or Windows refuses.

**Logfiles.** Settings, Logfiles opens the folder of the game's exe in Explorer, where the game writes its logs (see [Settings: folders and caches](#settings-folders-and-caches) when it is missing).

## The install check

`InstallChecks` (`ILauncherBridge.CheckInstallAsync`) runs eleven read-only checks of the game's install and returns one `InstallCheck` each (`Id`, `Level` ok, warn or block, `Text` a Strings key, `Args` for its placeholders, `Fix` the button the dashboard offers), in this order: `game`, `version`, `files`, `path`, `steam`, `setup`, `windows`, `disk`, `display`, `running`, `dlls` (the number of a row below is the order the checks were added in; `display` is row 11 and comes after `disk`). The launcher runs it when it opens (the dashboard shows "Game check: OK" or the problem with its fix button) and the start runs its blocking part again, with `display`; the problem report carries the results. Nothing is ever written into the game folder; the one fix that writes, `fix-display`, writes the graphics file in %APPDATA%. ## Settings: folders and caches

The Settings menu's folder and cache entries are `ILauncherBridge.OpenFolder(kind)` and `ClearCache(kind)`, which return a `Result`: nothing is shown on success, and a failure is a text key the menu shows in a message. Nothing reaches the mock. The game folder is a window instead, opened from Game settings (see [website.md](website.md): the Settings menu): it also uses `ChooseGameFolder()` and `UseAutomaticGameFolder()`, and shows a failure in the window.

| Entry | What it does |
|---|---|
| Game folder (`game`) | the window's "Open folder" button opens the game folder, where the game is installed. When `client_exe` is in a subfolder, that is the folder above the exe's own (Logfiles opens the exe's). |
| Logfiles (`logs`) | opens the folder of the exe, where the game writes its logs. |
| Screenshots (`screenshots`) | opens `Pictures\<product>\Screenshots`, where the game writes its screenshots (the Pictures folder is the one Windows says). The game creates the folder with its first screenshot; until then the launcher opens the nearest folder above it that exists (`Pictures\<product>`, then Pictures) instead of failing. |
| Clear launcher cache (`launcher`) | the launcher's own browser (WebView2) drops its disk cache and its cache storage while it runs (`ClearBrowsingDataAsync`); cookies, local storage and settings are kept. The call is not awaited: the menu answers at once, and a browser that is not up yet or fails is not reported. |
| Clear game cache (`game`) | deletes the cache folders of the game's in-game browser under `%APPDATA%\<product>`: in each of `cache`, `cache_local`, `cache_dev` and `cache_beta` (the game picks one by the server it connects to), and in its `Default` folder: `Cache`, `Code Cache`, `GPUCache`, `DawnGraphiteCache`, `DawnWebGPUCache`, `GrShaderCache`, `ShaderCache`, `GraphiteDawnCache`. Cookies, local storage, session storage and the settings files are never touched. A folder that cannot be deleted does not stop the others. |

`<product>` is the name of the client's exe without its extension; it is the name of the game's own folders in `%APPDATA%` and Pictures.

Failures: `Settings.NoFolder` (no game found, the folder does not exist, or the kind is unknown; nothing is opened, and a game cache that is not there is not an error), `Settings.CacheGameRunning` (Clear game cache is refused while the client's exe runs: the browser has its files open) and `Settings.CacheFailed` (a game cache folder could not be deleted, or the kind is unknown).

Tests: `FolderActionTests` (temporary install, `%APPDATA%` and Pictures folders: every kind opens the right folder and a missing one opens nothing; the screenshots fall back to the nearest parent; the game cache loses only its cache folders in every profile root and keeps cookies, local storage and settings; refused while the game runs and without a game; a locked folder is reported and the rest still cleared; the launcher cache calls the browser).

Game settings changes only the values you edit. Every other byte of both files stays as it was, and no line is ever added. A file with an unknown format is left alone. The game reads both files once at start, so Save is refused while the game runs. The game writes the options file itself but never the graphics file (the old launcher wrote it; without one the game runs on built-in values): when it is missing the dialog shows defaults (windowed at the desktop's resolution and refresh rate, medium quality, vertical sync on) and Save creates it, 12 lines with CRLF line ends, the three after vertical sync 0. A missing options file only hides the contextual help switch.

**Game language and units** (Game settings, below the options of the files). *Game language* lists the 22 languages the game ships (`GameLanguages`: `en_US`, `de_DE`, `es_ES`, `et_EE`, `fr_FR`, `hr_HR`, `hu_HU`, `nl_NL`, `pl_PL`, `pt_BR`, `pt_PT`, `ru_RU`, `sv_SE`, `da_DK`, `cs_CZ`, `nb_NO`, `it_IT`, `fi_FI`, `tr_TR`, `sl_SI`, `ka_KA`, `ro_RO`) by their own names ("Deutsch", "Français", …). It is not in the game's files: the game takes it from the `lang` segment of the launch URL and reads it once at its start. The launcher saves the choice in `launcher.json` (`game_language`) and sends it as `lang` with every start (`ServerServersService`: a hunt, a tutorial, hosting and joining a multiplayer game), and the server puts it in the launch URL ([server.md](server.md#sign-in-and-tokens)). Before a choice it is the launcher's own language when the game has it (`GameLanguages.For`: `fr` is `fr_FR`, `pt-BR` is `pt_BR`, bare `pt` Brazilian, `no` and `nn` `nb_NO`), else `en_US`; a code the game does not have counts as no choice. Switching the launcher's language sets it again, even after a pick here (see [Languages](#languages)). *Units* (Metric or Imperial; only for a signed-in player) is the account's setting, on the server so it follows the player to another PC (`IAccountService.SetImperialAsync`: `POST /account/settings`, [server.md](server.md#sign-in-and-tokens)); the game's connect carries it as `account.use_imperial`, and it is read at the game's next start. The launcher's and the website's pages show the same choice (`Session.Imperial`, from `GET /auth/me`): the shot distances, the weight of a score sheet and the ranges of the boards put yards and pounds first, the metric value in brackets (the distance travelled stays in km and miles, as both are shown already).

**Unverified in game:** the game's own locator file spells three languages `se_SV`, `no_NO` and `si_SI`, while the game's localization list (the connect's `localization.languages`) and `GameLanguages` spell them `sv_SE`, `nb_NO` and `sl_SI`. Which spelling the game matches for Swedish, Norwegian and Slovenian is not verified in game; if one of them shows English, change its code in `GameLanguages` and in the server's `GameTokens.GameLanguages`.

**Display mode.** The game itself knows two window styles only, windowed (title bar, centred in the work area) and exclusive fullscreen, chosen by the fullscreen flag of its graphics file. Game settings offers three: **Borderless** (the default), **Fullscreen (Exclusive)** and **Windowed**. Borderless is a window over the whole monitor without title bar or border: Alt+Tab, a second monitor, the launcher and overlays work as with a window, and leaving the game never resets its graphics device. The choice is kept in `launcher.json` (`display_mode`, as text: a value the launcher does not know reads as no choice), since the file only knows fullscreen on or off. Until the player chooses, a file that says fullscreen (or no file) shows Borderless and a windowed file shows Windowed; the first start saves that mode as his choice, because a Borderless start writes the file windowed. In Borderless the dialog hides the resolution list: the game runs at the monitor's current resolution and refresh rate, which Save writes (windowed); Fullscreen writes the fullscreen flag and Windowed clears it, with the resolution chosen. The tutorial page's Fullscreen box means any full screen: ticked keeps an exclusive choice and is Borderless otherwise, and its resolution list is hidden while it means Borderless.

Nothing else is read from or written to the game's folders, except that Settings, Clear game cache deletes the game's cache folders in `%APPDATA%` ([Settings: folders and caches](#settings-folders-and-caches)). Steam's registry keys and the Steam library files are only read; the one write into Steam's files is the game's launch option, with the player's OK ([Start it from Steam](#start-it-from-steam)).

## Start it from Steam

Install the launcher with `HunterResurgence-win-Setup.exe` from the [latest release](https://github.com/yinyin99/hunter-resurgence/releases/latest). It installs for your user only (no admin prompt) into `%LocalAppData%\HunterResurgence`, adds shortcuts and an Add/Remove programs entry, and registers the link `hunter-resurgence://` for your user. Windows may warn that the Setup is not code-signed: choose **More info**, then **Run anyway**. To remove it: Windows Settings, Apps, Installed apps, Uninstall; or `%LocalAppData%\HunterResurgence\Update.exe --uninstall`.

**Steam's Play button** (`SteamOption.cs`, `SteamVdf.cs`, `SteamOptionModal.razor`). The official servers are closed and the game's own launcher, which Steam opens on Play, cannot reach a server by itself: it needs this launcher. With the player's OK the launcher tells Steam to open it instead: it changes one setting of this game in Steam (its launch options), nothing else: not other games, not Steam itself, not the game's files. The player can see it in Steam: right-click the game, Properties, Launch options. Steam must be closed while the setting is written, because Steam saves its own copy when it exits. Uninstalling the launcher puts the setting back.

- **The line** is `"<install folder>\<exe>" %command%` with the exe at the root of the Velopack install folder (`VelopackLocator.Current.RootAppDir`), which stays the same across updates, not the one in `current\`. A launcher that the Setup did not install (a development or unpacked copy) says so and offers the Copy line only.
- **Where**: `<Steam>\userdata\<account>\config\localconfig.vdf` of the signed-in user (`ActiveProcess\ActiveUser`), else of the user whose file changed last; key `LaunchOptions` directly in the app's block (`steam_app_id`) under `UserLocalConfigStore/Software/Valve/Steam/apps`; the key is inserted when absent, the app's block too. It is a text edit of that one value: every other byte of the file stays. A copy of the original, `localconfig.vdf.launcher-backup`, is kept next to it before the first write. A file that does not parse (quotes, braces, key/value pairs, UTF-8) or has no `apps` block is left alone and the dialog says so with the Copy line.
- **Steam running**: the dialog asks to close it; the launcher runs `steam.exe -shutdown`, waits up to 30 seconds and never kills Steam (it then says to close Steam by hand). When the launcher had closed a running Steam, it starts Steam again by itself after the write (`steam.exe -silent`) and the dialog says so; a Steam that was not running stays closed (the launcher starts it when the player presses Start).
- **At every start** (the Splash, after the older-setup and player-kit dialogs) the launcher reads the option. When it is not ours (never set, or Steam or the player changed it) the dialog opens, at most once per 24 hours; its **Don't ask again** check box, with **Not now** or **Copy the line instead**, stops the offers for good (`launcher.json`: `steam_option_never`, `steam_option_asked`). The Settings item **Use Steam's Play button** opens the same dialog at any time. A launch option of the player's own is shown in the dialog and only replaced by **Close Steam and set it**; the dialog's **Copy the line instead** shows the line with a Copy button.
- **Uninstall** (Velopack's before-uninstall hook, after the other steps because it may wait for the player and for Steam): when the option is still our line it is replaced by the previous one (`steam_option_before` in `launcher.json`, in the file noted in `steam_option_file`) or removed when there was none; a changed option is left alone. A running Steam is closed first after a Yes/No question (default No: then the option stays and the player removes it in Steam).

Tests: `SteamOptionTests` (temporary vdf files: write, other bytes and other apps unchanged, insert, restore, unparseable file left alone).

Press Play in Steam. The game's own files stay untouched. On its first start the launcher asks to set up this PC for the community server ([The player kit](#the-player-kit)); keep it open while you play.

## Install, update and the link

- **Velopack** (`Program.cs`) runs first in `Main`: it handles the install, update and uninstall steps of the Setup and applies an update that was downloaded earlier when the launcher starts. A launcher that was not installed by the Setup (`dotnet run`, an unpacked build) never updates itself and shows no update.
- **The update** (`LauncherUpdater`) checks the releases of this repository at start (`GithubSource`, no pre-releases), downloads a newer one in the background (the patch bar shows it as a launcher update) and then shows the "launcher updated" message; its OK button applies the update and restarts the launcher. Nothing is checked, shown or applied while the game runs (`GameFiles.ClientRunning`), and a feed, download or checksum that fails leaves the installed version as it is, without a message. After the update's restart (Velopack's `OnRestarted` hook, `Program.Restarted`) the new window is brought to the front once (`LauncherUpdater.ShouldActivate`: restarted and the game not running); when Windows refuses, its taskbar button blinks.
- **The link** `hunter-resurgence://open` (`LinkScheme`) is written by the Setup and removed by the uninstall, under `HKCU\Software\Classes\hunter-resurgence`: Windows starts `resurgence-launcher.exe "hunter-resurgence://open"`. One launcher runs at a time: a second start (the link, a shortcut, Steam) brings the open window forward and exits. The elevated `--hosts on|off` copy is not a second start: it runs on its own.

### Install and uninstall

**The first start after the install** (Velopack's first-run hook, `Program.FirstRun`; `Cleanup.cs`) looks in fixed places for what an older setup left and shows one dialog, **Older setup found**. Nothing is deleted before the player chooses **Delete**; **Not now** leaves everything. Nothing outside the list below is touched.

| Found | Where | What happens |
|---|---|---|
| An older player kit setup: the hosts block, the authority `Hunter Resurgence local CA`, the leaf and its key | the hosts file, the current user's trust list, `%LOCALAPPDATA%\hunter-resurgence-play` | Shown as kept when it fits this version (the block has the names in `settings.json`, in any order, other lines do not matter; the leaf is valid, has exactly those names and is signed by the trusted authority), else as replaced: the setup window that follows opens with the reason and replaces all of it in its one hosts prompt. |
| A running `play.exe` (next to a `settings.json`) or a `resurgence-launcher.exe` that is not this install | any process | Listed; Delete asks it to close and stops it if it does not within a few seconds. |
| Old unpacked folders `launcher-win-x64` and `play-win-x64`, each with its exe still inside | Downloads, the desktop, the folder above a running old program's folder | Listed; Delete removes each with everything in it. |
| Stray game logs: `*.netlog`, `cef.log`, an empty `icons` folder | the game's install folder itself, never inside the game's own `game` folder | Listed; Delete removes them. |

If the player said No at the certificate prompt of a setup, no leaf is left (it is written last): the next start finds no setup and shows the setup window again.

**The uninstall** (Velopack's before-uninstall hook, `Cleanup.Uninstall`) removes the hosts block (the file is then byte for byte what it was before setup), the leaf and its key, the authority and the link scheme. Each step runs on its own: one that fails does not stop the others. Windows may ask in the hook (administrator permission for the hosts file, and to remove the authority); the hook has 30 seconds. If you say No, remove the block yourself (the lines between `# >>> hunter-resurgence play` and `# <<< hunter-resurgence play`) or run Settings, Remove the setup before uninstalling. The hook also asks, in a Yes/No box whose default is **No**, whether to delete `%APPDATA%\hunter-resurgence` (`launcher.json`, `session.dat`); No, closing the box without an answer and the 30 seconds running out all keep the data. The question is in the Windows display language. The game's files are never touched.

Tests: `CleanupTests` (temporary folders, hosts file, certificate store and registry key).

## Languages

The UI has 19 languages (`Languages.All` in `src/Ui/Languages.cs`): English, French, German, Spanish, Portuguese (Brazil), Russian, Italian, Dutch, Polish, Portuguese (Portugal), Swedish, Danish, Norwegian (bokmål), Finnish, Czech, Hungarian, Romanian, Slovenian and Turkish. All texts are .NET resources in `src/Ui/`: `Strings.resx` (English, also the fallback) and one `Strings.<code>.resx` per other language. The French texts are the original French of the old screens; the few new texts are in our own French.

Game vocabulary (animal names, collectables and a few labels) is not written by hand: the resx keys `Term.species.<id>`, `Term.collectable.<id>` and `Term.ui.<name>` hold one text per old id and language. A service passes the id (the mocks pass the English name, which is matched to its term); a text without a term is shown as it is. To add a language, add its texts to `Strings.<code>.resx` the same way and list it in `Languages.All`.

A text is a whole sentence: a link or bold part is a hole, never markup in the resx. `{0}...{1}` wrap the words (`L.Html`), or one hole is the whole link or name (`L.Frag`); a translation may move the holes. Counts are written without a plural noun (`Games shown: {0}`), so one string fits every number.

At start the launcher uses the language saved in `launcher.json`, else the Windows display language when one of the 19 matches (`Languages.Match`: the region is ignored, so `de-AT` is German; bare `pt` is Portuguese (Brazil); `no` and `nn` are Norwegian bokmål), else English. The player kit's texts are the `Kit.*` keys and `Settings.KitSetup`/`Settings.KitRemove` of the same files. A test (`tests/Resurgence.Tests/LauncherApp/TranslationsTests.cs`) checks that every other language file has the same keys and the same `{0}` placeholders as the English one, and that no key keeps its English text in all 18 (names such as `App.Name` are listed in the test). Native speakers are welcome to check any of the `src/Ui/Strings.<code>.resx` files.

Choosing a language (the language dialog or Settings; both go through `LauncherLanguageSwitcher.Set`) saves it in `launcher.json`, sets the game's language (`game_language`) to the matching one of the game's 22 when the game has it (`GameLanguages.Match`; else it stays as it is; a pick in Game settings holds until the next switch), makes it the process's default culture and reloads the page: the same page shows in the new language, still signed in, with the dialog closed. Only `CultureInfo.DefaultThreadCurrentCulture`/`DefaultThreadCurrentUICulture` are set, never `CurrentCulture`/`CurrentUICulture`: an assignment to those on the UI thread would keep it on the old language. For the same reason the launcher sets WPF's switch `Switch.MS.Internal.DoNotUseCulturePreservingDispatcherOperations` in `Resurgence.Launcher.csproj`; without it WPF writes the UI thread's culture back after every dispatcher operation, which keeps the language of the start.
