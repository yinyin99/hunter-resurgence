# Restore library

`src/Restore` (`Resurgence.Restore`) reads a backup zip made by any version of the [backup tool](backup.md), or by another community tool ([below](#backups-of-other-tools)), and returns a neutral player model and a report (layer A). It has no database and no server types. Storing the model is layer B, in the server (`server/Server/Restorer.cs`, [below](#storing-the-model)), in SQLite ([ADR 0001](adr/0001-sqlite-for-profiles.md)).

## Run it

`server import backup <zip> [--account <id>]` restores a zip into the server's database and prints the report: [docs/server.md](server.md#import-a-backup-zip). It reads the zip with the server's own item catalogue (an `Application/application` reply, never the one inside the zip being read) so the units rule is exact; without a catalogue the rule is `zero-only`. A zip the reader refuses prints `refused: <reason>`; a file that cannot be read prints `cannot read: <message>`; both exit 1.

In code: `Importer.Read(path or stream, catalogue, limits)` returns `Restored(Model, Report)` or throws `RestoreException`; `ApplicationCatalogue.Read(stream)` is the catalogue. `Importer.FromReplies(uid, handle, replies, catalogue)` does the same for a public profile whose replies are kept elsewhere (no zip): each `ArchivedReply(Path, Endpoint, Params, Status, Body)` is one reply file as a public-mode zip would hold it. The manifest is made up (format 2, mode `public`, identity `handle`, the uid and handle), the bodies are parsed with the zip's JSON caps, a body that is not JSON goes to `Rejected`, and the replies are mapped like a public zip's (the report mode is `public by handle` when a `Public_user/getByHostname` reply is among them). A `uid` that is not digits within an id throws `RestoreException`.

## What is refused, what is rejected

The backup zip is read once, in memory; nothing is extracted (a picture or score sheet page is checked against its hash and only its name is kept: the server reads its bytes when it stores it, [below](#pictures)). The whole backup zip is **refused** when it breaks a cap (`Limits`: 100,000 entries, counted in the zip's central directory before it is opened, which may hold 64 MiB at most, 1 GiB of content, 64 MiB per entry, 32 MiB for the manifest, 128 MiB of JSON in total, `manifest.json` included, and 32 MiB per JSON entry (a real backup holds under 4 MiB of JSON), JSON nesting 64, more than 100:1 compression for an entry of 1 MiB or more), has an unsafe entry name (`..`, a rooted path, a drive letter, a backslash), matches no known format (`not a backup zip`: no `manifest.json` and no `index.json` with section files, [below](#backups-of-other-tools)), a manifest that does not parse (a duplicate key included), a `uid` that is not digits only or too large for a 64-bit id, no `claim.key` or one that does not hash to `claim_hash`, a `format` newer than 2, or an identity reply whose `id` is not the manifest `uid`. A single file is **rejected** (and reported) when its SHA-256 differs from the manifest or it is not valid JSON (a duplicate key included); a file the manifest does not list is rejected too. Manifest entries with an `error` or no `sha256` are missing data, listed under `failed`, not a fault of the backup zip.

Our `manifest.json` may sit at the root or one folder down (a folder zipped instead of its content); the other files are then looked up in that folder. Deeper than that, or a `.zip` inside the zip, the zip is refused, and an upload says so in words the player can act on: choose the zip the backup tool made, as it is ([server.md](server.md#upload-a-backup-zip)). The server's log line of a refused zip gives its size and its first five entry names.

## Version and mode

No `format` in the manifest = format 1 (defined in [backup.md](backup.md#what-is-saved)); `format: 2` adds `mode`, `identity`, a per-file `date` and `checks`. `tool_version` is copied, never compared. The mode comes from the files: `Me_me.json` present = my account, otherwise public (by handle when the `Public_user/getByHostname` reply is there, else by id). A manifest `mode` that disagrees gives a warning and the files win.

## Backups of other tools

`Importer.Read` picks the reader from the zip's own files, never from what an upload says of it: the table `Importer.Formats` pairs each format's `IsOne` check with its reader, the first match reads, and a zip that matches none is refused (`not a backup zip`). Every reader only turns its files into the saved replies the mapper reads (the same `SavedFile` list `Importer.FromReplies` builds), so the mapping, the field rules and the restore are shared. The entry count, the central directory's size and the entry names are checked once before any reader; the byte, JSON and compression caps apply as each reader reads an entry. A new format is one line in the table and its reader.

**The format decides only the parser, never the trust.** A zip without our manifest has no Steam id and no claim hash: its `Identity.SteamId64` and `ClaimHash` stay null whatever its files say, so an upload of it is never a Steam match and always waits for an operator ([docs/server.md](server.md#upload-a-backup-zip)), like any upload.

**One file per API section** (`SectionBackup`): a folder at the root of the zip or one level down with `index.json` (`user_id`, `handle`, `captured_at`, `files`) and a `json_<section>.json` for each section, each the original server's reply as it came. A second folder in the zip (a converted copy for another server) is ignored, like anything outside the folder with the `index.json`; a second folder that also holds an `index.json` and a section file makes the zip ambiguous, and it is refused. The `user_id` is checked like the manifest's `uid`. The identity's format is 0 and `complete` is `unknown`; the handle is the index's and `captured_at` the start time. A file in the folder that is no `json_<section>.json` is rejected (`not a section file`), a section the index does not list is rejected (`not listed in index.json`) and a listed file that is not in the zip is missing; the zip holds no checksum to check and no picture. **A public profile of the same tool** is a folder `<tool>_public_<handle>` (at the root or one level down) of `json_<section>.json` files **without** `index.json`, and is read by the same reader. The handle is the folder's suffix and must be the `hostname` of its `json_profile.json` (another handle is refused); the user id is that file's `id`, or the v2 profile's (`json_v2_profile.json`); a save with no readable id is refused. It has no `me` section, so it is a public save: mode `public`, no wallet, no Steam id, and it always waits for the operator. Its `competitions_previous`, `competitions_list` and `competitions_league` become the replies of `Page_content/list_previous_competitions`, `list_competitions` and `list_community_league_competitions`; `competition_pages` (an object keyed by competition id) one `Page_content/competitions_new` reply per id (param `competition_id`); `lodge_contents` (keyed by lodge id) one lodge row per id, as `lodge_<id>`. The server only keeps the competition replies as saved (no page of it reads them yet). The other sections (`competitions`-less lists such as `campaign_competitions`, `challenges_all`, `expedition_current`, `leaderboard_current`, `lodge_catalog_*`, `lodge_slot_types`, `lodge_weapon_slots`, `results`, `scoresheets`) stay in `Extras` under their file name. On an account that already has the same profile from an archive claim, approving it adds what the claim lacked (hunts and their details, gallery, competitions, lodge contents) and replaces nothing ([server.md](server.md#upload-a-backup-zip)).

## Field rules

- **Items**: `Inventory/list` wins over `Inventory/dict` for a row both hold (the dict can lag a change); a difference in `metadata`, `units` or `dir` is a warning. `Units` is the saved value only when the item catalogue the caller passes (`IItemCatalogue.HasUnits`) says the item has units (a count, as climbing gear has), otherwise null (a placeable has none, whatever number the dict holds, 0 or 1). Without a catalogue: 0 reads as null, every other value is kept, and the report says `zero-only`.
- **Positions**: `round(value * 1000)` per axis, from the number's decimal text (never a double), half away from zero. A coordinate beyond ±2,000,000 (or not a number) means no location, with a warning. A placed row (slot 23) without a position is a warning and goes to `Extras`, not to `Items`; a position without a direction keeps the direction null, with a warning. `metadata` is kept as sent (a feeder's `metadata.reserve` is never renumbered, integers stay integers).
- **Skills** as sent (level plus progress); `SkillSet.Floor()` gives the levels. **Wallet** from `Me/me` (`ems`, `gms`), own backup zips only. **Statistics**: the four `data` objects, `distance`, `duration` and the two minigame scores. **Achievements** one to one, with their `triggers` (earn times). **Trophies and lodges** as raw rows; a harvest reply with status 404 means none. So does one without a status whose body is not a harvest record (a JSON object with at least one member and none of `message`, `error`, `errorCode`). A backup run killed before it wrote its manifest can leave a 404 that way once a later run resumes it. Such a file is kept in `Extras`, with the warning `<n> harvest file(s) without a status hold no harvest record: not restored as trophies, kept in Extras`.
- **Account defaults** for the fields of the game's login reply that no web reply holds. **Membership**: `freeplay` 0, `staff` 2, `premium` 1 and `freebeta` 0 (these two inferred, flagged in the report), anything else 0 with a warning.
- **Shapes**: where an object is expected (the manifest's `checks`, a `Trophy/list` or `Page_content/minigames_list` reply, its `position`, an item's `location`), an empty `[]` reads as empty (this API sends `[]` for an empty map) and any other non-object is not read, with the warning `<what> is not an object: not read`; the rest of the reply is still read. An `Inventory/list` element that is not an object (other than `null` or `[]`), and the `own` rows of an element whose `item` is not an object, go to `Extras` as inventory rows not read.
- Every other reply (hunts, messages, friends, missions, competitions and the rest) is kept whole in `Extras` and counted under `unsupported`, one line per endpoint with the ids in its path shown as `*` (`/game/user/*/ranks`); "no entry" answers (status 404, such as a leaderboard the player is not on) are counted on one line of their own. Derived files (`map-setups.json`, `messages-index.json`, `competition-history.json`) are checked but not used: the raw replies decide.

## Report

`mode`, `complete` (`yes` = `completed_utc` present, `no`, `unknown` for a format 1 backup zip without it), the units rule used, and the lists `restored`, `unsupported`, `missing` (for example the wallet of a public backup zip, or the hunts `checks.hunts` says were saved short or whose list did not load completely, `list_failed`), `warnings`, `failed` and `rejected`. The same backup zip always gives the same model and report (items by item id, then guid).

## Storing the model

`Restorer.Import(state, zipPath, account, dataDir)` turns the model into the rows of one account in one transaction: `ClearModel`, the inserts, the audit row. The same zip always gives the same rows. Any zip is accepted and replaces the account's profile (no merge); hunt history stays. Before replacing an existing account the whole database is copied with `VACUUM INTO <db>.bak-<UTC time>`. Every imported zip is kept as `restores/<account id>/<SHA-256>.zip` in the data folder, so a disputed account can be reset and imported again.

| Model | Rows |
|---|---|
| `Items` | `items`. `Units` as read (layer A applied the catalogue). A placed item's `Position` and `Direction` (millimetres) go into its metadata under `__position` and `__direction` (the table has no columns for them); the connect reply moves them back to the row's `position` and `direction`. `WebReserve` goes into it as `__reserve` (the connect row has none; `Inventory/list` shows it as the `location`'s `reserve`) |
| `Wallet` | `wallet` (`em`, `gm`); a zip without one (a public zip) stores 0 em. The gm is never under 15,000 (`Restorer.GmFloor`, the same as a new account's): the restore raises a lower one, and the report says `wallet: gm raised from <old> to 15000` (a zip without a wallet: the dropped list says what was stored). Every start item id (`start.items` of the facts file) the restored items lack is added like a new account gets it, and the report says `start items added: <n>`. It holds for every restore: the command, an approved upload and any other that goes through `Restorer.Apply` |
| `Skills` | `skills`: weapon by item id, tracking and spotting by species slot; `xp` is `Skills.Xp(level plus progress)`. A zip without skills stores a new player's 59 + 59 |
| `Profile`, the zip's own `Me/me` | `profile`: the reply of `Me/me` without `ems`, `gms` and `unread_messages`, over the typed profile fields (`id` and `handle` are the account's) |
| `Stats` | `statistics` |
| `Achievements` | `achievements` (earn times in `triggers`). On a community server the check right after it adds the earn time of each threshold the account's statistics reach that has none, and a larger counter as `value` ([docs/server.md](server.md#achievements)) |
| `Trophies`, `Lodges` | `trophies`, `lodges` as read |
| `Extras` | `extras`, keyed by the path in the zip; the saved loadouts (`game_user_loadout.json`) are also read into `loadouts`, one row each under a new id ([docs/server.md](server.md#loadouts)) |
| `Account`, `Profile` | the account's `account` object (the connect reply's): handle, `user_id`, `account_id` (= the user id), hostname, gender (the listed avatar's when the profile's picture is one, else the profile's), hunterscore, membership, avatar URL (this server's address of the avatar (`<game host>/media/avatar/256/<id>.png`) when the profile's address is an avatar of the list below; else the link of the picture the zip holds as the account's imported avatar, `<game host>/photos/<account id>/avatar.jpg`; else the default avatar's address: [docs/server.md](server.md#avatars)), the importer's defaults for the Facebook fields, and `face` (a 3D head: `1000000 + id mod 1000` of the avatar below, else the default head of the gender; `avatar` and `avatar_id` where the account has them hold the avatar's id itself): the id of the avatar of the server's recorded `Avatar/getAvatars` list whose picture address's path the profile's avatar address's path ends with (any host), else the default avatar `1000000`; the report says `avatar <id>` or, when the profile has an address that no entry matches, warns that the default is kept. Without a list (the command line importer) the default stays and nothing is reported. On a community server the hunterscore is then the one the server computes from the restored statistics ([docs/server.md](server.md#the-hunterscore)), in `account` and in the profile |

What is dropped, and the report says so: the e-mail, Facebook id and other login-only fields (accounts keep none); keys named `email`, `first_name`, `last_name`, `real_name`, `address` and `phone`, anywhere in a stored reply (counted in the report); the zip's Steam id and claim hash (a Steam id match is shown to the operator as information, is not proof of ownership, and an account's `steam_id64` is only one the server verified).

The target is the zip's user id, created from the zip's handle (`user-<id>` without one) when it does not exist; a handle that another account has refuses the import. `--account <id>` targets an existing account, whatever the zip's user id: the account keeps its id and takes the zip's handle only when nobody else has it. A local server (`offline_mode` true) with no `--account` restores into the local account, the one the game connects as.

On a community server the same rows come from an upload, not from the command: an uploaded zip is kept for an operator and never restored automatically; the operator's `review approve <id>` restores it once per game user id, the account adopting the zip's handle, and its user id too while it has not played: an account that has played keeps its own and its hunts stay ([docs/server.md](server.md#upload-a-backup-zip)). The database is not copied there. A player can also claim a public profile from the operator's archive (`Importer.FromReplies` reads its saved replies like a public zip): the same rows are written onto the account, whose user id never changes ([Archive claims](server.md#archive-claims)). Either way gm$ ends at 15,000 at least.

An account with a `profile` row is a restored account. For it the server answers from its rows, not the recorded reply: the connect reply's `account`, `inventory`, `wallet`, `skills`, `user_stats` (statistics, achievements with their earn times, minigame scores, `first_time` 0), `account_info` (`steam_id` is the account's verified one or empty; no e-mail) and the `network` handle, host and user id; `Me/me`; `Skill/list`, `Statistics/total` and `Achievement/stats` for the account's own user id (on a community server `Statistics/total` answers any account's, [docs/server.md](server.md#public-reads)); and on a community server the trophy list, the trophy and lodge pages and the harvest records of the account. The restored statistics are a base: `user_stats` and `Statistics/total` add the account's server hunts (the open one so far) on top, and a later restore replaces only the base ([docs/server.md](server.md#the-statistics)). Everything else of those replies still comes from the recording on a local server: the world data, `boost`, `competitions`, `inventory.infos` and `active_services`, the expedition, and the other profile reads (missions, friends, the apiv2 profile). Accounts without a `profile` row keep today's answers on a local server. A community server never answers from the recording what is a player's own: see [Recordings on a community server](server.md#recordings-on-a-community-server).

**Missions.** The saved `Mission_missions.json` stays in `extras` and is copied into the account's mission rows at the restore (and, for an account restored before, on its first mission call): completed and active missions with their finished objectives, the switches and the favourite mission packs ([docs/server.md](server.md#missions)).

**Challenges.** The saved `Challenge_get_user_challenges...json` stays in `extras` and its completed challenges are copied into the account's `challenges` rows at the restore, as saved ([docs/server.md](server.md#challenges)).

**Hunt history.** The hunts of the backup zip are read from the saved replies in `extras` when asked, with no table of their own: `Expedition/list` lists the server hunts first and then the saved hunts as saved (every saved `Expedition/list` page joined by its `offset`, each hunt once) as one paged list whose `total` counts both, and `Public_user/expedition` with a saved hunt's id answers the saved reply. Without `expedition_id` it answers the account's latest server hunt, else the newest saved one. A zip that saved no hunt keeps the recorded answers. A hunt list saved short (`checks.hunts`) lists what it holds. Saved hunts are shown only: the statistics and the hunterscore already hold them ([docs/server.md](server.md#the-statistics)). A saved kill whose picture or score sheet page the zip holds is linked to them ([Pictures](#pictures)).

## Pictures

The files of the zip that are no JSON reply (`photos/`, `kills/` and `images/`) are named by layer A and checked like every file (the SHA-256 of the manifest, the caps of `Limits`: 64 MiB an entry, 1 GiB in all); `Restored.Media` lists each by its path and its entry in the zip, and layer A's report line `pictures and score pages` counts them and the restore's own report line says what was stored: `pictures stored: gallery <n>, kill photos and score pages <n>, avatar and background pictures <n>`, with, when a gallery entry's file is not in the zip, `pictures from links: <n fetched> of <n without a file>` at its end (and `<n> gallery pictures already in the gallery` for the pictures the account already had). A `photos/` file that no saved gallery entry names is not stored (it stays in the kept zip). `Importer.MediaPath(folder, url)` is the path the backup tool gave the picture of a link: the folder, then the host and the path (no query) with every character outside `A-Z a-z 0-9 . _ = -` as `_`. A file whose hash does not match is rejected, not named.

The server stores them after the rows are committed (`State.PreparePictures` inside the transaction, `State.Unpack` after it; a restore that fails writes no file), into the account's photo folder, `photos/<account id>/`, the folder and the links of a photo taken here:

| `photos/<file>` of a saved `Gallery/list` entry (matched by its `url`); when `photos/<file>` is not in the zip, `kills/<file>` is used (a zip of backup tool 0.9.0 held the picture only there) | `<id>-<type>-<token>.jpg` (the token of [docs/server.md](server.md#gallery)) and a `photos` row (`saved` holds the entry's details: `animal` the species, `label` its label else its kill's score, and, when it has one, `kill_id`. A real `Gallery/list` entry's `animal` is the kill, an object `{scoreType, species_id, score, id, species}` (null for a camera photo, `label` null), read from it; a plain text `animal` is the species. | `kills/<file>` (a kill's photo, matched by the `kill.photo` link of the saved hunt) | `kills_<file>` | the `photo` of that kill in `Public_user/expedition`, now the server's link; a kill whose picture is not in the zip keeps the saved link |

A restore again deletes the account's restored gallery rows and files, `avatar.jpg` and every `kills_` and `images_` file first, then unpacks the new zip's; the photos taken on the server stay. Delete my data removes the folder with the account ([docs/server.md](server.md#upload-a-backup-zip)). The bytes are copied from the zip entry to the file as they are, never held whole.

**Pictures from links.** A saved gallery entry (`Gallery/list`, `Gallery/list_all`; an entry is an object with details, or a plain link in a `Gallery/list_all` of another save format ([Backups of other tools](#backups-of-other-tools)), which takes the details of a `Gallery/list` entry with the same link, else none) whose picture file the zip lacks (a save of another format, or one of ours with files missing) is a link to the original photo host, which may disappear. `State.MissingPictures` lists those links and `PictureLinks.Fetch` downloads them **when the zip is uploaded** (within about 80 seconds, as the fetch is part of the player's request; a restore fetches what is left, see the next paragraph), not only when it is approved, so a zip waiting for review does not lose them: the pictures are kept as `restores/<account id>/<SHA-256>.pictures.zip` beside the kept zip (one entry per link, named by the SHA-256 of the link) and follow it when the account adopts the zip's user id; rejecting the zip deletes them. A restore and `import pictures` read that zip as if the files were in the backup zip: same rows, same `photos/<account id>/` files, with the entry's `type`, `label` (its score), `animal` (its species) and `kill_id`. `admin gallery-details` sets these details again on the pictures an account already has, from its kept zips ([docs/server.md](server.md#import-a-backup-zip)). `import pictures` fetches the links itself when no such zip was kept. Every fetch follows these rules, because the links come from a player's file: https only, on the default port, no credentials in the link; the host is one of the settings' `picture_link_hosts` (exact name; none by default, so nothing is fetched); a redirect is followed (three at most) only when it meets these rules too; the connection goes only to a public address (checked when it is made: not loopback, private, link-local, shared, multicast or reserved, nor an IPv6 range that embeds an IPv4 address), no proxy; at most 16 MiB a picture and 1 GiB, 1,000 links a save, 15 seconds a picture and 80 seconds in all (the fetch is part of the upload request, which a proxy in front ends after about 100 seconds), four at a time; the links not fetched in time are skipped and counted, and deleting the kept `.pictures.zip` lets `import pictures` fetch again; the body must start like a JPEG. A link that fails a rule or the download is skipped and counted in the report line above.

**Uploaded avatars.** A save of a player who uploaded his own avatar on the original site may hold only the picture's link (another tool's zip, an archive claim, one of ours made before the tool saved images), not the picture. The link names the player's user id (`https://<host>/…/uploads/thumb/242x242/<uid>.jpg`), and the original avatar host still serves that thumbnail, while the website host of the link is gone. So, when the zip holds no picture of the avatar, `State.UploadedAvatarLink` names `<avatar base>/uploads/thumb/242x242/<uid>.jpg` (`<avatar base>` is `avatar_uploads`, else the recorded avatar list's address up to `/256/`: [docs/server.md](server.md#avatars); the uid is the link's), and it is read from the operator's saved copy `<avatar_uploads_dir>/242/<uid>.jpg` when there is one (no host list needed), else fetched through `PictureLinks` like a gallery link: at upload time (kept in the `.pictures.zip` beside the zip), by `import pictures`, at the claim for an archive claim (the archived uid). The avatar host must be in `picture_link_hosts`. The picture is then used exactly as a zip's avatar picture: the account's imported avatar (`photos/<account id>/avatar.jpg`), `avatar_url`/`face` and the profile's `avatar` pointing at it. A save with **no avatar at all** (an archived profile that has only the API v2 profile) is tried by the user id as well; a 404 (a player who uploaded none, its body is XML) is no JPEG, so the default avatar stays. A save that names an avatar of the server's list is never fetched: the player chose it. The avatar is the first link fetched at upload (a long gallery can use up the fetch's time budget, and what is last is skipped), and the upload's fetch gives up after about 80 seconds because it is part of the player's request: a restore (approve, `import backup` or `import pictures`) fetches every link, the avatar first, that the `.pictures.zip` beside the kept zip still lacks and adds it to that zip, with no time budget but the per-picture one (a zip kept before this, a budget that ran out, a failed fetch; an archive claim fetches only its avatar itself). A failed fetch (host not listed, refused, not a JPEG, timeout) keeps the default avatar and the importer's warning; a fetched avatar drops that warning from the report. `admin avatars` ([docs/server.md](server.md#avatars)) does the same afterwards for the accounts restored earlier.

`import pictures <zip> --account <id>` ([docs/server.md](server.md#import-a-backup-zip)) runs only `PreparePictures`, `Unpack` and the avatar of a restore on an existing account, leaving its other rows untouched. Unlike a restore it only adds: it removes no gallery row or file an earlier restore stored (a save that holds links only cannot wipe a gallery restored from files), and a picture the account already has, by the SHA-256 of its file, is not added again, so running it twice adds nothing the second time. A restore replaces the account's restored pictures as above, and also does not store a picture twice.
