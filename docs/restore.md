# Restore library

`src/Restore` (`Resurgence.Restore`) reads a backup zip made by any version of the [backup tool](backup.md) and returns a neutral player model and a report (layer A). It has no database and no server types. Storing the model is layer B, in the server (`server/Server/Restorer.cs`, [below](#storing-the-model)), in SQLite ([ADR 0001](adr/0001-sqlite-for-profiles.md)).

## Run it

`server import backup <zip> [--account <id>]` restores a zip into the server's database and prints the report: [docs/server.md](server.md#import-a-backup-zip). It reads the zip with the server's own item catalogue (an `Application/application` reply, never the one inside the zip being read) so the units rule is exact; without a catalogue the rule is `zero-only`. A zip the reader refuses prints `refused: <reason>`; a file that cannot be read prints `cannot read: <message>`; both exit 1.

In code: `Importer.Read(path or stream, catalogue, limits)` returns `Restored(Model, Report)` or throws `RestoreException`; `ApplicationCatalogue.Read(stream)` is the catalogue.

## What is refused, what is rejected

The backup zip is read once, in memory; nothing is extracted. The whole backup zip is **refused** when it breaks a cap (`Limits`: 100,000 entries, counted in the zip's central directory before it is opened, which may hold 64 MiB at most, 1 GiB of content, 64 MiB per entry, 32 MiB for the manifest, 128 MiB of JSON in total, `manifest.json` included, and 32 MiB per JSON entry (a real backup holds under 4 MiB of JSON), JSON nesting 64, more than 100:1 compression for an entry of 1 MiB or more), has an unsafe entry name (`..`, a rooted path, a drive letter, a backslash), has no `manifest.json` at the root or one folder down, a manifest that does not parse (a duplicate key included), a `uid` that is not digits only or too large for a 64-bit id, no `claim.key` or one that does not hash to `claim_hash`, a `format` newer than 2, or an identity reply whose `id` is not the manifest `uid`. A single file is **rejected** (and reported) when its SHA-256 differs from the manifest or it is not valid JSON (a duplicate key included); a file the manifest does not list is rejected too. Manifest entries with an `error` or no `sha256` are missing data, listed under `failed`, not a fault of the backup zip.

## Version and mode

No `format` in the manifest = format 1 (defined in [backup.md](backup.md#what-is-saved)); `format: 2` adds `mode`, `identity`, a per-file `date` and `checks`. `tool_version` is copied, never compared. The mode comes from the files: `Me_me.json` present = my account, otherwise public (by handle when the `Public_user/getByHostname` reply is there, else by id). A manifest `mode` that disagrees gives a warning and the files win.

## Field rules

- **Items**: `Inventory/list` wins over `Inventory/dict` for a row both hold (the dict can lag a change); a difference in `metadata`, `units` or `dir` is a warning. `Units` is the saved value only when the item catalogue the caller passes (`IItemCatalogue.HasUnits`) says the item has units (a count, as climbing gear has), otherwise null (a placeable has none, whatever number the dict holds, 0 or 1). Without a catalogue: 0 reads as null, every other value is kept, and the report says `zero-only`.
- **Positions**: `round(value * 1000)` per axis, from the number's decimal text (never a double), half away from zero. A coordinate beyond ±2,000,000 (or not a number) means no location, with a warning. A placed row (slot 23) without a position is a warning and goes to `Extras`, not to `Items`; a position without a direction keeps the direction null, with a warning. `metadata` is kept as sent (a feeder's `metadata.reserve` is never renumbered, integers stay integers).
- **Skills** as sent (level plus progress); `SkillSet.Floor()` gives the levels. **Wallet** from `Me/me` (`ems`, `gms`), own backup zips only. **Statistics**: the four `data` objects, `distance`, `duration` and the two minigame scores. **Achievements** one to one, with their `triggers` (earn times). **Trophies and lodges** as raw rows; a harvest reply with status 404 means none. So does one without a status whose body is not a harvest record (a JSON object with at least one member and none of `message`, `error`, `errorCode`). A backup run killed before it wrote its manifest can leave a 404 that way once a later run resumes it. Such a file is kept in `Extras`, with the warning `<n> harvest file(s) without a status hold no harvest record: not restored as trophies, kept in Extras`.
- **Account defaults** for the fields of the game's login reply that no web reply holds. **Membership**: `freeplay` 0, `staff` 2, `premium` 1 and `freebeta` 0 (these two inferred, flagged in the report), anything else 0 with a warning.
- **Shapes**: where an object is expected (the manifest's `checks`, a `Trophy/list` or `Page_content/minigames_list` reply, its `position`, an item's `location`), an empty `[]` reads as empty (this API sends `[]` for an empty map) and any other non-object is not read, with the warning `<what> is not an object: not read`; the rest of the reply is still read. An `Inventory/list` element that is not an object (other than `null` or `[]`), and the `own` rows of an element whose `item` is not an object, go to `Extras` as inventory rows not read.
- Every other reply (hunts, messages, friends, missions, competitions and the rest) is kept whole in `Extras` and counted under `unsupported`, one line per endpoint with the ids in its path shown as `*` (`/game/user/*/ranks`); "no entry" answers (status 404, such as a leaderboard the player is not on) are counted on one line of their own. Derived files (`map-setups.json`, `messages-index.json`, `competition-history.json`) are checked but not used: the raw replies decide.

## Report

`mode`, `complete` (`yes` = `completed_utc` present, `no`, `unknown` for a format 1 backup zip without it), the units rule used, and the lists `restored`, `unsupported`, `missing` (for example the wallet of a public backup zip, or the hunts `checks.hunts` says were saved short or whose list did not load completely, `list_failed`), `warnings`, `failed` and `rejected`. The same backup zip always gives the same model and report (items by item id, then guid).

## Storing the model

`Restorer.Import(state, zipPath, account, dataDir)` turns the model into the rows of one account in one transaction: `ClearModel`, the inserts, the audit row. The same zip always gives the same rows. Any zip is accepted and replaces the account's profile (no merge); hunt history stays. Before replacing an existing account the whole database is copied with `VACUUM INTO <db>.bak-<UTC time>`. Every imported zip is kept as `restores/<account id>/<SHA-256>.zip` in the data folder, so a disputed account can be reset and imported again.

| Model | Rows |
|---|---|
| `Items` | `items`. `Units` as read (layer A applied the catalogue). A placed item's `Position` and `Direction` (millimetres) go into its metadata under `__position` and `__direction` (the table has no columns for them); the connect reply moves them back to the row's `position` and `direction`. `WebReserve` is dropped: the connect row has none |
| `Wallet` | `wallet` (`em`, `gm`); a zip without one (a public zip) stores 0 |
| `Skills` | `skills`: weapon by item id, tracking and spotting by species slot; `xp` is `Skills.Xp(level plus progress)`. A zip without skills stores a new player's 59 + 59 |
| `Profile`, the zip's own `Me/me` | `profile`: the reply of `Me/me` without `ems`, `gms` and `unread_messages`, over the typed profile fields (`id` and `handle` are the account's) |
| `Stats` | `statistics` |
| `Achievements` | `achievements` (earn times in `triggers`). On a community server the check right after it adds the earn time of each threshold the account's statistics reach that has none, and a larger counter as `value` ([docs/server.md](server.md#achievements)) |
| `Trophies`, `Lodges` | `trophies`, `lodges` as read |
| `Extras` | `extras`, keyed by the path in the zip |
| `Account`, `Profile` | the account's `account` object (the connect reply's): handle, `user_id`, `account_id` (= the user id), hostname, gender, hunterscore, membership, avatar URL, the importer's defaults for `face` and the Facebook fields. On a community server the hunterscore is then the one the server computes from the restored statistics ([docs/server.md](server.md#the-hunterscore)), in `account` and in the profile |

What is dropped, and the report says so: the e-mail, Facebook id and other login-only fields (accounts keep none); keys named `email`, `first_name`, `last_name`, `real_name`, `address` and `phone`, anywhere in a stored reply (counted in the report); the zip's Steam id and claim hash (a Steam id match is shown to the operator as information, is not proof of ownership, and an account's `steam_id64` is only one the server verified); the web reserve of placed items.

The target is the zip's user id, created from the zip's handle (`user-<id>` without one) when it does not exist; a handle that another account has refuses the import. `--account <id>` targets an existing account, whatever the zip's user id: the account keeps its id and takes the zip's handle only when nobody else has it. A local server (`offline_mode` true) with no `--account` restores into the local account, the one the game connects as.

On a community server the same rows come from an upload, not from the command: an uploaded zip is kept for an operator and never restored automatically; the operator's `review approve <id>` restores it once per game user id, the account adopting the zip's user id and handle while it has not played ([docs/server.md](server.md#upload-a-backup-zip)). The database is not copied there.

An account with a `profile` row is a restored account. For it the server answers from its rows, not the recorded reply: the connect reply's `account`, `inventory`, `wallet`, `skills`, `user_stats` (statistics, achievements with their earn times, minigame scores, `first_time` 0), `account_info` (`steam_id` is the account's verified one or empty; no e-mail) and the `network` handle, host and user id; `Me/me`; `Skill/list`, `Statistics/total` and `Achievement/stats` for the account's own user id (on a community server `Statistics/total` answers any account's, [docs/server.md](server.md#public-reads)); and on a community server the trophy list, the trophy and lodge pages and the harvest records of the account. The restored statistics are a base: `user_stats` and `Statistics/total` add the account's closed server hunts on top, and a later restore replaces only the base ([docs/server.md](server.md#the-statistics)). Everything else of those replies still comes from the recording on a local server: the world data, `boost`, `competitions`, `inventory.infos` and `active_services`, the expedition, and the other profile reads (missions, friends, the apiv2 profile). Accounts without a `profile` row keep today's answers on a local server. A community server never answers from the recording what is a player's own: see [Recordings on a community server](server.md#recordings-on-a-community-server).

**Hunt history.** The hunts of the backup zip are read from the saved replies in `extras` when asked, with no table of their own: `Expedition/list` lists the server hunts first and then the saved hunts as saved (every saved `Expedition/list` page joined by its `offset`, each hunt once) as one paged list whose `total` counts both, and `Public_user/expedition` with a saved hunt's id answers the saved reply. Without `expedition_id` it answers the account's latest server hunt, else the newest saved one. A zip that saved no hunt keeps the recorded answers. A hunt list saved short (`checks.hunts`) lists what it holds. Saved hunts are shown only: the statistics and the hunterscore already hold them ([docs/server.md](server.md#the-statistics)).
