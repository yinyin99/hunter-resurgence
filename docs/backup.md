# Profile backup tool

`tools/backup/` is a Windows desktop app that saves a player's profile from the official servers as raw replies, before they shut down on 2026-11-11. It only reads: it never changes anything on the server.

## How it works, in short

The tool asks the official servers for your profile and saves what they answer, unchanged, in a folder on your PC. It only reads: it never changes anything on the server. The one exception is the optional Messages group: opening an unread conversation can mark it as read, and nothing can undo that.

It connects only to the official servers listed in `settings.json`, next to `backup.exe`. Your backup stays on your PC; upload to a server is not available yet. To read your own account it uses the session of the running game, and never writes that session to a file. It runs on your PC and needs no installation and no administrator rights. The backup folder, its zip and `claim.key` stay on your PC: keep the zip private, it holds your account's data, your Steam id and `claim.key`.

A backup is a copy of your profile at one moment: as it was while the backup ran. Anything you play, earn, buy or change in the game afterwards is not in it: run another backup, which goes into a new folder with the date and time in its name. "Skip files already saved" only continues a run that did not finish.

## Build and run

```
dotnet build tools/backup -c Release
dotnet test tests/Resurgence.Tests -c Release
tools\backup\publish.cmd <path\to\your\settings.json>
```

The window is WPF with the WPF UI library, restyled with the same dark theme and orange accent as the web app (it does not follow the system theme, except in Windows high contrast mode: then the system's high-contrast colours are used, read once at startup). With Windows animations off, the progress bar does not sweep while the total is unknown; the progress text says what is going on. The published exe is self-contained: players install nothing. The project is a console `Exe` for `dotnet run`; the publish profile makes the published exe a GUI one.

`publish.cmd` takes the path of a `settings.json` you filled in (see below). It publishes `tools\backup\bin\Release\net10.0-windows\win-x64\publish\backup.exe`, copies your `settings.json` beside it, and writes `backup-win-x64.zip` with both into `tools\backup\bin\Release\net10.0-windows\win-x64\`. The zip is what players download. The exe is stored uncompressed on purpose: it starts faster and needs less memory.

### settings.json

`settings.json` sits next to the exe. It holds `client_exe` (the game's exe name, used to find the running game), `oauth_consumer_key` (the website's public key) and the host names the app talks to: `api_host`, `apiv2_host`, `web_host`, plus `photo_host`, `static_host`, `avatar_host` (pictures are fetched only from https URLs on a host listed here, so every picture host needs a key) and any other `*_host` that pictures may come from. The repository only contains `tools/backup/settings.example.json` with placeholders; while the file is missing or a required key is missing or still a placeholder, the window says once, in its language, that `settings.json` must sit next to `backup.exe` and Start stays off; the file and key are in the Details log. The real values are not in this repository: whoever builds a release supplies them (the release workflow reads them from repository secrets, see `CONTRIBUTING.md`). The release zip therefore carries them in plain text: anyone who downloads it can read the host names, the exe name and the consumer key in its `settings.json`. That is intended: the app cannot reach the official servers without them, and the consumer key is the website's public key, not a secret.

## Languages

The window is in English, French, Spanish, Portuguese (Brazil), German or Russian. It starts in the Windows display language when that is one of them, otherwise in English. The picker in the window switches it (not while a backup runs) and the choice is kept in `%APPDATA%\game-backup\language.txt`, next to `claim.key`. The texts are standard .NET resources: `Strings.resx` (English, also the fallback) and one `Strings.<culture>.resx` per language. The log lines and everything in `manifest.json` stay English. To add a language, add its `Strings.<culture>.resx` with the same keys, list it in `Loc.Languages` and in `SatelliteResourceLanguages` of the publish profile; the tests fail when a resx lacks a key or has other `{0}` placeholders than the English one.

## What is saved

One file per request, named by endpoint and parameters (for example `Inventory_dict__user_id=<id>.json`), body exactly as the server sent it. `manifest.json` lists every file (`path`, `endpoint`, `params` without the token, `status`, `sha256`, `time_utc`, `date`) and the requests that did not give a file (`error`), plus `format`, `mode`, `identity`, `tool_version`, `groups`, `uid`, `handle`, `claim_hash`, `checks` and, once a run ended whole (not cancelled, nothing left to retry), `completed_utc`. `format` is 2 from this release; a zip without `format` (every release up to v0.3.0-rc.1) is format 1. `mode` is `own` (My account) or `public` (Public profile), and `identity` says how the account was named: `me` (own account), `handle` or `id` (public); a public run that continues a folder holding own-account files keeps `own` and `me`. `time_utc` is the PC's clock when the file was saved; `date` is the server's clock, the HTTP `Date` header of the reply in UTC, absent when the server sent none (and on failed requests and derived files). `checks` is there only when the hunt history is short (see the table): `checks.hunts` has `total` (the number `Expedition/list` gives), `listed` (the hunts the list held) and `saved`; it is omitted when the run saved them all. The output folder is `backup-<uid>`; the zip is `backup-<uid>-<time>.zip` beside it. "Skip files already saved" only continues a run that did not end whole (cancelled, or with requests that failed). A new run after a finished one is a new snapshot in `backup-<uid>-<yyyyMMdd-HHmmss>`, so hunts played since are saved and the first backup stays as it was.

| Group | Content | Needs the running game |
|---|---|---|
| Profile | statistics, skills, achievements, challenges, personal leaderboards (every season), minigame positions, membership bundles, the item catalogue, avatar picture, antler boards, campaign scores (public; `null` while no campaign runs) | no |
| Inventory and dogs | owned items and dogs, placed-item positions, loadout | partly |
| Map setups | the equipment placed on each map (`map-setups.json`, see below) | partly |
| Trophies and lodges | trophy list, lodges, harvest record of each own trophy | partly |
| Hunt history | every hunt with its kills, shots and scores; if the server lists more hunts than could be saved, the result bar says so and the manifest has `checks.hunts` | no |
| Kill pages and photos (off by default) | score sheet page of every scored kill and the picture of every kill that has one, newest hunts first; many requests | no |
| Account | missions, wallet history, bank transactions, competition states, message settings, recruits, backgrounds | yes |
| Friends | friends list, friend requests | partly |
| Photos (off by default) | gallery pictures at full size | no |
| Messages (off by default) | every conversation, read and unread, in full; unread ones will show as read afterwards (see "Messages") | yes |
| Competition history (off by default) | your result in each finished competition the website still lists (about the last 7 days), optionally older editions; hundreds of requests (see "Competition history") | no |

Pictures are fetched only from https URLs on a host listed in `settings.json`; anything else is logged and skipped. `oauth_consumer_key` is sent for the item catalogue request only and never appears in a file name, the log or the manifest.

Requests run in one lane per host: at most one request at a time and one start per second per host, with retries and back-off. A host that stays silent after its retries gets one attempt per request until it answers again; after 20 requests in a row that gave up, the run stops with "Backup stopped" instead of trying the rest (what was saved is kept, run again later with resume on). A `Retry-After` on a 429 or 503 is waited out instead of the fixed back-off, for at most 120 seconds. Every request has the same 120 second timeout: replies of the website are slow and a shorter limit would fail good requests. The progress line shows the requests done, the group in work and the time left, worked out from the pace of the last 90 seconds (in hours and minutes when long). Cancel ends the run after writing `manifest.json`, so a resumed run continues.

### Map setups

The group is on by default and runs last, after every other group, so it reads the inventory at the end of the run. Every placed item (tents, blinds, tree stands, tripods, towers, feeders, decoys, climbing gear and the rest) is an inventory row in slot 23 with a `location`. The position, direction, settings (`metadata`) and units of each placed item are saved per map.

- **Raw replies.** `Inventory/dict` and `Inventory/list` are asked again at the end of every run, even with "skip files already saved" on, so a setup changed after an earlier backup is never saved stale. They overwrite the files of the inventory group (same names).
- **`map-setups.json`.** Made by the tool from those replies, listed in the manifest with `derived: true` and its SHA-256, and part of the zip. It has `format`, `tool_version`, `uid`, `sources` (file, SHA-256 and row counts of each read, or `unavailable` / `skipped: public profile`), `totals` (placed items, maps, count per kind) and `reserves`: one entry per map (the reserve number as the service counts it, from 1; the name when the item catalogue was saved; items with no reserve are under `null`). Each item has `guid`, `item_id`, `define` and `name` (from the catalogue), `kind` (tent, tree_stand, tripod, shooting_rest, blind, tower, feeder, decoy, caller, target, mat, flag, climbing, other), `units`, `pos`, `dir` and `metadata` exactly as the server sent them (never rounded or converted), and `in`: which sources list it (`dict`, `list`, `me`).
- **Sources.** `Inventory/dict` and `Inventory/list` (both public, so a public profile has them too) and, in My account mode, the `worlditems` of the identity reply, which has a position but no direction and is only a cross-check: an item it alone lists is never a row. When both inventory replies hold a row, the list is used, because the dict can lag a change (after a feeder refill it kept the old bait amount for a minute); a row only the dict has is kept. An item counts as placed only when its slot is 23; picked-up items (slot 0, 1, 11 to 17) can keep an old location and are ignored. The item names and kinds come from the item catalogue; if the profile group did not save it, the setups group fetches it (the same request and file).
- **Checks** (never fail the run): `location_null` (placed items without a position, left out of `reserves`), `location_null_rows` (the whole row of each of them: `guid`, `item_id`, `units`, `metadata`, so the item can be given back), `only_in` (per source, items that another source lacks), `pos_differs` (items whose position differs between sources), `metadata_differs` (items whose `metadata`, `units` or `dir` differ between dict and list, compared as the server wrote them) and `dir_null` (items with a position but no direction; they are saved, a restore has to invent a direction). The result bar shows "Map setups: N placed items on M maps", "none placed", or a warning when a check found something. If one read failed, its source says `unavailable` and the file is built from the other one; if both failed no file is written and an older one is removed.
- **Climbing gear.** `units` of a placed path is the cost of the anchor it is bound to: 20 or 25. It is kept as sent. About 1% of the rows carry other values (a stack placed without being trimmed); they are valid and kept.
- **Restore format.** Nothing is re-typed: `pos`, `dir`, `units` and `metadata` are the server's own JSON text, so a restore can rebuild the row the game is given. That row is: `guid` as a string of the web `id` (a JSON number reads as 0), `item_id`, `slot` 23, `units` the value from the inventory dict only when the catalogue item has `units` (a count, as climbing gear has), otherwise null (a placeable has none, whatever number the dict holds, 0 or 1), `position` and `direction` as `round(web value * 1000)` integers (millimetres; round, not truncate, because a binary double can sit just below, as `3144.645 * 1000` does, so read the number as decimal text), and `metadata` as is. A float or string where the game expects an integer reads as 0. A feeder's `metadata.reserve` is the web map number minus 1 (`location.reserve` is 1-based) and is kept as sent, because it decides whether the feeder belongs to the bait map. Every load carries the placed rows of all maps and the game skips those outside the loaded map, so no filtering per map is needed. Per class only some `metadata` keys matter, all integers: tree stand `tree_shape_key`, `tree_shape_position_x/y/z`; rifle rest `erect_stance`; tower `deployable_timestamp`, `is_constructing`; feeder `bait_amount`, `bait_attractiveness`, `penalty_remaining`, `reserve` (its other keys belong to the server but are saved too); everything else (tents, blinds, tripods, mats, flags, decoys, callers, targets, climbing gear) has `{}`.

### Messages

The group is off by default. It saves `Chat/conversations` first and unchanged: its `read` flag per conversation is the original state, and it is never overwritten later in the run. Then it asks for every conversation, one `Chat/conversation` request per partner (the website has no paging for it), and saves each reply as it came, in `Chat_conversation__user_id=<id>.json`. Read conversations go first, then the unread ones, so that a run that stops has touched the unread ones last. Opening an unread conversation can mark it read on the server: the website sets `read` itself after that request and has no call to undo it. The group description says so, and when conversations were opened the result bar adds "N unread conversations were opened and now show as read." (the count is of the unread ones opened in this run). Resume skips conversations whose file is saved; one that failed or was not reached is asked for on the next run. `messages-index.json` (derived) has `format`, `tool_version` and `uid` like the other derived files, and lists per conversation `user_id`, `read`, the file, the `total` the reply states and the number of messages in it; `checks.possibly_capped` names the conversations where the two differ. The group needs the game session.

### Competition history

The group is off by default and uses public reads, so it works in public-profile mode too. The server has no per-player history; a past result is the player's row in the edition page. The tool pages `Page_content/list_previous_competitions` (20 at a time, by the list's `total`), reads `Page_content/competitions_new` for each edition, does the same for the community league list, and saves every reply as it came. `competition-history.json` (derived, listed in the manifest, part of the zip) has per edition `id`, type id and name, `start`, `end`, and the player's `position` and `points`; the row is found by user id. `complete` is `true` only when every list page and every edition came; otherwise it is `false` and `failed` names what is missing (`request`, plus the `offset` for a list page or the `id` for an edition, and a `reason`: `no data` for a request that gave no file, `not an edition` for an edition reply that was saved but is not an object (for example `null`), `total not readable` when the list's total is there but is not a whole number, so the rest of the list was not asked). A failed list page does not stop the other pages, the community list or the editions. The next run with "skip files already saved" asks for the missing requests only and writes `complete: true` with an empty `failed`.

- **A window of about 7 days.** The list holds only the newest 250 finished editions, about the last week. A backup made more than a week after a win does not contain it unless the older-editions switch is on.
- **Entrants capped at 100.** The server returns at most the best 100 entrants of an edition. A player ranked lower is not in the reply; that edition is `not_listed: true` (no rank is guessed). A win cannot be missing.
- **Older editions (a separate switch, off by default).** Every edition reply lists earlier editions of the same type. With the switch on, the tool follows them, each edition once, past the window of the list. That can be thousands of requests (an estimate: up to about 7,000 more, 2 hours or more at one request per second per host). The switch is only available while the history group is ticked.
- **Cost and resume.** Without the switch it is hundreds of requests, tens of KB each, and takes about half an hour: the list pages are slow (often over a minute each, a few run into the 120 second timeout and are retried). There is no shorter timeout: the slow replies are good ones. Resume skips editions whose file is saved (finished editions never change); an edition that failed is asked again on the next run and does not stop the others.

### Two modes

- **My account**: reads the signed-in player's data using the session of the running game. The app asks the watcher for the current session before every request that needs it, so a game restarted during a long run brings its new session into the run (a "session refused" mark is cleared by it). A JWT that the server refuses (401) is replaced and that request is made once more.
- **Public profile**: type a handle or id. Only public data is saved; requests that need the game session are logged as "skipped, needs the game" and are not counted as failed.

"Select all" and "Select none" beside "What to save" tick or untick the groups that can be used in the chosen mode; in Public profile mode the groups that need the game stay off. The two source choices move with all four arrow keys (one Tab stop). Enter in the handle field or the output folder field starts a backup; Start is not the window's default button, so on a tick, a switch, a link or any other button Enter does only what that control does and never starts a backup. It never cancels a running one. While `settings.json` is missing, Enter in a field does nothing but is announced to a screen reader with the status sentence. Alt+Space, or a right click on the title bar, opens the window menu (Restore, Move, Size, Minimize, Maximize, Close), so the window can be moved and sized from the keyboard.

The window keeps the language picker, the mode, the groups (in two columns) and the options in one scrolling area; Start (Cancel while a backup runs), the result bar and Details stay in view below it. Until you resize it, the window is as tall as its content, up to the height of the work area, and follows the content both ways (a longer language, the result bar, the open log make it taller, and it shrinks back). Dragging an edge, or Alt+Space, Size, gives it a height to keep: it then grows only when what cannot scroll (Start, the result bar, Details, and a part of the cards beside them) needs more room, goes back to your height when that fits again, never below it, and the cards scroll. The window's top edge stays where it is unless the window would leave the work area; then it moves up only as far as needed, and back when the window shrinks again, unless you moved it in between. A maximized or minimized window is left alone, and Restore brings back the bounds it had. While a backup runs the cards are disabled, also for a screen reader (the status line and the "What to save" heading are not), but keep their colours so you can still read what is being saved; a ticked group stays orange, like a switch that is on and like the selected mode. What is off for its own reason (the groups that need the game in Public profile mode, the older-editions switch without its group, Upload) keeps the dim look it has when idle. If Start finds something missing, it says so in an informational bar and focuses the field when that is the handle; the bar closes by itself as soon as it is fixed. It checks in this order: nothing ticked, no handle (Public profile), no game session (My account). A bar about a backup (saved, cancelled, stopped, failed) stays until the next run.

### Slow options

Kill pages and photos, Photos and Competition history carry a `slow` tag and, like the older-editions switch, a cost line under the row; the lines use only the figures given in this document ("many requests", "large", "hundreds of requests, tens of KB each", "up to about 7,000 more requests, 2 hours or more"). When Start (or Enter in a field) finds one of them ticked, and the checks above pass, a dialog lists the ticked ones with their cost and says the run can take a long time (at most one request per second per host), that the progress line shows the time left, and that Cancel keeps what is saved and "Skip files already saved" continues from there. Its buttons are "Start backup" and "Back": Back has the focus, Esc and the close button are Back, and nothing starts unless "Start backup" is pressed. There is no "don't ask again", and the wording does not change with resume. Hunt history, Messages, Account and Trophies are not tagged: their cost grows with the account and no figure is documented.

When a run ends whole with nothing failed, the result bar ends with a line of its own: "Backup finished <date time>. Anything you play, earn, buy or change in the game after that is not in it: run a new backup." The time is when the run ended, in the window's language. A run with gaps, a cancelled one and a stopped one do not get it: they are continued with resume, not redone.

## What is not saved

- A picture of the placed equipment (the positions themselves are saved, see "Map setups").
- In-game settings and controls (graphics settings and key bindings stay on the player's PC) and any client state that was never sent to the server.
- Vehicle position, map markers and drawn lines, and the last position or start point: the server does not store them (the vehicle is made per hunt, markers and lines live on the in-game map page only, the start point is chosen at launch).
- Other players' data (only the public profile of a typed handle is saved).
- Tokens: a reply that contains an access token, a JWT, the website's public key (`oauth_consumer_key`) or the string `refresh_token` is dropped and logged. The JWT the app obtains for some requests is kept in memory only.
- Not data: a reply is saved only if it is what was asked for. API replies must be valid JSON (`null` is), pictures must start with a JPEG, PNG, GIF or WebP header, score sheets must contain a table. A proxy, login or error page, or a cut-off reply, is not saved; the request is listed in `manifest.json` as failed ("reply is not data") and the result bar says "some pages did not hold data".
- Dead on the server: a picture or score sheet whose address answers 404 is gone for good. It is listed in `manifest.json` with the error "dead on the server (404)", is not counted among the failed requests (so it never asks you to run again) and the result bar shows its own count. A resumed run does not ask for it again.
- Kills and photos off: when "Kill pages and photos" or "Photos" was not ticked, the result bar adds "Kill pages and photos were not saved; tick them for a complete backup." Messages are off by default for privacy and get no such hint; when they ran, the result bar says how many unread conversations were opened (see "Messages").
- Data only the game's own load reply carries: achievement earn times, the player's own minigame score when outside the top 30, daily-mission and objective counters, the imperial-units setting, the list of reserve licences. The website has no endpoint for them. None blocks a restore: the saved achievement values, statistics, mission states, trophies and inventory rebuild the profile; these only affect toasts, counters and the unit display.
- Gift codes, and any endpoint that changes state.

The app shows a short, plain-language version of this list in a dialog, behind the "What isn't saved?" link next to Start. It lists only what you will not find in a backup: the equipment pictures, settings and controls, vehicle position and map drawings, other players' data, the data only the game's load carries, and gift codes. The items about how the tool works (tokens, "not data" replies, dead files, the kills and photos hint) are left out: the result bar reports them when they happen. A "How does it work?" link in the status card, at the top, opens a short version of "How it works, in short" in a dialog.

## Privacy

- The session token is never written to a file, the log, the manifest or the zip. It is sent only to the API host, as the form field the website uses.
- In My account mode the manifest has `steam_id64`: the Steam account signed in on this PC. The app reads the value `ActiveUser` under `HKCU\Software\Valve\Steam\ActiveProcess` from the registry, read-only; nothing else from Steam, no Steam API, no network. It is stored only in the player's own folder and zip and is never sent anywhere by the app. If nobody is signed in the field is omitted. Public profile mode never writes it. A community server can use it as a hint that the Steam account signing in owns the backup, not as proof.
- Keep the zip private: it holds the account's data, the Steam id and `claim.key`.

## How the token is found

The launcher starts the game with a connect argument on its command line that carries the session. The app reads the command line of the running game process every 2 seconds (Windows `NtQueryInformationProcess`, same user, no administrator rights, no injection, no memory read) and keeps the access token. A new hunt means a new process and a new token, which replaces the old one. The refresh token in the same argument is parsed away and dropped. The launcher's own command line has no token, so the app waits until a hunt has started.

If the API refuses the token, the app says "start a hunt to refresh" and skips the requests that need it. Start a hunt and run again.

## Claim key

On first run the app writes 32 random bytes to `%APPDATA%\game-backup\claim.key`: the key is made once per PC and kept there. Every backup folder and zip contains that file as `claim.key`, so every backup made on one PC contains the same key, and two zips with the same `claim_hash` came from the same PC. `manifest.json` records only its SHA-256 as `claim_hash`. The key is a hint, not proof: anyone who has the zip has the key. Keep the zip private: the key, together with the Steam account, is what a future restore uses as a hint that the backup is yours.

The first restore will be local: a server on your own PC reads your own zip. A community server is planned after that, with Steam sign-in first (email sign-in may follow). The Steam account recorded in the backup links it to your sign-in. These are hints, not proof: if two people claim the same profile, the claim may be reviewed.

## Tests

`dotnet test tests/Resurgence.Tests -c Release` runs the xUnit tests of the backup tool (folder `BackupTool`) against a fake HTTP handler and a harmless fake process; no real server is contacted. The same project holds the launcher's tests. It exits 0 when every test passes.
